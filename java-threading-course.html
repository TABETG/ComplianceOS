01

Concepts fondamentaux

Junior

Avant de coder, il faut comprendre pourquoi le multithreading existe. Un programme Java tourne par défaut sur un seul fil d'exécution — le main thread. Si une tâche est longue (réseau, I/O, calcul), tout le programme se bloque.

🧵

Thread

Unité d'exécution légère au sein d'un processus. Partage la mémoire heap mais possède sa propre stack.

⚙️

Processus

Programme en cours d'exécution avec sa propre mémoire isolée. Un processus peut contenir plusieurs threads.

🔄

Concurrence

Plusieurs tâches semblent s'exécuter en même temps (interleaving sur un seul cœur).

⚡

Parallélisme

Plusieurs tâches s'exécutent vraiment simultanément sur plusieurs cœurs CPU.

Thread vs Processus

AspectThreadProcessus
MémoirePartagée (heap)Isolée
CréationRapide (~µs)Lente (~ms)
CommunicationDirecte (variables)IPC (socket, pipe…)
Crash impactTout le processusSeulement lui-même
💡

La JVM démarre toujours avec plusieurs threads en arrière-plan : main, GC, Finalizer, Signal Dispatcher…

02

Créer un Thread

Junior

Il existe 3 façons principales de créer et démarrer un thread en Java.

① Étendre Thread

public class MonThread extends Thread {
    @Override
    public void run() {
        System.out.println("Thread : " + Thread.currentThread().getName());
    }
}

// Utilisation
MonThread t = new MonThread();
t.start(); // ⚠️ NE PAS appeler run() directement !
⚠️

Appeler t.run() au lieu de t.start() exécute le code sur le thread courant sans créer de nouveau thread — erreur classique en entretien !

② Implémenter Runnable

public class MaTache implements Runnable {
    @Override
    public void run() {
        System.out.println("Runnable en action !");
    }
}

Thread t = new Thread(new MaTache());
t.start();

// Avec lambda (Java 8+) — la vraie vie
Thread t2 = new Thread(() -> System.out.println("Lambda thread !"));
t2.start();
✅

Préférez toujours Runnable à l'héritage Thread : Java n'a pas l'héritage multiple, et implémenter Runnable vous laisse libre d'hériter d'une autre classe.

③ Callable + Future (retour de valeur)

import java.util.concurrent.*;

Callable<Integer> tache = () -> {
    Thread.sleep(1000);
    return 42;
};

ExecutorService executor = Executors.newSingleThreadExecutor();
Future<Integer> future = executor.submit(tache);

System.out.println("En attente du résultat...");
Integer result = future.get(); // bloque jusqu'à la fin
System.out.println("Résultat : " + result); // 42

executor.shutdown();

Méthodes importantes

Thread t = new Thread(() -> { /* ... */ });

t.start();              // démarre le thread
t.join();               // attend la fin du thread
t.join(2000);           // attend 2s max
t.interrupt();          // signal d'interruption
t.isAlive();            // true si encore en vie
t.getState();           // retourne Thread.State
t.setDaemon(true);     // thread démon (finit avec main)
t.setPriority(5);     // 1 (MIN) à 10 (MAX), défaut 5

// Méthodes statiques
Thread.sleep(1000);     // pause 1s (lève InterruptedException)
Thread.yield();          // hint au scheduler de céder le CPU
Thread.currentThread(); // thread courant

Gestion de l'interruption

Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            System.out.println("Travaille...");
            Thread.sleep(500);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // ✅ Bonne pratique : restaurer le flag
            break;
        }
    }
    System.out.println("Thread arrêté proprement");
});

t.start();
Thread.sleep(2000);
t.interrupt(); // demande l'arrêt
🚫

Thread.stop() et Thread.suspend() sont dépréciés depuis Java 1.2 — ils peuvent laisser des objets dans un état incohérent. Utilisez toujours l'interruption ou un flag volatile.

04

Synchronisation

Intermédiaire

Quand plusieurs threads accèdent à la même variable en écriture, on a une race condition. Le mot-clé synchronized garantit qu'un seul thread exécute un bloc à la fois.

Le problème sans synchronisation

public class Compteur {
    private int valeur = 0;

    public void incrementer() {
        valeur++; // ❌ NON ATOMIQUE : read → modify → write
    }
}

// Résultat attendu avec 2 threads × 10 000 : 20 000
// Résultat réel : 17 432 (ou n'importe quoi...)

Méthode synchronisée

public class CompteurSûr {
    private int valeur = 0;

    public synchronized void incrementer() {
        valeur++; // ✅ Protégé par le monitor de l'objet
    }

    public synchronized int getValeur() {
        return valeur;
    }
}

// synchronized static → monitor de la CLASS (pas de l'instance)
public static synchronized void methodeStatique() { /* ... */ }

Bloc synchronisé

public class BanqueService {
    private final Object verrou = new Object();
    private double solde = 1000.0;

    public void retirer(double montant) {
        synchronized (verrou) { // verrou minimal sur l'objet dédié
            if (solde >= montant) {
                solde -= montant;
                System.out.println("Retrait OK : " + montant);
            }
        }
        // Le reste du code n'est pas bloqué
    }
}

Le mot-clé volatile

public class FlagExample {
    // Sans volatile : les threads peuvent lire une valeur cachée (CPU cache)
    private volatile boolean arrete = false;

    public void travailler() {
        while (!arrete) {
            // boucle
        }
        System.out.println("Arrêté !");
    }

    public void arreter() {
        arrete = true; // visible immédiatement par tous les threads
    }
}
💡

volatile garantit la visibilité mais PAS l'atomicité. volatile int i; i++; reste une race condition ! Pour des opérations composées, utilisez synchronized ou les classes Atomic*.

05

wait() / notify() / notifyAll()

Intermédiaire

Ces méthodes permettent la communication inter-threads via le monitor d'un objet. Elles ne peuvent être appelées que depuis un bloc synchronized.

Exemple Producteur / Consommateur

public class FileAttente {
    private final Queue<String> file = new LinkedList<>();
    private final int capaciteMax;

    public FileAttente(int capaciteMax) {
        this.capaciteMax = capaciteMax;
    }

    // Producteur
    public synchronized void produire(String item) throws InterruptedException {
        while (file.size() == capaciteMax) {
            wait(); // ✅ while, PAS if (spurious wakeup)
        }
        file.add(item);
        System.out.println("Produit : " + item);
        notifyAll(); // réveille les consommateurs en attente
    }

    // Consommateur
    public synchronized String consommer() throws InterruptedException {
        while (file.isEmpty()) {
            wait(); // attend qu'il y ait quelque chose
        }
        String item = file.poll();
        notifyAll(); // réveille les producteurs bloqués
        return item;
    }
}
⚠️

Utilisez toujours while et jamais if autour de wait(). Les spurious wakeups (réveils parasites) peuvent sortir un thread de wait() sans qu'un notify ait été appelé.

MéthodeEffet
wait()Libère le lock et met le thread en WAITING
wait(ms)Libère le lock, attend max ms ms (TIMED_WAITING)
notify()Réveille UN thread en attente (aléatoire)
notifyAll()Réveille TOUS les threads en attente (plus sûr)
06

ExecutorService & Thread Pools

Intermédiaire

Créer un thread à chaque tâche est coûteux. Les thread pools réutilisent des threads pré-créés. C'est le pattern standard en production.

Types de pools

import java.util.concurrent.*;

// Pool fixe — N threads max, file d'attente illimitée
ExecutorService pool = Executors.newFixedThreadPool(4);

// Thread unique — garantit ordre séquentiel
ExecutorService single = Executors.newSingleThreadExecutor();

// Pool élastique — crée des threads à la demande, réutilise les idle
ExecutorService cached = Executors.newCachedThreadPool();

// Pool planifié — pour les tâches récurrentes ou différées
ScheduledExecutorService sched = Executors.newScheduledThreadPool(2);

// Work-stealing (Java 7+) — pour les tâches fork/join
ExecutorService fj = ForkJoinPool.commonPool();

Utilisation complète

ExecutorService executor = Executors.newFixedThreadPool(3);

// Soumettre des Runnable
executor.execute(() -> System.out.println("Tâche 1"));

// Soumettre des Callable avec Future
Future<String> f = executor.submit(() -> {
    Thread.sleep(500);
    return "Résultat";
});

try {
    String res = f.get(2, TimeUnit.SECONDS); // timeout
} catch (TimeoutException e) {
    f.cancel(true); // annulation
}

// Arrêt propre — TOUJOURS dans un finally ou try-with-resources
executor.shutdown();                    // n'accepte plus de nouvelles tâches
executor.awaitTermination(30, TimeUnit.SECONDS); // attend max 30s
executor.shutdownNow();                 // force l'arrêt (interrupt)

ThreadPoolExecutor personnalisé

// Pour un contrôle total en production
ThreadPoolExecutor custom = new ThreadPoolExecutor(
    2,                          // corePoolSize
    10,                         // maximumPoolSize
    60, TimeUnit.SECONDS,       // keepAliveTime
    new ArrayBlockingQueue<>(100), // workQueue bornée
    new ThreadFactory() {      // nommage des threads
        int count = 0;
        public Thread newThread(Runnable r) {
            return new Thread(r, "worker-" + count++);
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy() // politique de rejet
);
🔧

Politiques de rejet : AbortPolicy (exception, défaut), CallerRunsPolicy (le thread appelant exécute la tâche), DiscardPolicy (ignore silencieusement), DiscardOldestPolicy (vire la plus ancienne).

invokeAll & invokeAny

List<Callable<String>> taches = List.of(
    () -> { Thread.sleep(100); return "A"; },
    () -> { Thread.sleep(200); return "B"; },
    () -> { Thread.sleep(50);  return "C"; }
);

// invokeAll : attend TOUTES les tâches
List<Future<String>> resultats = executor.invokeAll(taches);

// invokeAny : retourne dès qu'une tâche réussit (ici "C")
String premier = executor.invokeAny(taches); // "C"

Locks avancés (java.util.concurrent.locks)

Avancé

Le package java.util.concurrent.locks offre des mécanismes plus flexibles que synchronized.

ReentrantLock

import java.util.concurrent.locks.*;

public class CompteurLock {
    private final ReentrantLock lock = new ReentrantLock();
    private int valeur = 0;

    public void incrementer() {
        lock.lock();
        try {
            valeur++;
        } finally {
            lock.unlock(); // ✅ TOUJOURS dans finally !
        }
    }

    // tryLock : non-bloquant
    public boolean essayerIncrémenter() {
        if (lock.tryLock()) {
            try {
                valeur++;
                return true;
            } finally {
                lock.unlock();
            }
        }
        return false; // lock non disponible, on n'attend pas
    }

    // tryLock avec timeout
    public void avecTimeout() throws InterruptedException {
        if (lock.tryLock(500, TimeUnit.MILLISECONDS)) {
            try { valeur++; }
            finally { lock.unlock(); }
        }
    }
}

ReadWriteLock — Optimisation lecture/écriture

public class Cache<K, V> {
    private final Map<K, V> map = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock  = rwLock.readLock();
    private final Lock writeLock = rwLock.writeLock();

    public V get(K key) {
        readLock.lock(); // plusieurs lecteurs simultanés OK
        try { return map.get(key); }
        finally { readLock.unlock(); }
    }

    public void put(K key, V value) {
        writeLock.lock(); // exclusif : bloque tous les lecteurs/écrivains
        try { map.put(key, value); }
        finally { writeLock.unlock(); }
    }
}

StampedLock (Java 8+) — Optimistic Reading

StampedLock sl = new StampedLock();
double x = 0, y = 0;

// Lecture optimiste (sans lock !) — très rapide
long stamp = sl.tryOptimisticRead();
double cx = x, cy = y;
if (!sl.validate(stamp)) { // quelqu'un a écrit entre-temps ?
    stamp = sl.readLock();  // on repasse en lecture classique
    try { cx = x; cy = y; }
    finally { sl.unlockRead(stamp); }
}

Condition Variables (alternative à wait/notify)

ReentrantLock lock = new ReentrantLock();
Condition nonVide = lock.newCondition();
Condition nonPleine = lock.newCondition();

// Producteur
lock.lock();
try {
    while (file.size() == max) nonPleine.await();
    file.add(item);
    nonVide.signal(); // signale spécifiquement les consommateurs
} finally { lock.unlock(); }

Classes Atomic

Avancé

Les classes java.util.concurrent.atomic utilisent les instructions CPU CAS (Compare-And-Swap) pour des opérations atomiques sans verrou — bien plus rapide que synchronized en faible contention.

AtomicInteger — le plus utilisé

import java.util.concurrent.atomic.*;

AtomicInteger compteur = new AtomicInteger(0);

compteur.incrementAndGet(); // ++i atomique → retourne nouvelle valeur
compteur.getAndIncrement(); // i++ atomique → retourne ancienne valeur
compteur.addAndGet(5);        // i += 5
compteur.get();               // lecture

// CAS manuel
boolean ok = compteur.compareAndSet(10, 20);
// Met 20 seulement si la valeur actuelle est 10

// Java 8 : updateAndGet
compteur.updateAndGet(v -> v * 2); // atomique

AtomicReference

AtomicReference<String> ref = new AtomicReference<>("initial");

ref.set("nouveau");
String ancien = ref.getAndSet("autre");
boolean ok = ref.compareAndSet("autre", "final");

LongAdder vs AtomicLong (Java 8+)

// LongAdder est préféré pour les compteurs très contendus
// → distribue les mises à jour sur plusieurs "cellules" internes
LongAdder adder = new LongAdder();
adder.increment();
adder.add(5);
long total = adder.sum();    // somme toutes les cellules
adder.reset();              // remet à zéro

// AtomicLong : meilleur quand on lit souvent (valeur précise à tout moment)
// LongAdder  : meilleur quand on écrit souvent (compteurs de métriques)

Collections concurrentes

Intermédiaire

N'utilisez jamais ArrayList, HashMap etc. en multithreading sans synchronisation. Java fournit des alternatives thread-safe optimisées.

ConcurrentHashMap — le plus important

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// Opérations atomiques
map.putIfAbsent("clé", 1);
map.computeIfAbsent("clé", k -> calculerValeur(k));
map.merge("clé", 1, Integer::sum); // incrémente ou initialise
map.compute("clé", (k, v) -> v == null ? 1 : v + 1);

// Ne verrouillez JAMAIS manuellement un ConcurrentHashMap !
// Il gère ses propres locks par segment (Java 8 : par bucket)

BlockingQueue — cœur du Producteur/Consommateur

// Implémentations
BlockingQueue<String> q1 = new ArrayBlockingQueue<>(100); // borné
BlockingQueue<String> q2 = new LinkedBlockingQueue<>();    // illimité
BlockingQueue<String> q3 = new PriorityBlockingQueue<>();  // priorité
BlockingQueue<String> q4 = new SynchronousQueue<>();      // transfert direct

// Opérations clés
q1.put(item);                   // bloque si pleine
q1.take();                      // bloque si vide
q1.offer(item, 1, TimeUnit.SECONDS); // avec timeout
q1.poll(1, TimeUnit.SECONDS);   // avec timeout

CopyOnWriteArrayList

// Chaque modification crée une copie de la liste
// Idéal : beaucoup de lectures, très peu d'écritures
CopyOnWriteArrayList<String> liste = new CopyOnWriteArrayList<>();
liste.add("item"); // coûteux (copie), mais les itérateurs sont safe

// L'itérateur ne lève jamais ConcurrentModificationException
for (String s : liste) { /* safe même si liste modifiée pendant l'itération */ }

Problèmes classiques

Avancé

🔴 Deadlock

Deux threads s'attendent mutuellement pour toujours.

Object ressourceA = new Object();
Object ressourceB = new Object();

// Thread 1 : prend A, veut B
new Thread(() -> {
    synchronized(ressourceA) {
        Thread.sleep(100);
        synchronized(ressourceB) { // ← attend Thread 2
            System.out.println("T1 a A et B");
        }
    }
}).start();

// Thread 2 : prend B, veut A
new Thread(() -> {
    synchronized(ressourceB) {
        Thread.sleep(100);
        synchronized(ressourceA) { // ← attend Thread 1 → DEADLOCK
            System.out.println("T2 a B et A");
        }
    }
}).start();

// ✅ Solution : toujours acquérir les locks dans le même ordre
// → Les deux threads prennent A d'abord, puis B

🟡 Livelock

Deux threads réagissent continuellement l'un à l'autre sans progresser (comme deux personnes dans un couloir).

🟠 Starvation

Un thread ne parvient jamais à acquérir un lock car d'autres threads sont toujours prioritaires.

// Solution : ReentrantLock avec fair = true
Lock fairLock = new ReentrantLock(true); // ordre FIFO garanti

🔵 Outils de diagnostic

// Détecter les deadlocks programmatiquement
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads();
if (deadlocked != null) {
    ThreadInfo[] infos = bean.getThreadInfo(deadlocked);
    for (ThreadInfo info : infos) {
        System.out.println("Deadlock : " + info.getThreadName());
    }
}

Outils de synchronisation avancés

// CountDownLatch — attendre N événements
CountDownLatch latch = new CountDownLatch(3);
// 3 threads font latch.countDown() quand prêts
latch.await(); // le main attend que les 3 aient fini

// CyclicBarrier — synchroniser N threads à un point
CyclicBarrier barrier = new CyclicBarrier(3, () ->
    System.out.println("Tous arrivés !"));
// Chaque thread appelle barrier.await() — attend les autres

// Semaphore — limiter l'accès à N ressources
Semaphore sem = new Semaphore(5); // 5 accès simultanés max
sem.acquire(); // prend un permis (bloque si 0)
try { /* accès à la ressource */ }
finally { sem.release(); }

// Exchanger — échange de données entre exactement 2 threads
Exchanger<String> ex = new Exchanger<>();
// Thread A : String fromB = ex.exchange("donnéeDeA");
// Thread B : String fromA = ex.exchange("donnéeDeB");
💡

Phaser (Java 7+) est la version évoluée de CyclicBarrier + CountDownLatch : les parties peuvent s'enregistrer et se désenregistrer dynamiquement.

CompletableFuture (Java 8+)

Avancé

CompletableFuture permet la programmation asynchrone et non-bloquante avec des pipelines de traitement chainés. C'est le standard moderne en Java.

Les bases

import java.util.concurrent.*;

// Tâche asynchrone sans retour
CompletableFuture.runAsync(() ->
    System.out.println("Async !"));

// Tâche asynchrone avec retour
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> {
    // s'exécute dans ForkJoinPool.commonPool()
    return appelAPILente();
});

// Avec ExecutorService dédié (recommandé en production)
ExecutorService pool = Executors.newFixedThreadPool(4);
CompletableFuture<String> cf2 = CompletableFuture.supplyAsync(
    () -> appelAPILente(), pool);

Pipeline de transformation

CompletableFuture<String> pipeline = CompletableFuture
    .supplyAsync(() -> fetchUserId())          // String
    .thenApply(id -> fetchUser(id))            // String → User
    .thenApply(User::getEmail)                // User → String
    .thenApplyAsync(email -> valider(email))   // async dans pool commun
    .exceptionally(ex -> "erreur@default.com") // gestion d'erreur
    .whenComplete((res, ex) -> log(res, ex)); // toujours appelé

String email = pipeline.get(); // bloquant
String email2 = pipeline.join(); // comme get() mais unchecked

Combinaison de futures

CompletableFuture<String> future1 = CompletableFuture.supplyAsync(() -> "Hello");
CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> "World");

// thenCombine : combine 2 futures quand les deux sont prêts
CompletableFuture<String> combined = future1
    .thenCombine(future2, (a, b) -> a + " " + b); // "Hello World"

// allOf : attend TOUS
CompletableFuture.allOf(future1, future2).join();

// anyOf : dès que le premier termine
CompletableFuture.anyOf(future1, future2).join();

// thenCompose : chaîne de futures (flatMap)
CompletableFuture<User> user = CompletableFuture
    .supplyAsync(() -> getUserId())
    .thenCompose(id -> fetchUserAsync(id)); // retourne CF<User>

Gestion d'erreurs complète

CompletableFuture<String> robuste = CompletableFuture
    .supplyAsync(() -> riskyOperation())
    .handle((result, ex) -> {        // reçoit résultat OU exception
        if (ex != null) {
            log("Erreur : " + ex.getMessage());
            return "valeur par défaut";
        }
        return result;
    })
    .thenApply(String::toUpperCase);

// Compléter manuellement
CompletableFuture<String> manual = new CompletableFuture<>();
manual.complete("valeur");           // succès
manual.completeExceptionally(new RuntimeException()); // échec
manual.completeOnTimeout("défaut", 1, TimeUnit.SECONDS); // Java 9

Questions d'entretien

Entretien

Cliquez sur une question pour révéler la réponse attendue.

🟢 Niveau Junior

Q01 Quelle est la différence entre un processus et un thread ? Junior ▼

Un processus est une instance de programme avec sa propre mémoire isolée (heap, stack, registres). Un thread est une unité d'exécution légère au sein d'un processus. Les threads d'un même processus partagent la mémoire heap mais ont chacun leur propre stack. Créer un thread est beaucoup plus rapide que créer un processus, mais les threads sont plus susceptibles de se corrompre mutuellement (race conditions, deadlocks).

Q02 Quelle est la différence entre thread.start() et thread.run() ? Junior ▼

start() crée un nouveau thread système et appelle run() dessus de façon asynchrone. run() exécute simplement la méthode sur le thread courant, comme un appel de méthode ordinaire — il n'y a donc aucun parallélisme. C'est l'une des erreurs les plus classiques en entretien.

Thread t = new Thread(() -> System.out.println(Thread.currentThread().getName()));
t.run();   // affiche "main"
t.start(); // affiche "Thread-0"
Q03 Quelle est la différence entre Runnable et Callable ? Junior ▼

Runnable a une méthode run() qui retourne void et ne peut pas lancer d'exceptions vérifiées. Callable<T> a une méthode call() qui retourne un résultat de type T et peut lancer une Exception. Callable est utilisé avec ExecutorService.submit() qui retourne un Future<T>.

Q04 Quels sont les états possibles d'un thread Java ? Junior ▼

6 états définis dans Thread.State :

  • NEW — thread créé mais pas encore démarré
  • RUNNABLE — en cours d'exécution ou prêt à s'exécuter
  • BLOCKED — en attente d'un monitor (synchronized)
  • WAITING — en attente indéfinie (wait(), join() sans timeout)
  • TIMED_WAITING — en attente temporisée (sleep(n), wait(n), join(n))
  • TERMINATED — exécution terminée
Q05 Qu'est-ce qu'un thread démon (daemon) ? Junior ▼

Un thread démon est un thread de service qui tourne en arrière-plan. La JVM se termine automatiquement quand il ne reste plus que des threads démons actifs (tous les threads non-démons sont finis). On le configure avec t.setDaemon(true) avant t.start(). Exemples : Garbage Collector, Finalizer. Attention : les threads démons peuvent être interrompus brutalement sans chance de nettoyer leurs ressources.

🟡 Niveau Intermédiaire

Q06 Qu'est-ce qu'une race condition ? Donnez un exemple et comment la corriger. Intermédiaire ▼

Une race condition se produit quand le résultat d'un programme dépend de l'ordre d'exécution non-déterministe des threads. L'opération i++ est non-atomique : elle se décompose en lire, incrémenter, écrire. Si deux threads exécutent cela simultanément, une mise à jour peut être perdue.

Solutions : synchronized, AtomicInteger, volatile (uniquement pour la visibilité, pas l'atomicité).

Q07 Différence entre synchronized et volatile ? Intermédiaire ▼

synchronized garantit la visibilité ET l'atomicité des blocs. Il empêche plusieurs threads d'entrer simultanément dans la section critique (exclusion mutuelle).

volatile garantit uniquement la visibilité : toute écriture est immédiatement visible par les autres threads (contourne le CPU cache). Il n'assure pas l'atomicité des opérations composées. Utilisez volatile pour les flags simples (boolean running), et synchronized ou Atomic* pour les compteurs ou opérations composées.

Q08 Pourquoi utiliser while et pas if autour de wait() ? Intermédiaire ▼

À cause des spurious wakeups — la JVM (ou l'OS sous-jacent) peut réveiller un thread en wait() sans qu'aucun notify() n'ait été appelé. Avec if, le thread continuerait sans vérifier si la condition est vraiment satisfaite, menant à des bugs subtils. Avec while, la condition est revérifiée à chaque réveil, garantissant la correction du programme. C'est également ce que recommande la Javadoc officielle.

Q09 Quelle est la différence entre notify() et notifyAll() ? Intermédiaire ▼

notify() réveille un seul thread arbitrairement choisi parmi ceux en attente sur le monitor. notifyAll() réveille tous les threads en attente — ils se battront ensuite pour le lock, et la condition sera revérifiée par chacun. En pratique, préférez notifyAll() : notify() peut mener à de la starvation si le mauvais thread est réveillé et qu'il ne progresse pas.

Q10 Comment fonctionne ConcurrentHashMap comparé à HashMap et Hashtable ? Intermédiaire ▼

HashMap n'est pas thread-safe. Hashtable est thread-safe mais synchronise toutes les opérations sur l'objet entier — très lent. ConcurrentHashMap divise la map en segments (Java 7) puis utilise des CAS et locks par bucket (Java 8+). Seul le bucket concerné est verrouillé, permettant des accès concurrents très performants. Les opérations comme putIfAbsent, computeIfAbsent, merge sont atomiques.

🔴 Niveau Avancé / Senior

Q11 Qu'est-ce qu'un deadlock et comment le prévenir ? Avancé ▼

Un deadlock survient quand deux threads (ou plus) s'attendent mutuellement pour libérer des ressources. Les 4 conditions nécessaires (Coffman) : exclusion mutuelle, possession et attente, pas de préemption, attente circulaire.

Préventions :

  • Toujours acquérir les locks dans le même ordre
  • Utiliser tryLock(timeout) plutôt que lock()
  • Réduire la granularité et la durée des sections critiques
  • Utiliser des structures lock-free (ConcurrentHashMap, AtomicXxx)
  • Détecter avec ThreadMXBean.findDeadlockedThreads()
Q12 Expliquez le problème ABA et comment le résoudre. Avancé ▼

Le problème ABA est un piège des algorithmes CAS. Un thread lit une valeur A, un autre thread la change en B puis en A. Le premier thread fait son CAS (compare A, swap) et réussit — alors qu'entre-temps la valeur a changé deux fois, ce qui peut corrompre l'état d'une structure de données.

Solution : utiliser AtomicStampedReference<T> ou AtomicMarkableReference<T> qui associent un stamp (numéro de version) à la référence. Le CAS échoue si le stamp a changé même si la valeur est redevenue A.

AtomicStampedReference<Integer> ref =
    new AtomicStampedReference<>(1, 0); // valeur=1, stamp=0
int[] stampHolder = new int[1];
Integer current = ref.get(stampHolder);
ref.compareAndSet(current, 2, stampHolder[0], stampHolder[0]+1);
Q13 Quelle est la différence entre ReentrantLock et synchronized ? Avancé ▼

ReentrantLock offre tout ce que fait synchronized, plus :

  • tryLock() : tentative non-bloquante
  • tryLock(timeout) : avec délai d'expiration
  • lockInterruptibly() : interruptible pendant l'attente
  • Fair mode : new ReentrantLock(true) → FIFO
  • Conditions multiples : lock.newCondition() — vous pouvez signaler un sous-groupe de threads
  • Monitoring : getQueueLength(), isLocked(), getHoldCount()

Inconvénient : il faut manuellement unlock() dans un bloc finally, sinon le lock ne sera jamais libéré. synchronized se déverrouille automatiquement à la fin du bloc.

Q14 Quelle taille de thread pool choisir en production ? Avancé ▼

La formule de Brian Goetz :

Pour les tâches CPU-bound : N_threads = N_CPUs + 1

Pour les tâches I/O-bound : N_threads = N_CPUs × (1 + temps_attente / temps_CPU)

En pratique pour les services web I/O-bound, on commence souvent avec N_CPUs × 2 à N_CPUs × 10 selon les mesures de profiling. L'essentiel est de mesurer avec des outils (JMeter, JFR) et d'éviter les pools non bornés (newCachedThreadPool) en production car ils peuvent créer des milliers de threads et provoquer des OOM ou une thrashing de contextes.

Q15 Expliquez le Java Memory Model (JMM) et la relation happens-before. Avancé ▼

Le JMM définit quand une écriture d'un thread est garantie d'être visible par un autre thread. Par défaut, rien n'est garanti — les compilateurs et CPUs réordonnent les instructions pour optimiser.

La relation happens-before garantit la visibilité. Elle est établie par :

  • Un unlock happens-before le prochain lock sur le même monitor
  • L'écriture d'un champ volatile happens-before sa lecture
  • Thread.start() happens-before toute action dans ce thread
  • Toute action d'un thread happens-before Thread.join() retourne
  • La fin de l'initialisation d'un objet happens-before sa première utilisation

Si deux actions ne sont pas reliées par happens-before, il y a une data race — comportement indéfini.

Q16 Comment implémenter un Singleton thread-safe ? Avancé ▼

Plusieurs approches :

// 1. Enum Singleton — la meilleure approche
public enum MonSingleton {
    INSTANCE;
    public void doSomething() { }
}

// 2. Initialization-on-demand holder (le plus idiomatique)
public class Singleton {
    private Singleton() {}
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// 3. Double-checked locking (Java 5+, avec volatile)
public class Singleton {
    private volatile static Singleton instance;
    public static Singleton getInstance() {
        if (instance == null) {                  // 1er check sans lock
            synchronized (Singleton.class) {
                if (instance == null)             // 2ème check avec lock
                    instance = new Singleton();
            }
        }
        return instance;
    }
}
Q17 Quelle est la différence entre thenApply et thenCompose dans CompletableFuture ? Avancé ▼

thenApply(fn) applique une fonction T → U sur le résultat — équivalent de map en Stream. thenCompose(fn) attend une fonction T → CompletableFuture<U> et retourne un CompletableFuture<U> (pas un CompletableFuture<CompletableFuture<U>>) — équivalent de flatMap. Utilisez thenCompose quand votre transformation elle-même retourne un future asynchrone, pour éviter l'imbrication.

Q18 Qu'est-ce que ThreadLocal et quand l'utiliser ? Avancé ▼

ThreadLocal<T> fournit une variable dont chaque thread a sa propre copie indépendante. Idéal pour stocker des données par-thread sans synchronisation : connexion DB, session utilisateur, SimpleDateFormat (qui n'est pas thread-safe).

private static final ThreadLocal<SimpleDateFormat> formatter =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

// Chaque thread a son propre SimpleDateFormat
String date = formatter.get().format(new Date());

Attention : avec les thread pools, un thread peut être réutilisé. Toujours appeler threadLocal.remove() après utilisation pour éviter les memory leaks et les données stale entre requêtes.
