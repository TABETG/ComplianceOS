Phase 1 · Java 24 · JEP 444

Virtual Threads — Scalabilité sans callback hell

Project Loom résout le problème fondamental du Java concurrent : les threads OS sont lourds et limités. Un Virtual Thread est géré par la JVM, ultra-léger, et rend le code séquentiel aussi performant que l'async.

CritèreThread OS (Platform)Virtual Thread (Loom)
Coût mémoire~2 Mo par thread~few Ko (dynamique)
Limite pratique~5 000 simultanésMillions simultanés
I/O bloquantBloque tout le thread OSLibère le carrier thread
Code styleCallback hell / reactiveSéquentiel lisible
Migration—0 changement de code métier
carrier thread — Thread OS sous-jacent qui exécute physiquement les virtual threads. La JVM gère un pool de carrier threads (= nb de CPUs). Chaque carrier peut "porter" un virtual thread différent selon les I/O. Analogie : carrier = cuisinier, virtual thread = commande. Le cuisinier peut gérer 100 commandes même si il ne peut préparer qu'une à la fois.
continuation — La JVM "photographie" l'état complet d'un virtual thread (stack, variables locales) quand il se bloque en I/O. Cette photo est stockée en heap. Quand l'I/O répond, la JVM "restaure" la photo sur un carrier thread disponible. C'est le mécanisme qui permet à des millions de VT de coexister avec seulement N carrier threads OS.

🎯 Questions d'entretien — Virtual Threads
QQuelle est la différence entre un Virtual Thread et un thread OS ? Pourquoi utiliser l'un plutôt que l'autre ?
Un thread OS est alloué par le système d'exploitation (~2Mo de stack, limite à quelques milliers). Un Virtual Thread est géré par la JVM, quasi-gratuit à créer, et peut exister en millions simultanément. La JVM monte le VT sur un carrier thread OS uniquement quand il est actif. Pour les workloads I/O-heavy (APIs REST, BDD, HTTP), les VT s'imposent. Pour les calculs CPU-intensifs (ML, chiffrement), les threads OS gardent leur avantage car un VT bloqué en CPU garde son carrier thread.
QQu'est-ce que le "pinning" d'un Virtual Thread et quand se produit-il ?
Le pinning survient quand un VT est forcé de rester attaché à son carrier thread OS même en attente I/O. Cela se produit avec : synchronized (remplacer par ReentrantLock), et les méthodes native/JNI. Java 24 améliore le diagnostic via -Djdk.tracePinnedThreads=full. En pratique pour ComplianceOS : remplacer tous les blocs synchronized par des ReentrantLock, et vérifier les drivers JDBC (PostgreSQL driver 42.7+ supporte le non-pinning).
QPourquoi ScopedValue est-il préférable à ThreadLocal avec les Virtual Threads ?
ThreadLocal est mutable et hérité par les threads enfants (risque de fuite de données entre tenants). ScopedValue est immutable, disponible uniquement dans le run() scope, et beaucoup plus performant car la JVM peut l'optimiser (pas de HashMap interne par thread). Dans un contexte multi-tenant comme ComplianceOS, utiliser un ScopedValue<TenantContext> garantit qu'aucun tenant ne peut "lire" le contexte d'un autre même en cas de partage de carrier threads.

Java 24 simplifie radicalement les classes de données immuables et les hiérarchies de types. Ces features réduisent le boilerplate de 80% et rendent le code plus sûr à la compilation.

📋 Pourquoi Records dans ComplianceOS ?
  • Les Domain Events (AuditStartedEvent, RiskScoredEvent) sont parfaits : immuables, transportés dans Kafka, equals() auto
  • Les DTOs API : plus besoin de Lombok @Data, les records sont standards Java
  • Les Projections JPA : interface ou record — plus léger qu'une @Entity complète
  • Les Value Objects DDD : CompanyId, TenantId, RegulationCode
⚠️ Piège fréquent en entretien : Un record NE PEUT PAS étendre une classe (il étend implicitement java.lang.Record). Il peut implémenter des interfaces. Un record est toujours final. Si vous avez besoin d'héritage → utilisez une sealed class + sous-records.
Deconstruction pattern — case Draft(var createdAt) extrait le composant du record directement dans la variable createdAt. Disponible depuis Java 21 (JEP 440). Évite le pattern if (x instanceof Draft d) { d.createdAt() ... }
🎯 Questions d'entretien — Records & Sealed
QQuelles sont les limitations d'un Record Java ? Quand NE PAS l'utiliser ?
Limitations : 1) Immuable — tous les champs sont final, pas de setter. 2) Pas d'héritage — un record ne peut pas étendre une classe (seulement implémenter des interfaces). 3) Pas de champs d'instance supplémentaires — uniquement les composants déclarés. Ne pas utiliser pour : des entités JPA/Hibernate (qui ont besoin d'un constructeur no-arg + setters), des objets mutables, ou des classes nécessitant de l'héritage. Pour ComplianceOS : les @Entity restent des classes normales, mais les DTOs/Events/Value Objects deviennent des records.
QQu'est-ce qu'une sealed class ? Quel avantage par rapport à une interface ordinaire ?
Une sealed class/interface restreint quels types peuvent l'implémenter (via permits). Avantages : 1) Le compilateur connaît TOUS les sous-types → les switch expressions peuvent être exhaustifs sans default (sécurité à la compilation). 2) Modélisation précise des algèbres de données (comme les types algébriques en Scala/Haskell). 3) Lisibilité : toute la hiérarchie est visible dans la déclaration. Dans ComplianceOS, sealed interface AuditStatus permits Draft, InProgress, Completed garantit qu'on ne peut pas "oublier" un cas dans les traitements.
QQuelle est la différence entre Lombok @Data et un Record Java ?
@Data Lombok génère du bytecode à la compilation via APT (Annotation Processing Tool) — c'est du code "invisible". Un Record est natif Java, compris par l'IDE et les outils d'analyse statique sans plugin. Les Records sont immuables par nature (Lombok @Data génère des setters). Pour des projets Java 16+, les Records sont la solution standard. Lombok reste utile pour les @Builder complexes, les @Slf4j, et les entités JPA. En entretien : mentionner que les Records éliminent le problème de "fragile base class" de Lombok.

Proxy Spring (CGLib) — Spring génère une sous-classe à la compilation. Quand vous appelez auditService.listAudits() depuis un autre bean, vous appelez en réalité le proxy, qui exécute les aspects (@Transactional, @PreAuthorize, etc.) PUIS délègue à votre code. C'est pourquoi la self-invocation (this.listAudits() depuis AuditService) bypasse les proxies.
@Transactional propagation — Contrôle ce qui se passe quand une méthode transactionnelle appelle une autre méthode transactionnelle :
REQUIRED (défaut) — rejoindre la transaction existante ou en créer une
REQUIRES_NEW — toujours créer une nouvelle transaction (suspend l'existante)
NESTED — savepoint dans la transaction existante Dans ComplianceOS : les audit events Kafka utilisent REQUIRES_NEW pour que l'event soit persisté même si la transaction principale rollback.
⚠️ Erreur classique : @Transactional sur une méthode private ou appelée par this. ne fonctionne pas. Spring ne peut pas intercepter via proxy. Solution : déplacer dans un bean séparé, ou utiliser ApplicationContext.getBean() (anti-pattern).
🎯 Questions d'entretien — Spring Core
QExpliquez le mécanisme de self-invocation et pourquoi @Transactional ne fonctionne pas dans ce cas.
Spring implémente AOP via des proxies dynamiques. Quand un bean externe appelle service.method(), l'appel passe par le proxy qui applique les aspects. Mais quand la méthode A appelle this.B() à l'intérieur du même bean, elle appelle directement l'objet réel, bypassant le proxy. Résultat : @Transactional, @Cacheable, @PreAuthorize sont ignorés. Solutions : 1) Extraire la méthode dans un autre bean. 2) Injecter le bean sur lui-même via @Autowired @Lazy (code smell). 3) Utiliser AspectJ weaving (modification du bytecode, pas de proxy).
QQuand utiliser @Transactional(readOnly = true) ? Quels sont les effets réels ?
Pour les opérations de lecture uniquement. Effets : 1) Hibernate désactive le dirty checking (pas besoin de comparer entity avant/après → moins de mémoire). 2) Certains drivers JDBC et bases de données optimisent les requêtes read-only (replicas). 3) Empêche par inadvertance les modifications (Hibernate ne flush pas). Dans ComplianceOS : toutes les méthodes listAudits(), getScore() ont readOnly=true. En entretien : préciser que readOnly=true est un HINT, pas une garantie absolue d'impossibilité d'écriture.
QQuelle est la différence entre @Bean et @Component ? Quand utiliser l'un ou l'autre ?
@Component (et ses dérivés @Service, @Repository, @Controller) est une annotation de classe : Spring détecte et instancie automatiquement via le component scan. @Bean est une annotation de méthode dans une classe @Configuration : vous contrôlez manuellement la création de l'instance (utile pour des classes tierces que vous ne pouvez pas annoter, ou pour des configurations conditionnelles). Exemple : @Bean public ObjectMapper objectMapper() { ... } — vous configurez exactement comment Jackson doit sérialiser. Dans ComplianceOS : les clients gRPC, le Kafka producer, le client Bedrock sont des @Bean car leur configuration est complexe.

🎯 Questions d'entretien — PostgreSQL Multi-tenant & RLS
QQuels sont les 3 patterns d'architecture multi-tenant pour une base de données ? Quand choisir RLS ?
1) Database per tenant : isolation maximale, coût élevé (N bases de données), complexe à gérer. Pour des clients Enterprise avec exigences de localisation géographique. 2) Schema per tenant : un schéma PostgreSQL par client (tenant_abc.audits), bonne isolation, rollout de migrations complexe (N schémas). 3) Shared table + RLS (choix ComplianceOS) : tous dans le même schéma, isolation via politiques PostgreSQL. Économique, opérationnel simple, mais shared resources. Choisir RLS pour des SaaS B2B avec beaucoup de petits/moyens clients, où l'isolation stricte par schéma n'est pas une obligation contractuelle.
QComment fonctionne un index IVFFlat de pgvector ? Quelle est la différence avec HNSW ?
IVFFlat (Inverted File Flat) : partitionne les vecteurs en lists clusters via k-means. Une recherche ne compare que les clusters les plus proches (paramètre probes). Rapide à construire, consomme peu de mémoire. HNSW (Hierarchical Navigable Small World) : graph multi-niveaux, recherche plus précise mais consomme 2–3x plus de mémoire. Pour ComplianceOS (1200 articles) : IVFFlat avec lists=100 suffit. Pour un corpus de 10M documents : HNSW ou Qdrant/Weaviate. Le recall (précision de la recherche approchée) se règle avec le paramètre probes (IVFFlat) ou ef (HNSW).
QPourquoi ne jamais utiliser un utilisateur PostgreSQL SUPERUSER ou BYPASSRLS en production ?
Un utilisateur SUPERUSER ou avec BYPASSRLS ignore toutes les Row-Level Security policies. Si un bug dans le code applicatif oublie un filtre WHERE tenant_id = ?, ou si un développeur exécute une requête ad-hoc depuis un outil de BDD connecté avec ce rôle, les données de TOUS les tenants sont exposées. Principe de least privilege : l'utilisateur applicatif (app_user) n'a que SELECT/INSERT/UPDATE sur les tables nécessaires, sans BYPASSRLS. Le rôle superuser est réservé aux migrations Flyway (dans un job séparé) et aux opérations DBA exceptionnelles.

Keycloak — OAuth2, OIDC, Passkeys FIDO2

Keycloak est le serveur d'identité. Votre application ne gère plus jamais de mots de passe — elle délègue entièrement à Keycloak. Comprendre le flow OAuth2/OIDC est indispensable pour tout rôle senior.

Authorization Code + PKCE — Flow OAuth2 pour les apps web. Le code est un code temporaire (30s) échangé contre un token. PKCE (Proof Key for Code Exchange) ajoute un code_verifier secret pour prévenir l'interception du code par une app malveillante. Obligatoire pour les SPAs et apps mobiles (pas de client_secret sécurisable).
OIDC (OpenID Connect) — Couche d'identité au-dessus de OAuth2. Ajoute l'id_token (JWT avec infos sur l'utilisateur : sub, email, name). OAuth2 seul gère l'autorisation (accès à des ressources). OIDC gère l'authentification (qui est-ce). ComplianceOS utilise les deux : OAuth2 pour les API calls, OIDC pour afficher le nom de l'utilisateur connecté.
Passkey FIDO2 / WebAuthn — L'utilisateur s'authentifie avec sa biométrie (Touch ID, Windows Hello) ou une clé physique (YubiKey). La clé privée ne quitte jamais l'appareil. Keycloak reçoit une signature cryptographique vérifiable. Zéro mot de passe, zéro phishing possible.

🎯 Questions d'entretien — Auth & OAuth2
QQuelle est la différence entre OAuth2 et OpenID Connect ? Quand avez-vous besoin des deux ?
OAuth2 est un protocole d'autorisation : "l'utilisateur autorise cette app à accéder à ses ressources". Il gère les tokens d'accès mais ne dit pas QUI est l'utilisateur. OIDC est une extension d'authentification au-dessus d'OAuth2 : il ajoute l'id_token (JWT signé contenant l'identité : sub, email, name, etc.) et l'endpoint /userinfo. Vous avez besoin des deux quand : 1) votre API doit autoriser des appels (OAuth2 access_token) ET 2) votre frontend doit afficher le profil de l'utilisateur connecté (OIDC id_token). ComplianceOS utilise les deux : l'access_token pour les appels API, l'id_token pour afficher "Bonjour Pierre Dupont".
QComment Spring Security valide-t-il un JWT ? Que se passe-t-il si Keycloak est temporairement indisponible ?
Spring télécharge les clés publiques de Keycloak depuis /jwks-uri au démarrage et les met en cache localement. La validation JWT est 100% locale : Spring vérifie la signature cryptographique (RS256 = RSA SHA-256), l'expiration (exp), l'émetteur (iss), et l'audience (aud). Si Keycloak est down, l'API continue de fonctionner pour les tokens valides (non expirés). En revanche : nouveaux logins impossibles (Keycloak down = impossible d'obtenir un token). Les JWKs sont rafraîchis périodiquement (cache-ttl configurable). Pour la haute disponibilité : Keycloak en cluster avec Redis pour les sessions.
QComment implémenter la révocation de token en temps réel avec JWT (sans opaque tokens) ?
Les JWT sont stateless par design : une fois émis, valides jusqu'à expiration. Pour révoquer immédiatement (ex: déconnexion admin forcée, compromission de compte), ComplianceOS utilise une blacklist Redis : à la révocation, le jti (JWT ID, claim unique) est ajouté dans Redis avec un TTL = durée restante du token. Chaque requête API vérifie d'abord Redis (<10ms grâce au cache in-memory) avant de valider la signature. C'est ce que CO-03 implémente. Alternative : tokens opaques avec introspection (chaque requête → call Keycloak = latence + SPOF). Le trade-off : blacklist Redis = performances, mais état distribué à gérer.

🎯 Questions d'entretien — gRPC & Résilience
QQuand utiliser gRPC plutôt que REST ? Quels sont les cas où REST reste préférable ?
gRPC est préférable pour : la communication interne entre microservices (performance, typage fort), les flux de données bidirectionnels (streaming), les environnements polyglots où le contrat .proto est le standard (Java → Python dans ComplianceOS). QExpliquez les états d'un Circuit Breaker. Comment configurer les seuils dans Resilience4j ?
3 états : CLOSED (normal, toutes requêtes passent, Resilience4j compte les échecs sur une fenêtre glissante), OPEN (déclenché quand le taux d'échecs dépasse le seuil configuré, ex. 50% sur 10 appels → fail fast immédiatement sans appeler le service), HALF-OPEN (après le cooldown configuré, laisse passer N appels de test : si succès → retour CLOSED, si échecs → retour OPEN). Configuration dans application.yml : failure-rate-threshold: 50, wait-duration-in-open-state: 30s, permitted-calls-in-half-open-state: 3. Le @Retry et @CircuitBreaker s'appliquent dans l'ordre inverse de déclaration dans Spring : @Retry est à l'intérieur du @CircuitBreaker.

📋 Problème N+1 GraphQL expliqué

Sans DataLoader : audits { company { name } } pour 20 audits → 1 SQL pour les audits + 20 SQL pour chaque company = 21 requêtes. Avec DataLoader : DGS collecte les 20 company_ids pendant la résolution → 1 SQL batch WHERE id IN (...) = 2 requêtes. Les DataLoaders sont par-requête (pas partagés entre utilisateurs).

Cursor-based pagination vs offset-based — LIMIT 10 OFFSET 100 (offset) scan toujours 110 lignes et est incohérent si des lignes sont ajoutées entre les pages. Cursor-based : WHERE id > last_id LIMIT 10 utilise l'index directement (O(log n)). Le cursor est l'identifiant de la dernière ligne vue, encodé en base64 (opaque pour le client).
SpEL (Spring Expression Language) — Langage d'expression utilisé dans @PreAuthorize. Donne accès à : authentication (utilisateur connecté), #paramName (paramètres de la méthode), @beanName (beans Spring), returnObject (résultat, pour @PostAuthorize). Puissant mais attention aux performances : évalué à chaque appel.
⚠️ Sécurité GraphQL : Désactiver l'introspection en production (spring.graphql.schema.introspection.enabled=false) pour ne pas exposer le schéma complet à des attaquants. Aussi : limiter la profondeur des requêtes pour éviter les attaques DoS par requêtes imbriquées exponentielles.
🎯 Questions d'entretien — GraphQL & Sécurité
QQu'est-ce que le problème N+1 en GraphQL et comment le résoudre ?
Le problème N+1 survient quand une requête GraphQL demande une collection de N objets, et que pour chaque objet, un resolver fait une requête SQL distincte pour un champ imbriqué. Exemple : 10 audits → 10 requêtes pour les companies = 11 requêtes au total. Solution : les DataLoaders (pattern BatchLoader). DGS collecte tous les IDs nécessaires pour un type de ressource, puis exécute UNE requête batch. Implémenté avec @DgsDataLoader dans DGS ou DataLoaderRegistry manuellement. Important : les DataLoaders sont par-requête HTTP pour éviter de mélanger les données entre utilisateurs.
QQuelle différence entre RBAC et ABAC ? Donnez un exemple de cas où ABAC est nécessaire.
RBAC (Role-Based Access Control) : accès basé sur le rôle de l'utilisateur. Simple à implémenter, mais manque de granularité. Ex: ADMIN peut tout faire, AUDITOR peut lire les audits. ABAC (Attribute-Based Access Control) : accès basé sur les attributs de l'utilisateur, de la ressource, et du contexte. Plus expressif. Ex dans ComplianceOS : un EXTERNAL_AUDITOR ne peut lire que les audits partagés explicitement avec lui (pas tous les audits du tenant). La règle : audit.shared_with.contains(user.id) — c'est un attribut de la ressource, pas juste un rôle. Spring Security l'implémente via @PreAuthorize("@secBean.canAccess(auth, #id)").

🎯 Questions d'entretien — CI/CD & GitOps
QQu'est-ce que GitOps ? Quelle est la différence avec un pipeline CI/CD classique ?
Un pipeline CI/CD classique (push-based) : le pipeline CI exécute kubectl apply directement sur le cluster. Problèmes : les credentials cluster sont dans la CI, les changements manuels directs ne sont pas trackés, rollback complexe. Event loop asyncio — Python (contrairement à Java) est single-thread par défaut. 🎯 Questions d'entretien — FastAPI & Python Async
QQuelle est la différence entre async def et def dans FastAPI ? Quand utiliser l'un ou l'autre ?
async def : la fonction est une coroutine, exécutée dans l'event loop asyncio. Les await libèrent l'event loop pour d'autres requêtes. Utiliser quand : appels I/O avec des libs async (httpx, asyncpg, aiofiles). def (sync) : FastAPI exécute la fonction dans un threadpool externe pour ne pas bloquer l'event loop. Utiliser quand : code CPU-intensif, ou bibliothèques sans support async (XGBoost, pdfplumber). Erreur fréquente : mettre requests.get() (bloquant) dans un async def → ça bloque tout l'event loop. Solution : utiliser httpx.AsyncClient ou asyncio.to_thread().

Gradient Boosting vs Random Forest — Random Forest : N arbres en parallèle, vote final. Robuste au surapprentissage mais pas optimal en précision. Détection via le dashboard Streamlit : comparer la distribution des features en production vs la baseline d'entraînement (test KS ou PSI). Si drift > 20% → alerte et ré-entraînement.
🎯 Questions d'entretien — ML & XGBoost
QComment fonctionne le Gradient Boosting ? Pourquoi XGBoost est-il souvent meilleur qu'une régression logistique ?
Le Gradient Boosting construit des arbres de décision en séquence. L'arbre 1 prédit → calcule les résidus (erreurs). L'arbre 2 apprend à prédire ces résidus → nouvelle prédiction améliorée. L'arbre 3 apprend les nouveaux résidus. etc. La prédiction finale est la somme pondérée de tous les arbres. XGBoost ajoute : régularisation L1/L2 (évite le surapprentissage), gestion native des valeurs manquantes, parallélisation. Meilleur qu'une régression logistique pour : des relations non-linéaires entre features, des interactions complexes entre variables (NIS2_coverage ET secteur financier → risque amplifié). La régression logistique reste utile pour l'interprétabilité directe des coefficients.
QQu'est-ce que SHAP et pourquoi est-ce important dans un contexte réglementaire ?
SHAP (SHapley Additive exPlanations) est basé sur la théorie des jeux coopératifs. Il décompose chaque prédiction en contributions individuelles de chaque feature. Propriétés importantes : efficience (somme des SHAP values = prédiction − baseline), symétrie, et dummy (une feature non-informative a une contribution de 0). Dans un contexte réglementaire (RGPD Article 22, futur AI Act) : les décisions automatisées impactant des entreprises doivent être explicables. "Votre score est HIGH car vos incidents de sécurité (+18.2 pts) et votre faible couverture NIS2 (+12.1 pts) dominent" est une explication légalement défendable. Les modèles "boîte noire" purs ne sont pas acceptables dans ce contexte.
QComment gérez-vous le versioning des modèles ML en production ? Comment faire un rollback ?
Versioning via MLflow (ou DVC) : chaque run d'entraînement enregistre les hyperparamètres, métriques (RMSE, R²), et le modèle sérialisé. Le modèle est taggé (staging, production, archived). Dans ComplianceOS : le service FastAPI charge le modèle au démarrage via son URI MLflow ("models:/risk_model/Production"). Pour un rollback : 1) Dans MLflow : déplacer le tag "Production" vers une version précédente. 2) Redémarrer le service (ou endpoint de rechargement à chaud si implémenté). Le rechargement sans redémarrage utilise un ReentrantLock pour thread-safety pendant le swap du modèle en mémoire.

Apache Arrow — Format de données colonnaire in-memory standard (développé par Apache). Polars est Arrow-native : zéro copie mémoire lors de l'échange de données entre Polars, PyArrow, DuckDB, et certains connecteurs SQL. Avec acks_late=True, l'ACK n'est envoyé au broker que si la tâche réussit. La tâche est alors rejouée automatiquement par un autre worker.
🎯 Questions d'entretien — ETL & Data Processing
QQuelle est la différence entre Polars et Pandas ? Quand choisir l'un ou l'autre ?
Polars est implémenté en Rust, Arrow-native, et supporte l'évaluation lazy. Pandas est Python + NumPy, row-based, évaluation eager. Avantages Polars : 5–10x plus rapide pour les transformations, consomme moins de mémoire (colonnaire), API lazy permet l'optimisation du plan de requête, expression API plus expressive et sûre. Choisir Polars pour : volumes > 100k lignes, pipelines ETL complexes, environnements de prod. Choisir Pandas pour : notebooks exploratoires, intégration avec scikit-learn/XGBoost (qui attendent des DataFrames Pandas), équipes déjà formées Pandas, volumes <100k lignes. Note : Polars peut exporter vers Pandas en 1 ligne (df.to_pandas()) pour la compatibilité.
QComment garantir l'idempotence d'un import de fichier ? Pourquoi est-ce crucial ?
L'idempotence garantit que réimporter le même fichier plusieurs fois ne crée pas de doublons. Implémentation : 1) Hash SHA-256 du contenu du fichier → stocké dans une table imports(hash, imported_at). 2) Avant import : vérifier si le hash existe déjà. 3) Si oui → retourner le résultat précédent. Crucial pour : les retries automatiques (Celery rejoue les tâches en cas d'échec → sans idempotence = doublons), les uploads utilisateurs (double-click sur le bouton), les intégrations ETL qui peuvent envoyer le même fichier. Variante : si le fichier peut être mis à jour légitimement, utiliser une clé de déduplication métier (ex: company_id + period + regulation) plutôt que le hash du fichier.

🎯 Questions d'entretien — eIDAS & Signature Électronique
QQuelle est la différence entre une signature électronique simple, avancée et qualifiée (eIDAS) ?
Simple : tout processus d'identification numérique (cliquer "J'accepte"). Aucune valeur probatoire garantie. Avancée (AdES) : liée à un certificat électronique, intégrité du document vérifiable, identité du signataire établie. Valeur juridique reconnue mais variable selon les États membres. Qualifiée (QES) : basée sur un certificat qualifié émis par un prestataire de confiance qualifié (QTSP, listé sur la Trust List EU), clé privée sur QSCD (HSM certifié). Valeur légale équivalente à la signature manuscrite dans tous les États membres EU. ComplianceOS utilise QES pour les rapports d'audit : valeur légale maximale, opposabilité garantie.
QQu'est-ce que PAdES-LTA et pourquoi est-il nécessaire pour l'archivage long terme ?
PAdES (PDF Advanced Electronic Signatures) est le format de signature pour les PDFs. Le niveau LTA (Long Term Availability) ajoute : 1) Un horodatage qualifié RFC 3161 (preuve de l'existence du document à un instant donné). 2) Un archive timestamp qui "re-signe" le document périodiquement (tous les 5–10 ans) avec un nouveau horodatage. Nécessaire car les algorithmes cryptographiques vieillissent (SHA-1 cassé, RSA-1024 cassé). Sans re-timestamping, une signature vieille de 15 ans pourrait ne plus être vérifiable car les algorithmes utilisés seraient dépréciés. Pour ComplianceOS (rétention DORA : 7 ans) : un job annuel vérifie les signatures proches de l'expiration et ajoute un nouveau timestamp.

🚀 Server Components vs Client Components

Server Components (défaut) : rendu sur le serveur. Accès direct à la DB. 0 bundle JS envoyé au client. Idéal pour les données statiques à l'affichage initial.

Client Components ("use client") : hydratés dans le navigateur. Utilisés pour l'interactivité (hooks, events, SSE). Résultat Lighthouse : >90 performance.
