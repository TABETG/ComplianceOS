Virtual Threads — Scalabilité sans callback hell

Project Loom résout le problème fondamental du Java concurrent : les threads OS sont lourds et limités. Un Virtual Thread est géré par la JVM, ultra-léger, et rend le code séquentiel aussi performant que l'async.

⚙️ Le mécanisme de continuation

Quand un virtual thread fait un appel I/O bloquant (DB, HTTP, fichier…), la JVM le suspend en sauvant son état (continuation). Le thread carrier OS est libéré pour exécuter un autre virtual thread. Quand l'I/O répond, la JVM monte le virtual thread sur un thread carrier disponible et reprend. Complètement transparent pour le développeur.

✅ Pour ComplianceOS : chaque requête HTTP = 1 virtual thread. 1000 requêtes simultanées = 1000 virtual threads. Aucun pool, aucune limite artificielle.

Java 24 simplifie radicalement les classes de données immuables et les hiérarchies de types. Ces features réduisent le boilerplate de 80% et rendent le code plus sûr à la compilation.

📊 Records vs POJO classique

POJO classique (50+ lignes) : constructeur, getters, equals(), hashCode(), toString().
Record (1 ligne) : tout est généré.

La différence ? record AuditEvent(UUID id, String tenantId) = 1 ligne.
Ce n'est pas du sucre syntaxique — les records sont vraiment immuables (pas de setters). Idéal pour les événements Kafka et les DTOs API.

🔒 Sealed — Pourquoi ça change tout

Sans sealed : une switch sur une interface peut rater des cas. Avec sealed, le compilateur connaît tous les sous-types et force l'exhaustivité.

Cas d'usage réel : chaque statut d'audit (Draft, InProgress, Completed…) est un record dans une sealed interface. Impossible d'oublier un cas dans la logique métier.

⚡ SequencedCollection (JEP 431)

Java 21+ — List.getFirst(), List.getLast(), List.reversed() sont maintenant des méthodes standard. Plus de list.get(list.size() - 1) partout dans le code.

Phase 1 · PostgreSQL 17

PostgreSQL 17 — Multi-tenancy avec RLS + performances avancées

Le Row-Level Security est le dernier rempart de l'isolation multi-tenant. Même si un bug dans le code Java oublie un filtre WHERE, la DB refusera de montrer les données d'un autre tenant.

SQL — PostgreSQL 17V1__schema.sql + V2__rls.sql
-- Schéma complet multi-tenant CREATE TABLE audits ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), tenant_id TEXT NOT NULL, company_id UUID NOT NULL, status audit_status NOT NULL DEFAULT 'DRAFT', regulation TEXT NOT NULL, risk_score NUMERIC(5,2), created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), metadata JSONB DEFAULT '{}' ); -- Index composite pour les requêtes fréquentes CREATE INDEX idx_audits_tenant_status ON audits(tenant_id, status) WHERE status != 'ARCHIVED'; -- Index partiel ! -- Activation RLS + politique d'isolation ALTER TABLE audits ENABLE ROW LEVEL SECURITY; ALTER TABLE audits FORCE ROW LEVEL SECURITY; -- même pour SUPERUSER -- Politique : chaque ligne filtrée automatiquement CREATE POLICY p_tenant_isolation ON audits AS PERMISSIVE FOR ALL TO app_user USING (tenant_id = current_setting('app.tenant_id', true)) WITH CHECK (tenant_id = current_setting('app.tenant_id', true)); -- Côté Java : Hibernate interceptor injecte le tenant -- avant chaque requête (dans FilterInterceptor) SET LOCAL app.tenant_id = 'acme-corp'; SELECT * FROM audits; -- → que les audits acme-corp -- Partitioning par tenant pour les gros volumes CREATE TABLE audit_logs ( id BIGSERIAL, tenant_id TEXT NOT NULL, action TEXT NOT NULL, ts TIMESTAMPTZ NOT NULL DEFAULT NOW() ) PARTITION BY RANGE (ts); -- Partitions mensuelles créées automatiquement par pg_partman CREATE TABLE audit_logs_2025_01 PARTITION OF audit_logs FOR VALUES FROM ('2025-01-01') TO ('2025-02-01'); -- pg_cron : archivage automatique partitions > 7 ans SELECT cron.schedule( 'archive-old-logs', '0 2 * * 0', -- dimanche 2h $$SELECT archive_partitions_older_than('7 years')$$ );
🚀 Performances PostgreSQL 17 — nouveautés
  • Incremental Sort amélioré : jusqu'à 5× plus rapide sur les jointures triées
  • VACUUM amélioré : moins d'I/O sur les tables très écrites (audit logs)
  • Parallel queries : les SELECT sur de gros volumes exploitent tous les CPU
  • Logical replication slots : réplication vers des replicas en lecture pour dashboards
🔧 Index stratégie — EXPLAIN ANALYZE

Index B-tree composite (tenant_id, status) : couvre 90% des requêtes.
Index partiel WHERE status != 'ARCHIVED' : 60% plus petit car ignore les archives.
pgvector HNSW : pour la recherche sémantique en O(log n).

Règle : EXPLAIN (ANALYZE, BUFFERS) sur chaque requête avant de merger. Si tu vois "Seq Scan" sur une grande table → ajoute un index.

📋 Flyway — Migrations versionées

Flyway applique les fichiers SQL dans l'ordre au démarrage. V1__init.sql, V2__rls.sql, V3__indexes.sql…
La table flyway_schema_history trace ce qui a été appliqué. Idempotent : rejouer ne duplique rien. Dev, staging et prod ont toujours le même schéma.

🐛 Le problème N+1 expliqué

Sans DataLoader : charger 100 audits → 1 requête. Puis pour chaque audit, charger sa company → 100 requêtes. Total : 101 requêtes SQL.

Avec DataLoader : DGS collecte tous les companyId demandés, puis les charge en 1 seule requête avec WHERE id IN (...). Total : 2 requêtes. 50× plus rapide pour 100 audits.

🔒 Sécurité GraphQL en production
  • Introspection désactivée : impossible de cartographier le schéma
  • Query depth limit : max 10 niveaux d'imbrication (anti-DoS)
  • Complexity limit : limite le coût de la requête (chaque champ a un poids)
  • Persisted queries : n'accepte que les requêtes pre-approuvées en prod

🎭 RBAC vs ABAC

RBAC (Role-Based) : permission basée sur le rôle. Exemple : AUDITOR peut créer des audits.
Simple à implémenter, couvre 90% des cas.

ABAC (Attribute-Based) : permission basée sur des attributs. Exemple : un AUDITOR ne peut voir que les audits de son propre tenant. Nécessite @PostAuthorize ou du code métier.

⚡ JWT Stateless vs Session

JWT stateless : le serveur ne stocke rien. Chaque requête contient toute l'info dans le token. Scalable horizontalement (pas de session à synchroniser).

Problème : impossible de révoquer avant expiration.
Solution : Redis blacklist avec le JTI (JWT ID unique). Vérification <1ms. C'est le meilleur compromis stateless + révocation.

💣 Sans Circuit Breaker — Panne en cascade

Scénario : ML Python down. Chaque requête attend 30s (timeout). 1000 req/s × 30s = 30 000 requêtes en attente. Les threads se saturent. Spring Boot devient unresponsive. Le SaaS tombe entièrement pour un seul service.

Avec Circuit Breaker : après 5 échecs, le CB s'ouvre. Les appels suivants reçoivent le fallback en <1ms. L'app reste opérationnelle.

🛡️ Bulkhead — Isolation des ressources

Le Bulkhead limite le nombre de threads/requêtes simultanés pour un service externe. Si ML Python ralentit, maximum 25 appels simultanés y sont alloués. Les autres requêtes vers d'autres services ne sont pas impactées.

🔄 ASGI vs WSGI — La vraie différence

WSGI (Flask, Django) : synchrone. Une requête bloque un thread pendant toute sa durée. Si tu attends une réponse LLM (2s), le thread est bloqué 2s.

ASGI (FastAPI) : async. Pendant que tu attends le LLM, Python traite d'autres requêtes sur le même thread. await libère le thread pour les autres. Résultat : 5–10× plus de requêtes simultanées avec le même matériel.

📋 Pydantic v2 — Validation stricte

Pydantic v2 est réécrit en Rust. Validation 5–50× plus rapide que v1. Si le body JSON ne respecte pas le schéma → HTTP 422 automatique avec le champ exact qui échoue.

Configuration : model_config = ConfigDict(strict=True) pour rejeter toute coercition (ex: "123" → int refusé).

📊 OpenTelemetry auto-instrumenté

FastAPIInstrumentor().instrument_app(app) : chaque requête HTTP génère automatiquement une trace OpenTelemetry avec les attributes HTTP (method, path, status). Corrélation directe avec les traces Java via le trace_id propagé dans les headers.

🌳 Pourquoi XGBoost & pas un LLM pour le scoring ?
  • Prédiction <200ms : XGBoost est instantané. Un LLM prend 2–5s.
  • Deterministe et reproductible : même input = même output. Un LLM varie.
  • Explicable avec SHAP : tu sais exactement pourquoi ce score. Un LLM = boîte noire.
  • Conforme RGPD Art. 22 : toute décision automatisée doit être explicable.
  • Pas de coût par requête : XGBoost tourne sur ton CPU. Pas de facture AWS Bedrock.

  • Distribution des scores : mean ± 20% de la baseline = alerte
  • Feature importance shift : un facteur pas important devient critique

eIDAS 2.0 — Signature qualifiée & horodatage longue durée

PAdES-LTA (Long Term Availability) garantit que la signature reste valide dans 100 ans, même si les algorithmes RSA/ECDSA actuels sont compromis. L'horodatage qualifié RFC 3161 prouve que le document existait à un moment précis.

TimescaleDB — Audit trail immuable & requêtes temporelles ultra-rapides

Chaque action dans ComplianceOS — login, création d'audit, accès à un document — est enregistrée dans TimescaleDB. L'audit trail est append-only : impossible à modifier ou supprimer. Conforme NIS2 et DORA (7 ans de rétention).

-- Hypertable TimescaleDB — partitionnée par temps automatiquement CREATE TABLE audit_trail ( id BIGSERIAL NOT NULL, tenant_id TEXT NOT NULL, user_id UUID, action TEXT NOT NULL, -- CREATE, READ, etc. resource_type TEXT NOT NULL, resource_id TEXT, old_value JSONB, new_value JSONB, ip_address INET, user_agent TEXT, correlation_id TEXT, ts TIMESTAMPTZ NOT NULL DEFAULT NOW() ); -- Hypertable : partitions automatiques par semaine SELECT create_hypertable('audit_trail', 'ts', chunk_time_interval => INTERVAL '1 week'); -- Compression automatique des chunks > 7 jours ALTER TABLE audit_trail SET (timescaledb.compress, timescaledb.compress_segmentby = 'tenant_id, resource_type'); SELECT add_compression_policy('audit_trail', INTERVAL '7 days'); -- Politique de rétention 7 ans SELECT add_retention_policy('audit_trail', INTERVAL '7 years'); -- Rôle append-only : aucun UPDATE/DELETE possible CREATE ROLE audit_writer NOLOGIN; GRANT INSERT ON audit_trail TO audit_writer; -- INSERT uniquement, pas de UPDATE ni DELETE --- -- Requêtes analytics rapides (hypertable optimisé) -- Toutes les actions d'un user sur 1 an < 2s SELECT action, resource_type, ts, new_value FROM audit_trail WHERE tenant_id = 'acme-corp' AND user_id = 'user-uuid' AND ts >= NOW() - INTERVAL '1 year' ORDER BY ts DESC; -- Continuous aggregate — pré-calcule les stats par heure CREATE MATERIALIZED VIEW hourly_audit_stats WITH (timescaledb.continuous) AS SELECT time_bucket('1 hour', ts) AS bucket, tenant_id, action, count(*) AS event_count FROM audit_trail GROUP BY bucket, tenant_id, action; -- → dashboard temps réel sans scan de la table complète
