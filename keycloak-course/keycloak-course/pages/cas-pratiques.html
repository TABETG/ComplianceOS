Cas pratiques

On transforme maintenant les concepts en architectures concrètes.

Cas 1 — Portail RH + admin + API métier

Clients Keycloak:
- hr-portal (public ou confidential selon architecture)
- admin-portal (confidential)
- hr-api (resource server)

Rôles:
- employee
- manager
- hr-admin

Choix : SSO central pour éviter plusieurs logins, MFA pour hr-admin, client roles spécifiques sur l’API RH.

Cas 2 — SaaS multi-rôles

Tu dois distinguer les rôles globaux de plateforme et les rôles tenant-spécifiques. Le vrai enjeu n’est pas seulement le login, mais aussi l’isolation logique des organisations clientes.

Bonne pratique

Définis clairement où se situe la séparation de tenants : dans le realm, dans les groupes, dans les claims, dans la base métier, ou dans une combinaison contrôlée.

Cas 3 — Application avec MFA

Contexte banque/finance ou administration sensible. Le flow browser demande mot de passe puis WebAuthn ou OTP selon la catégorie d’utilisateur.

Cas 4 — Passwordless avec FIDO2

Contexte entreprise interne moderne. Les utilisateurs s’authentifient avec Windows Hello ou Passkeys. On réduit les tickets support liés aux mots de passe, mais on doit soigner le parcours d’enrôlement et de secours.

Cas 5 — API protégée user/admin/manager

GET /api/invoices          -> user, manager, admin
POST /api/invoices/approve -> manager, admin
DELETE /api/users/{id}     -> admin only

Le RBAC côté Keycloak donne la base. L’API doit ensuite contrôler les routes et parfois les règles métier contextuelles, par exemple “un manager ne peut approuver que les factures de son périmètre”.
