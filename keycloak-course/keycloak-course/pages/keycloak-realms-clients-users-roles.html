Realms, clients, users, roles

C’est le cœur du modèle Keycloak. Bien le comprendre évite une grande partie des erreurs de conception.

Realm

Un realm est une frontière logique : utilisateurs, groupes, rôles, clients, sessions, providers. Deux realms différents sont isolés.

Attention

Un realm n’est pas juste un “dossier”. C’est une vraie frontière de configuration et d’identité. Le choix du nombre de realms est un choix d’architecture.

Client

Un client représente l’application ou le service qui délègue le login à Keycloak. Son type influence sa sécurité :

  • Public client : ne peut pas garder un secret de manière fiable, typiquement SPA.
  • Confidential client : peut protéger un secret, typiquement backend.
  • Bearer-only : reçoit seulement des tokens, sans redirection de login classique.

User, group, role

Realm: acme
Client: finance-api
Groups:
- finance-users
- finance-managers

Realm roles:
- employee
- admin

Client roles (finance-api):
- invoice:read
- invoice:approve

Un utilisateur peut recevoir des rôles directement ou via ses groupes.

Scopes et protocol mappers

Les client scopes et protocol mappers servent à contrôler quels claims sont injectés dans les tokens. C’est ici qu’on projette des rôles, groupes ou attributs utilisateur.

Piège fréquent

Mettre trop d’informations dans le token. Un token n’est pas un mini-annuaire LDAP ni une base de données transportable.
