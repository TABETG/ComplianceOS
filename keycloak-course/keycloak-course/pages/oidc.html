OpenID Connect

OIDC ajoute une couche d’identité au-dessus d’OAuth2. C’est lui qui permet au client de savoir quel utilisateur s’est authentifié.

Pourquoi OIDC existe

OAuth2 répond au problème d’accès à une ressource. OIDC répond au problème d’identité. En clair : OAuth2 donne une clé d’accès ; OIDC dit aussi qui a ouvert la porte.

Définition

Un ID token est un token destiné au client pour attester l’authentification de l’utilisateur.

Claims et scopes

{
  "iss": "https://sso.example.com/realms/acme",
  "sub": "user-123",
  "aud": "web-portal",
  "email": "alice@example.com",
  "preferred_username": "alice",
  "given_name": "Alice",
  "family_name": "Martin"
}

Les scopes openid, profile, email contrôlent ce que le client demande en standard.

Endpoints importants

  • /.well-known/openid-configuration : discovery endpoint
  • /protocol/openid-connect/certs : JWKS
  • /protocol/openid-connect/userinfo : profil utilisateur
Bonne pratique

Utilise le discovery endpoint et le JWKS du provider, au lieu de coder en dur des URLs de clés sans gouvernance.

Validation côté API

# À valider au minimum
- signature
- iss (issuer)
- exp / nbf / iat
- aud ou azp selon le contexte
- scopes / rôles nécessaires
Attention

Décoder un JWT n’est pas le valider. Sans vérification cryptographique et contrôles de claims, tu n’as aucune garantie de confiance.
