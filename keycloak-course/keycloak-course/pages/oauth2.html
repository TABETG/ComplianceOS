OAuth2

OAuth2 est un cadre de délégation d’autorisation. Il ne dit pas d’abord qui est l’utilisateur ; il dit comment un client peut obtenir un accès limité à une ressource.

Les rôles OAuth2

RôleQuestionExemple
Resource OwnerÀ qui appartiennent les données ?L’utilisateur
ClientQui demande l’accès ?SPA, backend, mobile app
Authorization ServerQui délivre le feu vert ?Keycloak
Resource ServerQui protège la ressource ?API métier

Authorization Code Flow

# 1) Redirection vers /authorize
GET /protocol/openid-connect/auth?
  client_id=web-portal&
  response_type=code&
  scope=openid profile email&
  redirect_uri=https://app.example.com/callback&
  code_challenge=...&
  code_challenge_method=S256

# 2) Échange du code contre des tokens
POST /protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id=web-portal&
code=abc123&
redirect_uri=https://app.example.com/callback&
code_verifier=...
Bonne pratique

Pour les public clients comme les SPA et les apps mobiles, utilise Authorization Code + PKCE.

Flows à connaître

  • Authorization Code + PKCE : standard moderne pour navigateur et mobile.
  • Client Credentials : service-to-service sans utilisateur final.
  • Refresh Token : renouvellement contrôlé des tokens.
  • Device Authorization Grant : appareils à capacité d’input limitée.
Piège fréquent

Utiliser Resource Owner Password Credentials ou des flows hérités par habitude. Dans une architecture moderne, on évite de demander le mot de passe directement au client.

Quand utiliser quoi

SPA React               -> Authorization Code + PKCE
Application mobile      -> Authorization Code + PKCE
Backend batch technique -> Client Credentials
TV / borne / CLI limitée-> Device Authorization Grant
