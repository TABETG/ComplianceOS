01

Concepts fondamentaux

Junior

Avant de coder, il faut comprendre pourquoi le multithreading existe. Un programme Java tourne par défaut sur un seul fil d'exécution — le main thread. Si une tâche est longue (réseau, I/O, calcul), tout le programme se bloque.

🧵

Thread

Unité d'exécution légère au sein d'un processus. Partage la mémoire heap mais possède sa propre stack.

⚙️

Processus

Programme en cours d'exécution avec sa propre mémoire isolée. Un processus peut contenir plusieurs threads.

🔄

Concurrence

Plusieurs tâches semblent s'exécuter en même temps (interleaving sur un seul cœur).

⚡

Parallélisme

Plusieurs tâches s'exécutent vraiment simultanément sur plusieurs cœurs CPU.

Thread vs Processus

AspectThreadProcessus
MémoirePartagée (heap)Isolée
CréationRapide (~µs)Lente (~ms)
CommunicationDirecte (variables)IPC (socket, pipe…)
Crash impactTout le processusSeulement lui-même
💡

La JVM démarre toujours avec plusieurs threads en arrière-plan : main, GC, Finalizer, Signal Dispatcher…

02

Créer un Thread

Junior

Il existe 3 façons principales de créer et démarrer un thread en Java.

① Étendre Thread

// ┌─ Approche 1 : héritage de Thread ─────────────────────────────────────────
// │  Peu recommandée car Java n'a pas d'héritage multiple : si votre classe
// │  hérite de Thread, elle ne peut plus hériter d'aucune autre classe.
// └────────────────────────────────────────────────────────────────────────────
public class MonThread extends Thread {

    @Override
    public void run() {
        // run() contient la logique qui s'exécutera dans le nouveau thread
        // currentThread().getName() retourne le nom auto-généré "Thread-0", "Thread-1"…
        System.out.println("Thread : " + Thread.currentThread().getName());
    }
}

// ── Utilisation ──────────────────────────────────────────────────────────────
MonThread t = new MonThread();
t.start(); // ✅ CORRECT : crée un nouveau thread OS et appelle run() dessus
// t.run(); ❌ ERREUR CLASSIQUE : run() serait exécuté dans le thread courant
⚠️

Appeler t.run() au lieu de t.start() exécute le code sur le thread courant sans créer de nouveau thread — erreur classique en entretien !

② Implémenter Runnable

// ┌─ Approche 2 : implémenter Runnable ───────────────────────────────────────
// │  RECOMMANDÉE. Runnable est une @FunctionalInterface avec une seule méthode
// │  run(). On garde la liberté d'hériter d'une autre classe métier.
// └────────────────────────────────────────────────────────────────────────────
public class MaTache implements Runnable {
    @Override
    public void run() {
        System.out.println("Runnable en action !");
    }
}

// ── Instanciation : on confie le Runnable à un Thread ────────────────────────
Thread t = new Thread(new MaTache());
t.start();

// ── Avec lambda (Java 8+) — syntaxe utilisée en pratique ────────────────────
// │  Runnable étant @FunctionalInterface, on peut le remplacer par une lambda.
// │  () -> ... remplace new MaTache() { public void run() { ... } }
Thread t2 = new Thread(() -> System.out.println("Lambda thread !"));
t2.start();
✅

Préférez toujours Runnable à l'héritage Thread : Java n'a pas l'héritage multiple, et implémenter Runnable vous laisse libre d'hériter d'une autre classe.

③ Callable + Future (retour de valeur)

// ┌─ Approche 3 : Callable<T> ────────────────────────────────────────────────
// │  Contrairement à Runnable, Callable peut :
// │    • retourner une valeur typée (ici Integer)
// │    • lever des exceptions vérifiées
// │  Utilisez-le avec ExecutorService.submit() → retourne un Future<T>
// └────────────────────────────────────────────────────────────────────────────
import java.util.concurrent.*;

Callable<Integer> tache = () -> {
    // Cette méthode s'exécute dans un thread du pool
    // Thread.sleep() simule un calcul long (réseau, base de données…)
    Thread.sleep(1000);
    return 42; // la valeur sera récupérée via future.get()
};

// ── Soumission au pool ───────────────────────────────────────────────────────
ExecutorService executor = Executors.newSingleThreadExecutor();
// submit() est NON BLOQUANT : il rend la main immédiatement avec un Future
Future<Integer> future = executor.submit(tache);

System.out.println("En attente du résultat..."); // s'affiche pendant le calcul

// ── Récupération du résultat ─────────────────────────────────────────────────
// future.get() est BLOQUANT : il attend que le Callable ait terminé
Integer result = future.get();
System.out.println("Résultat : " + result); // 42

// ── Arrêt propre de l'executor ───────────────────────────────────────────────
executor.shutdown(); // ⚠️ TOUJOURS appeler shutdown() pour libérer les ressources

Méthodes importantes

Thread t = new Thread(() -> { /* logique métier */ });

// ── Contrôle du cycle de vie ─────────────────────────────────────────────────
t.start();              // NEW → RUNNABLE : crée le thread OS et démarre l'exécution
t.join();               // le thread appelant attend la fin de t (état TERMINATED)
t.join(2000);           // idem mais avec timeout de 2 secondes (TIMED_WAITING)
t.interrupt();          // envoie un signal d'interruption (ne force pas l'arrêt !)
t.isAlive();            // true entre start() et TERMINATED
t.getState();           // retourne l'enum Thread.State courant

// ── Configuration (AVANT start()) ────────────────────────────────────────────
t.setDaemon(true);     // ⚠️ doit être appelé AVANT start(), sinon IllegalThreadStateException
t.setPriority(5);     // 1=MIN_PRIORITY … 5=NORM_PRIORITY … 10=MAX_PRIORITY
t.setName("worker-1"); // facilite le débogage dans jstack / profilers

// ── Méthodes statiques (s'appliquent au thread COURANT) ──────────────────────
Thread.sleep(1000);     // RUNNABLE → TIMED_WAITING pendant 1s (lève InterruptedException)
Thread.yield();          // "hint" au scheduler : je veux bien céder mon tour CPU
Thread.currentThread(); // référence vers le Thread qui exécute cette ligne de code

Gestion propre de l'interruption

// ┌─ Pattern standard pour un thread interruptible ───────────────────────────
// │  L'interruption est COOPÉRATIVE : le thread doit VOULOIR s'arrêter.
// │  t.interrupt() positionne le flag interne "interrupted" à true.
// └────────────────────────────────────────────────────────────────────────────
Thread t = new Thread(() -> {
    // isInterrupted() lit le flag sans le remettre à false
    while (!Thread.currentThread().isInterrupted()) {
        try {
            System.out.println("Travaille...");
            // sleep() lève InterruptedException si le flag est levé pendant le sommeil
            Thread.sleep(500);
        } catch (InterruptedException e) {
            // ATTENTION : catch InterruptedException remet automatiquement le flag à false
            // → il faut le restaurer explicitement pour que la boucle while puisse
            // │  détecter l'interruption à la prochaine itération
                        Thread.currentThread().interrupt(); // ✅ restaurer le flag !
            break; // sortir de la boucle proprement
        }
    }
    // ici : libérer les ressources (connexions, fichiers…)
    System.out.println("Thread arrêté proprement");
});

t.start();
Thread.sleep(2000); // laisse le thread travailler 2s
t.interrupt();    // demande l'arrêt — le thread répondra dès que possible
🚫

Thread.stop() et Thread.suspend() sont dépréciés depuis Java 1.2 — ils peuvent laisser des objets dans un état incohérent. Utilisez toujours l'interruption ou un flag volatile.

04

Synchronisation

Intermédiaire

Quand plusieurs threads accèdent à la même variable en écriture, on a une race condition. Le mot-clé synchronized garantit qu'un seul thread exécute un bloc à la fois.

Le problème sans synchronisation

public class Compteur {
    private int valeur = 0;

    public void incrementer() {
        // ┌─ valeur++ n'est PAS atomique ! ────────────────────────────────────────
        // │  Le CPU décompose cette opération en 3 instructions :
        // │    1. LOAD  : lire valeur depuis la mémoire dans un registre
        // │    2. ADD   : incrémenter le registre de 1
        // │    3. STORE : réécrire le registre en mémoire
        // │  Si deux threads exécutent LOAD simultanément (ex. valeur = 5),
        // │  ils calculent tous les deux 6 et écrivent 6 — une incrémentation est perdue.
        // └────────────────────────────────────────────────────────────────────────
                valeur++; // ❌ race condition : 2 threads × 10 000 ≠ 20 000
    }
}

Méthode synchronisée

public class CompteurSûr {
    private int valeur = 0;

    // ┌─ synchronized sur une méthode d'instance ──────────────────────────────
    // │  Acquiert le "monitor" (verrou intrinsèque) de l'INSTANCE (this).
    // │  Un seul thread à la fois peut exécuter une méthode synchronized
    // │  de ce même objet. Les autres threads se mettent en état BLOCKED.
    // └────────────────────────────────────────────────────────────────────────
        public synchronized void incrementer() {
        valeur++; // ✅ atomique du point de vue des autres threads
    }

        public synchronized int getValeur() {
        // ✅ synchronized en lecture aussi : garantit la visibilité mémoire
        return valeur;
    }

    // Méthode statique → verrou sur la CLASS, pas sur l'instance
    // Utile pour protéger les champs statiques partagés entre toutes les instances
    public static synchronized void methodeStatique() { /* … */ }
}

Bloc synchronisé — granularité fine

public class BanqueService {
    // Objet dédié au verrouillage : meilleure pratique que de synchroniser sur "this"
    // → évite les interférences si du code externe synchronise aussi sur this
    private final Object verrou = new Object();
    private double solde = 1000.0;

    public void retirer(double montant) {
        // ── Section critique : le minimum possible est enfermé dans le bloc ──────
        // │  Réduire la taille du bloc = réduire la contention = meilleures perfs
        synchronized (verrou) {
            if (solde >= montant) {
                solde -= montant;
                System.out.println("Retrait OK : " + montant);
            }
        }
        // Code hors du bloc : s'exécute en parallèle (logs, notifications…)
        System.out.println("Opération terminée");
    }
}

Le mot-clé volatile

// ┌─ Le problème de la visibilité mémoire (Java Memory Model) ────────────────
// │  Chaque CPU a ses propres caches L1/L2. Une écriture en mémoire principale
// │  peut ne pas être immédiatement visible dans le cache d'un autre CPU.
// │  Sans volatile, un thread peut lire une valeur "stale" (obsolète).
// └────────────────────────────────────────────────────────────────────────────
public class FlagExample {
    // volatile garantit que toute lecture va chercher la valeur en mémoire principale
    // → jamais de cache CPU entre-deux → visibilité immédiate entre threads
        private volatile boolean arrete = false;

    public void travailler() {
        // Sans volatile, cette boucle pourrait ne jamais s'arrêter !
        // (le thread A lit arrete=false depuis son cache et ne voit jamais true)
        while (!arrete) { /* traitement continu */ }
        System.out.println("Arrêté !");
    }

    public void arreter() {
        arrete = true; // visible immédiatement dans la mémoire principale
    }
}
💡

volatile garantit la visibilité mais PAS l'atomicité. volatile int i; i++; reste une race condition ! Pour des opérations composées, utilisez synchronized ou les classes Atomic*.

wait() / notify() / notifyAll()

Intermédiaire

Ces méthodes permettent la communication inter-threads via le monitor d'un objet. Elles ne peuvent être appelées que depuis un bloc synchronized.

Exemple Producteur / Consommateur

public class FileAttente {
    private final Queue<String> file = new LinkedList<>();
    private final int capaciteMax;

    public FileAttente(int capaciteMax) { this.capaciteMax = capaciteMax; }

    // ┌─ PRODUCTEUR ────────────────────────────────────────────────────────────
    public synchronized void produire(String item) throws InterruptedException {
        // ┌─ WHILE, pas IF ─────────────────────────────────────────────────────
        // │  Après un notify(), le thread recompète pour le monitor.
        // │  Il peut être réveillé (spurious wakeup) sans que la condition ait
        // │  changé → while re-vérifie la condition à chaque réveil.
        // └─────────────────────────────────────────────────────────────────────
                while (file.size() == capaciteMax) {
            // wait() : libère le monitor + suspend ce thread (état WAITING)
            // Le thread sera réveillé par notifyAll() depuis le consommateur
            wait();
        }
        file.add(item);
        System.out.println("Produit : " + item);
        // notifyAll() réveille TOUS les threads en attente sur ce monitor
        // (les consommateurs qui attendaient du travail)
        notifyAll();
    }

    // ┌─ CONSOMMATEUR ─────────────────────────────────────────────────────────
    public synchronized String consommer() throws InterruptedException {
                while (file.isEmpty()) {
            wait(); // attend qu'un producteur ajoute un élément et appelle notifyAll()
        }
        String item = file.poll(); // retire la tête de la file
        // réveille les producteurs éventuellement bloqués sur "file pleine"
        notifyAll();
        return item;
    }
}
⚠️

Utilisez toujours while et jamais if autour de wait(). Les spurious wakeups (réveils parasites) peuvent sortir un thread de wait() sans qu'un notify ait été appelé.

MéthodeEffet
wait()Libère le lock et met le thread en WAITING
wait(ms)Libère le lock, attend max ms ms (TIMED_WAITING)
notify()Réveille UN thread en attente (aléatoire)
notifyAll()Réveille TOUS les threads en attente (plus sûr)

ExecutorService & Thread Pools

Intermédiaire

Créer un thread à chaque tâche est coûteux. Les thread pools réutilisent des threads pré-créés. C'est le pattern standard en production.

Types de pools

import java.util.concurrent.*;

// ── Pools courants (Executors est une factory) ────────────────────────────────

// N threads fixes. Si tous occupés, les tâches attendent dans une file illimitée.
// Adapté aux workloads prévisibles (CPU-bound, N ≈ nombre de cœurs).
ExecutorService fixe = Executors.newFixedThreadPool(4);

// Un seul thread → garantit que les tâches s'exécutent dans l'ordre de soumission.
ExecutorService single = Executors.newSingleThreadExecutor();

// Crée des threads à la demande, réutilise les threads idle (keepAlive = 60s).
ExecutorService cached = Executors.newCachedThreadPool(); // ⚠️ DANGEREUX en prod : peut créer des milliers de threads

// Pour les tâches périodiques (ex: nettoyage toutes les X secondes).
ScheduledExecutorService sched = Executors.newScheduledThreadPool(2);

// Pool de "vol de travail" : les threads inactifs volent des tâches aux autres.
// Taille = nombre de cœurs CPU par défaut. Idéal pour les tâches récursives (fork/join).
ExecutorService fj = ForkJoinPool.commonPool();

Utilisation complète

ExecutorService executor = Executors.newFixedThreadPool(3);

// ── execute() : soumet un Runnable (pas de résultat, pas d'exception) ─────────
executor.execute(() -> System.out.println("Tâche 1"));

// ── submit() : soumet un Callable et retourne un Future ──────────────────────
// Retour IMMÉDIAT : la tâche s'exécute en arrière-plan
Future<String> f = executor.submit(() -> {
    Thread.sleep(500);
    return "Résultat";
});

try {
    // get(timeout) : bloque au maximum 2s, puis lève TimeoutException
    // Sans timeout, get() bloquerait indéfiniment si le thread plante
        String res = f.get(2, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    f.cancel(true); // true = interrompre le thread en cours si possible
}

// ── Arrêt propre en 3 étapes ──────────────────────────────────────────────────
executor.shutdown();                         // 1. refuse les nouvelles soumissions
                                              //    les tâches déjà soumises continuent
executor.awaitTermination(30, TimeUnit.SECONDS); // 2. attend max 30s la fin
executor.shutdownNow();                      // 3. force si toujours pas fini (interrupt)

ThreadPoolExecutor personnalisé

// ┌─ En production, préférez ThreadPoolExecutor à Executors ───────────────────
// │  Vous contrôlez explicitement tous les paramètres critiques :
// │  • taille du pool • file d'attente bornée • politique de rejet
// └────────────────────────────────────────────────────────────────────────────
ThreadPoolExecutor custom = new ThreadPoolExecutor(
    2,                             // corePoolSize : threads maintenus vivants même idle
    10,                            // maximumPoolSize : plafond absolu (si file pleine)
    60, TimeUnit.SECONDS,          // keepAliveTime : durée de vie des threads > core
        new ArrayBlockingQueue<>(100), // ✅ file BORNÉE : évite OOM si surge de tâches
    r -> {                         // ThreadFactory : nomme les threads pour le debug
        Thread t = new Thread(r);
        t.setName("worker-" + t.getId());
        return t;
    },
    // CallerRunsPolicy : si la file est pleine, le thread APPELANT exécute la tâche
    // → mécanisme de back-pressure naturel (ralentit le producteur)
    new ThreadPoolExecutor.CallerRunsPolicy()
);
🔧

Politiques de rejet : AbortPolicy (exception, défaut), CallerRunsPolicy (le thread appelant exécute la tâche), DiscardPolicy (ignore silencieusement), DiscardOldestPolicy (vire la plus ancienne).

invokeAll & invokeAny

List<Callable<String>> taches = List.of(
    () -> { Thread.sleep(100); return "A"; },
    () -> { Thread.sleep(200); return "B"; },
    () -> { Thread.sleep(50);  return "C"; }
);

// invokeAll : attend QUE TOUTES les tâches soient terminées (succès ou erreur)
// Retourne dans l'ordre de la liste, pas dans l'ordre de fin
List<Future<String>> resultats = executor.invokeAll(taches); // attend ~200ms

// invokeAny : retourne DÈS QU'UNE tâche réussit, annule les autres
// Ici "C" (50ms) gagne → résultat = "C", A et B sont annulés
String premier = executor.invokeAny(taches); // attend ~50ms seulement

Locks avancés (java.util.concurrent.locks)

Avancé

Le package java.util.concurrent.locks offre des mécanismes plus flexibles que synchronized.

ReentrantLock

import java.util.concurrent.locks.*;

public class CompteurLock {
    // ReentrantLock = "réentrant" : un thread qui détient déjà le lock
    // peut le rereacquérir sans se bloquer lui-même (utile pour les méthodes récursives)
    private final ReentrantLock lock = new ReentrantLock();
    private int valeur = 0;

    public void incrementer() {
        lock.lock(); // acquisition bloquante (comme synchronized)
        try {
            valeur++;
        } finally {
            // ┌─ TOUJOURS dans un bloc finally ─────────────────────────────────
            // │  Si une exception est levée dans le try, unlock() sera quand même
            // │  appelé. Sans finally → deadlock garanti si exception.
            // └─────────────────────────────────────────────────────────────────
                        lock.unlock(); // ✅ toujours libérer dans finally !
        }
    }

    // ── tryLock() : tentative NON BLOQUANTE ──────────────────────────────────────
    // Retourne true si le lock a été acquis, false immédiatement sinon.
    // Permet d'implémenter une logique alternative si le lock est pris.
    public boolean essayerIncrémenter() {
        if (lock.tryLock()) {
            try { valeur++; return true; }
            finally { lock.unlock(); }
        }
        return false; // lock non disponible, on n'attend pas
    }

    // ── tryLock(timeout) : attend au maximum N ms ─────────────────────────────────
    // Contrairement à lock(), si l'attente dépasse 500ms, on abandonne.
    // Très utile pour prévenir les deadlocks (timeout = sortie de secours).
    public void avecTimeout() throws InterruptedException {
        if (lock.tryLock(500, TimeUnit.MILLISECONDS)) {
            try { valeur++; }
            finally { lock.unlock(); }
        }
    }
}

ReadWriteLock — Optimisation lecture/écriture

// ┌─ Principe du ReadWriteLock ─────────────────────────────────────────────────
// │  Lecture  : plusieurs threads simultanés autorisés (pas de modification)
// │  Écriture : accès EXCLUSIF (bloque toutes les lectures et écritures)
// │  Idéal quand les lectures sont beaucoup plus fréquentes que les écritures.
// └────────────────────────────────────────────────────────────────────────────
public class Cache<K, V> {
    private final Map<K, V> map = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock  = rwLock.readLock();  // verrou de lecture
    private final Lock writeLock = rwLock.writeLock(); // verrou d'écriture

    public V get(K key) {
                readLock.lock();  // ✅ plusieurs threads peuvent lire simultanément
        try { return map.get(key); }
        finally { readLock.unlock(); }
    }

    public void put(K key, V value) {
        writeLock.lock(); // exclusif : bloque tout autre lecteur ET écrivain
        try { map.put(key, value); }
        finally { writeLock.unlock(); }
    }
}

StampedLock (Java 8+) — Lecture Optimiste

// ┌─ StampedLock : encore plus rapide que ReadWriteLock ───────────────────────
// │  La lecture OPTIMISTE ne prend PAS de lock → ultra-rapide.
// │  Elle parie que personne n'écrira pendant la lecture.
// │  Si quelqu'un a écrit entre-temps → validate() échoue → on relit avec lock.
// └────────────────────────────────────────────────────────────────────────────
StampedLock sl = new StampedLock();
double x = 0, y = 0;

// Étape 1 : lecture optimiste — obtient un "stamp" (jeton de version)
long stamp = sl.tryOptimisticRead(); // ne bloque PAS
double cx = x, cy = y;                // lecture des données

// Étape 2 : valider que personne n'a modifié x/y depuis le stamp
if (!sl.validate(stamp)) {
    // Un écrivain est passé → lecture invalidée → fallback en lecture classique
    stamp = sl.readLock();
    try { cx = x; cy = y; }
    finally { sl.unlockRead(stamp); }
}
// cx et cy sont maintenant cohérents

Condition Variables — alternative fine à wait/notify

// ┌─ Condition : associe plusieurs files d'attente à un seul lock ─────────────
// │  Avec wait/notifyAll, on réveille TOUS les threads même si leur condition
// │  n'est pas satisfaite. Avec Condition, on signale précisément qui réveiller.
// └────────────────────────────────────────────────────────────────────────────
ReentrantLock lock     = new ReentrantLock();
Condition nonVide    = lock.newCondition(); // file d'attente "consommateurs"
Condition nonPleine  = lock.newCondition(); // file d'attente "producteurs"

// ── Producteur ───────────────────────────────────────────────────────────────
lock.lock();
try {
    while (file.size() == max) nonPleine.await(); // attend signal "place libre"
    file.add(item);
    nonVide.signal(); // réveille UN consommateur (pas tous !)
} finally { lock.unlock(); }

08

Classes Atomic

Avancé

Les classes java.util.concurrent.atomic utilisent les instructions CPU CAS (Compare-And-Swap) pour des opérations atomiques sans verrou.

AtomicInteger — le plus utilisé

import java.util.concurrent.atomic.*;

// ┌─ Comment fonctionne CAS (Compare-And-Swap) ────────────────────────────────
// │  Le CPU propose une instruction atomique : "si la valeur en mémoire est X,
// │  la remplacer par Y, sinon ne rien faire et retourner false".
// │  Pas de verrou → pas de blocage → bien plus rapide que synchronized.
// └────────────────────────────────────────────────────────────────────────────
AtomicInteger compteur = new AtomicInteger(0); // valeur initiale = 0

// Opérations atomiques courantes
compteur.incrementAndGet(); // ++i atomique  → retourne la NOUVELLE valeur
compteur.getAndIncrement(); // i++ atomique  → retourne l'ANCIENNE valeur
compteur.addAndGet(5);        // i += 5        → retourne la nouvelle valeur
compteur.get();               // lecture simple (thread-safe)

// ── CAS manuel : base de tous les algorithmes lock-free ──────────────────────
// "Si la valeur actuelle est 10, la mettre à 20 ; sinon ne rien faire"
boolean ok = compteur.compareAndSet(10, 20);
// ok = true si la valeur était bien 10 (maintenant 20), false sinon

// ── Java 8+ : transformations fonctionnelles atomiques ───────────────────────
compteur.updateAndGet(v -> v * 2);      // applique la fonction de façon atomique
compteur.accumulateAndGet(3, Integer::sum); // compteur += 3 de façon atomique

AtomicReference

// AtomicReference permet de faire un CAS sur n'importe quelle référence objet
// Utile pour les structures de données lock-free (listes, piles, arbres…)
AtomicReference<String> ref = new AtomicReference<>("initial");

ref.set("nouveau");                        // écriture atomique
String ancien = ref.getAndSet("autre");   // swap atomique → retourne "nouveau"
boolean ok = ref.compareAndSet("autre", "final"); // CAS → true si "autre"

LongAdder vs AtomicLong (Java 8+)

// ┌─ Pourquoi LongAdder est plus rapide sous haute contention ─────────────────
// │  AtomicLong utilise UN SEUL compteur → beaucoup de CAS en échec si
// │  plusieurs threads écrivent simultanément (spinning coûteux).
// │  LongAdder : distribue les incréments sur N "cellules" internes,
// │  une par thread actif. sum() additionne toutes les cellules à la fin.
// └────────────────────────────────────────────────────────────────────────────
LongAdder adder = new LongAdder();
adder.increment(); // incrémente la cellule du thread courant
adder.add(5);
long total = adder.sum(); // somme toutes les cellules → valeur approximative "en live"
adder.reset();           // remet toutes les cellules à zéro

// Règle d'usage :
// AtomicLong → quand on lit souvent (valeur précise à tout moment requis)
// LongAdder  → quand on écrit souvent (compteurs de métriques, stats)

Collections concurrentes

Intermédiaire

N'utilisez jamais ArrayList, HashMap etc. en multithreading sans synchronisation.

ConcurrentHashMap — le plus important

// ┌─ ConcurrentHashMap vs Hashtable ───────────────────────────────────────────
// │  Hashtable  : synchronized sur la map ENTIÈRE → un seul thread à la fois
// │  CHM Java 7 : locks par "segment" (16 segments → 16 threads simultanés)
// │  CHM Java 8 : CAS + locks par BUCKET → concurrence maximale
// └────────────────────────────────────────────────────────────────────────────
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// ── Opérations ATOMIQUES (pas besoin de synchronized externe) ────────────────
map.putIfAbsent("clé", 1);
// computeIfAbsent : calcule la valeur si la clé n'existe pas (atomique)
map.computeIfAbsent("clé", k -> calculerValeur(k));
// merge : si "clé" existe → applique (valeurExistante + 1), sinon → 1
map.merge("clé", 1, Integer::sum); // ✅ idiome parfait pour les compteurs
// compute : version plus générale, reçoit clé et valeur (ou null si absente)
map.compute("clé", (k, v) -> v == null ? 1 : v + 1);

// ⚠️ N'utilisez jamais synchronized(map) { ... } avec ConcurrentHashMap !
// │  Vous bloquez sans gain, et pouvez même créer des deadlocks.

BlockingQueue — cœur du Producteur/Consommateur

// ┌─ BlockingQueue : communication thread-safe entre producteurs/consommateurs ─
// │  Implémente automatiquement le pattern wait/notify vu en section 5.
// └────────────────────────────────────────────────────────────────────────────
BlockingQueue<String> q1 = new ArrayBlockingQueue<>(100); // ✅ file BORNÉE (recommandé)
BlockingQueue<String> q2 = new LinkedBlockingQueue<>();    // ⚠️ illimitée → risque OOM
BlockingQueue<String> q3 = new PriorityBlockingQueue<>();  // triée par priorité
BlockingQueue<String> q4 = new SynchronousQueue<>();      // transfert direct (taille 0)

// ── Opérations BLOQUANTES (à utiliser avec try/catch InterruptedException) ───
q1.put(item);                          // insère, BLOQUE si la file est pleine
q1.take();                             // retire, BLOQUE si la file est vide
// ── Opérations avec TIMEOUT (évitent un blocage infini) ──────────────────────
q1.offer(item, 1, TimeUnit.SECONDS);  // insère ou abandonne après 1s
q1.poll(1, TimeUnit.SECONDS);         // retire ou retourne null après 1s

// ┌─ Principe Copy-On-Write ────────────────────────────────────────────────────
// │  À chaque modification (add, set, remove), une COPIE COMPLÈTE du tableau
// │  interne est créée. La copie reçoit la modification, puis remplace l'original.
// │  Les lecteurs lisent toujours un snapshot cohérent, SANS verrou.
// └────────────────────────────────────────────────────────────────────────────
CopyOnWriteArrayList<String> liste = new CopyOnWriteArrayList<>();

liste.add("item"); // ⚠️ O(n) : copie tout le tableau → très coûteux si grande liste

// ── L'itérateur est IMMUTABLE et ne lève jamais ConcurrentModificationException
// (il itère sur le snapshot au moment de l'appel, même si la liste est modifiée)
for (String s : liste) { // ✅ safe même avec modifications concurrentes
    System.out.println(s);
}

Problèmes classiques

Avancé

🔴 Deadlock

Deux threads s'attendent mutuellement pour toujours.

Object ressourceA = new Object();
Object ressourceB = new Object();

// ┌─ Scénario de deadlock : acquisition dans l'ordre INVERSE ──────────────────
// │  Thread 1 : A → B          Thread 2 : B → A
// │  T1 prend A (succès), T2 prend B (succès)
// │  T1 attend B (pris par T2)  T2 attend A (pris par T1) → DEADLOCK
// └────────────────────────────────────────────────────────────────────────────

new Thread(() -> { // ❌ Thread 1 : prend A, veut B
    synchronized(ressourceA) {
        try { Thread.sleep(100); } catch (Exception e) {}
        synchronized(ressourceB) { // ← bloqué ici ad infinitum
            System.out.println("T1 a A et B");
        }
    }
}).start();

new Thread(() -> { // ❌ Thread 2 : prend B, veut A
    synchronized(ressourceB) {
        try { Thread.sleep(100); } catch (Exception e) {}
        synchronized(ressourceA) { // ← bloqué ici ad infinitum → DEADLOCK
            System.out.println("T2 a B et A");
        }
    }
}).start();

// ── Solution : TOUJOURS acquérir les locks dans le MÊME ordre ────────────────
new Thread(() -> { // ✅ Les deux threads : A en premier, puis B
    synchronized(ressourceA) {
        synchronized(ressourceB) {
            // impossible d'avoir un deadlock : les deux veulent A d'abord
        }
    }
}).start();

🟡 Livelock

Deux threads réagissent continuellement l'un à l'autre sans progresser (comme deux personnes dans un couloir qui s'évitent à l'infini). Différent du deadlock : les threads sont actifs mais n'avancent pas.

🟠 Starvation

Un thread ne parvient jamais à acquérir un lock car d'autres threads sont toujours prioritaires.

// ── Solution à la starvation : lock équitable (fair) ─────────────────────────
// Un lock fair garantit l'ordre FIFO : le thread qui attend depuis le plus longtemps
// est le prochain servi. Plus lent (throughput réduit), mais équitable.
Lock fairLock = new ReentrantLock(true); // true = mode équitable (FIFO)
// ⚠️ Le lock fair est plus lent que le lock non-fair (défaut)
// │  À utiliser uniquement si la starvation est avérée en production.

🔵 Outils de diagnostic

// ┌─ Détection programmatique des deadlocks via JMX ───────────────────────────
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads(); // null si aucun deadlock
if (deadlocked != null) {
    ThreadInfo[] infos = bean.getThreadInfo(deadlocked, true, true); // avec stack trace
    for (ThreadInfo info : infos) {
        System.err.println("⚠️ Deadlock sur : " + info.getThreadName());
        System.err.println("   Attend : " + info.getLockName());
    }
}
// Astuce : "jstack <pid>" en ligne de commande dump tous les threads avec leurs locks

Outils de synchronisation avancés

// ── CountDownLatch : attendre N événements (usage unique) ────────────────────
// Scénario : le main attend que 3 services soient prêts avant de démarrer.
CountDownLatch latch = new CountDownLatch(3);
// 3 threads de services appelleront latch.countDown() quand prêts
latch.await();           // le main bloque jusqu'à ce que le compteur atteigne 0
latch.await(30, TimeUnit.SECONDS); // avec timeout de sécurité

// ── CyclicBarrier : synchroniser N threads à un point de rendez-vous ─────────
// Scénario : 3 threads calculent chacun une partie → se retrouvent pour fusionner.
// "Cyclic" = réutilisable (contrairement à CountDownLatch)
CyclicBarrier barrier = new CyclicBarrier(3, () ->
    System.out.println("Tous arrivés ! Phase suivante..."));
// Chaque thread appelle barrier.await() — le dernier arrivé déclenche le callback

// ── Semaphore : limiter l'accès à N ressources simultanées ───────────────────
// Scénario : pool de 5 connexions DB → au plus 5 threads peuvent accéder à la DB.
Semaphore sem = new Semaphore(5); // 5 "permis" disponibles
sem.acquire();                  // prend 1 permis, bloque si 0 disponible
try { /* accès à la ressource limitée */ }
finally { sem.release(); }     // ✅ TOUJOURS libérer dans finally

// ── Exchanger : rendez-vous et échange de données entre exactement 2 threads ──
Exchanger<String> ex = new Exchanger<>();
// Thread A : String reçuDeB = ex.exchange("donnéeDeA");  ← bloque jusqu'à B
// Thread B : String reçuDeA = ex.exchange("donnéeDeB");  ← les deux se débloquent

CompletableFuture (Java 8+)

Avancé

CompletableFuture permet la programmation asynchrone et non-bloquante avec des pipelines de traitement chainés.

Les bases

import java.util.concurrent.*;

// ── runAsync : tâche sans retour ──────────────────────────────────────────────
CompletableFuture.runAsync(() ->
    System.out.println("S'exécute dans ForkJoinPool.commonPool()"));

// ── supplyAsync : tâche avec retour ──────────────────────────────────────────
// Retour IMMÉDIAT : l'appel n'attend pas la fin de l'opération asynchrone
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> {
    // s'exécute dans ForkJoinPool.commonPool() (threads daemon)
    return appelAPILente(); // ex: appel HTTP, requête DB…
});

// ── Avec ExecutorService dédié (RECOMMANDÉ en production) ────────────────────
// ForkJoinPool.commonPool() est partagé avec les Streams parallèles.
// Un executor dédié évite les interférences et permet un dimensionnement précis.
ExecutorService pool = Executors.newFixedThreadPool(4);
CompletableFuture<String> cf2 = CompletableFuture.supplyAsync(() -> appelAPILente(), pool);

Pipeline de transformation

// ┌─ Chaque étape s'exécute quand la précédente est terminée ──────────────────
// │  Les méthodes *Async() utilisent un thread du pool pour l'étape suivante.
// │  Les méthodes sans Async réutilisent le thread de l'étape précédente.
// └────────────────────────────────────────────────────────────────────────────
CompletableFuture<String> pipeline = CompletableFuture
    .supplyAsync(() -> fetchUserId())       // démarre le pipeline : retourne un String
    .thenApply(id -> fetchUser(id))         // String → User (même thread)
    .thenApply(User::getEmail)             // User → String (même thread)
    .thenApplyAsync(email -> valider(email)) // String → String (nouveau thread pool)
    .exceptionally(ex -> {                   // si TOUTE étape lève une exception
        log("Erreur pipeline : " + ex.getMessage());
        return "erreur@default.com";          // valeur de repli
    })
    .whenComplete((res, ex) -> log(res, ex)); // callback final (succès ET erreur)

String email = pipeline.get(); // ⚠️ bloquant — à éviter dans les serveurs réactifs
String email2 = pipeline.join(); // ✅ même résultat mais lève CompletionException (unchecked)

Combinaison de futures

CompletableFuture<String> future1 = CompletableFuture.supplyAsync(() -> "Hello");
CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> "World");

// ── thenCombine : combine 2 futures INDÉPENDANTS quand les deux sont terminés ─
CompletableFuture<String> combined = future1
    .thenCombine(future2, (a, b) -> a + " " + b); // "Hello World"

// ── allOf : attend QUE TOUS les futures soient terminés ──────────────────────
// Retourne CF<Void> → récupérer les valeurs avec future1.join(), future2.join()…
CompletableFuture.allOf(future1, future2).join();

// ── anyOf : retourne DÈS QUE le PREMIER future est terminé ───────────────────
// Utile pour les appels en double (appel le plus rapide gagne)
CompletableFuture.anyOf(future1, future2).join();

// ── thenCompose : chaîne de futures DÉPENDANTS (le résultat de l'un alimente le suivant)
// Si on utilisait thenApply ici → CF<CF<User>> (imbriqué → inutilisable)
// thenCompose "aplatit" le résultat → CF<User>
CompletableFuture<User> user = CompletableFuture
    .supplyAsync(() -> getUserId())
    .thenCompose(id -> fetchUserAsync(id)); // fetchUserAsync retourne CF<User>

Gestion d'erreurs complète

CompletableFuture<String> robuste = CompletableFuture
    .supplyAsync(() -> riskyOperation())
    // handle() reçoit (résultat, exception) — l'un des deux est toujours null
    // Contrairement à exceptionally(), handle() s'exécute TOUJOURS (succès ou erreur)
    .handle((result, ex) -> {
        if (ex != null) {
            log("Erreur : " + ex.getMessage());
            return "valeur par défaut"; // recovery
        }
        return result; // chemin nominal
    })
    .thenApply(String::toUpperCase); // continue le pipeline sur la valeur récupérée

// ── Complétion manuelle : utile pour les callbacks (ex: callback HTTP) ────────
CompletableFuture<String> manual = new CompletableFuture<>();
manual.complete("valeur");                              // déclenche le pipeline (succès)
manual.completeExceptionally(new RuntimeException()); // déclenche avec erreur
manual.completeOnTimeout("défaut", 1, TimeUnit.SECONDS); // Java 9 : timeout automatique

🟢 Niveau Junior

Q01 Quelle est la différence entre un processus et un thread ? Junior ▼

Un processus est une instance de programme avec sa propre mémoire isolée (heap, stack, registres). Un thread est une unité d'exécution légère au sein d'un processus. Les threads d'un même processus partagent la mémoire heap mais ont chacun leur propre stack. Créer un thread est beaucoup plus rapide que créer un processus, mais les threads sont plus susceptibles de se corrompre mutuellement (race conditions, deadlocks).

Q02 Quelle est la différence entre thread.start() et thread.run() ? Junior ▼

start() crée un nouveau thread système et appelle run() dessus de façon asynchrone. run() exécute simplement la méthode sur le thread courant, comme un appel de méthode ordinaire — il n'y a donc aucun parallélisme.

Thread t = new Thread(() -> System.out.println(Thread.currentThread().getName()));
t.run();   // ❌ affiche "main" → pas de nouveau thread
t.start(); // ✅ affiche "Thread-0" → nouveau thread créé
Q03 Quelle est la différence entre Runnable et Callable ? Junior ▼

Runnable a une méthode run() qui retourne void et ne peut pas lancer d'exceptions vérifiées. Callable<T> a une méthode call() qui retourne un résultat de type T et peut lancer une Exception. Callable est utilisé avec ExecutorService.submit() qui retourne un Future<T>.

Q04 Quels sont les états possibles d'un thread Java ? Junior ▼

6 états définis dans Thread.State :

  • NEW — thread créé mais pas encore démarré
  • RUNNABLE — en cours d'exécution ou prêt (attend le CPU)
  • BLOCKED — en attente d'un monitor (synchronized)
  • WAITING — en attente indéfinie (wait(), join() sans timeout)
  • TIMED_WAITING — en attente temporisée (sleep(n), wait(n), join(n))
  • TERMINATED — exécution terminée
Q05 Qu'est-ce qu'un thread démon (daemon) ? Junior ▼

Un thread démon est un thread de service qui tourne en arrière-plan. La JVM se termine automatiquement quand il ne reste plus que des threads démons actifs. On le configure avec t.setDaemon(true) avant t.start(). Exemples : GC, Finalizer. Attention : les threads démons peuvent être interrompus brutalement sans chance de nettoyer leurs ressources.

🟡 Niveau Intermédiaire

Q06 Qu'est-ce qu'une race condition ? Donnez un exemple et comment la corriger. Intermédiaire ▼

Une race condition se produit quand le résultat dépend de l'ordre d'exécution non-déterministe des threads. L'opération i++ est non-atomique (read → modify → write). Si deux threads l'exécutent simultanément, une mise à jour peut être perdue.

Solutions : synchronized, AtomicInteger, volatile (uniquement pour la visibilité, pas l'atomicité).

Q07 Différence entre synchronized et volatile ? Intermédiaire ▼

synchronized garantit la visibilité ET l'atomicité des blocs. Il empêche plusieurs threads d'entrer simultanément dans la section critique.

volatile garantit uniquement la visibilité : toute écriture est immédiatement visible (contourne le cache CPU), mais n'assure pas l'atomicité des opérations composées. Utilisez volatile pour les flags simples, et synchronized ou Atomic* pour les compteurs.

Q08 Pourquoi utiliser while et pas if autour de wait() ? Intermédiaire ▼

À cause des spurious wakeups — la JVM ou l'OS peut réveiller un thread sans qu'un notify() ait été appelé. Avec if, le thread continuerait sans vérifier si la condition est vraiment satisfaite. Avec while, la condition est revérifiée à chaque réveil. C'est la recommandation de la Javadoc officielle.

Q09 Quelle est la différence entre notify() et notifyAll() ? Intermédiaire ▼

notify() réveille un seul thread arbitraire parmi ceux en attente. notifyAll() réveille tous les threads — ils recompètent pour le lock, la condition est revérifiée par chacun. Préférez notifyAll() : notify() peut mener à de la starvation si le mauvais thread est réveillé.

Q10 Comment fonctionne ConcurrentHashMap comparé à HashMap et Hashtable ? Intermédiaire ▼

HashMap n'est pas thread-safe. Hashtable synchronise toutes les opérations sur l'objet entier — très lent. ConcurrentHashMap utilise des CAS et locks par bucket (Java 8+) : seul le bucket concerné est verrouillé, permettant une très haute concurrence. Les opérations composées (putIfAbsent, computeIfAbsent, merge) sont atomiques.

🔴 Niveau Avancé / Senior

Q11 Qu'est-ce qu'un deadlock et comment le prévenir ? Avancé ▼

Un deadlock survient quand deux threads s'attendent mutuellement. Les 4 conditions de Coffman : exclusion mutuelle, possession et attente, pas de préemption, attente circulaire.

  • Toujours acquérir les locks dans le même ordre
  • Utiliser tryLock(timeout) (sortie de secours)
  • Réduire la granularité des sections critiques
  • Préférer les structures lock-free (ConcurrentHashMap, AtomicXxx)
  • Détecter avec ThreadMXBean.findDeadlockedThreads()
Q12 Expliquez le problème ABA et comment le résoudre. Avancé ▼

Un thread lit la valeur A. Un autre thread la change en B puis en A. Le premier fait son CAS (compare A, swap) et réussit — alors que l'état a changé deux fois, ce qui peut corrompre une structure de données.

Solution : AtomicStampedReference<T> associe un stamp (numéro de version) à la référence. Le CAS échoue si le stamp a changé même si la valeur est redevenue A.

// Chaque CAS vérifie DEUX conditions : la valeur ET le numéro de version
AtomicStampedReference<Integer> ref =
    new AtomicStampedReference<>(1, 0); // valeur=1, stamp=0
int[] stampHolder = new int[1];
Integer current = ref.get(stampHolder); // lit valeur et stamp simultanément
// CAS : "si valeur=current ET stamp=stampHolder[0], mettre newVal avec stamp+1"
ref.compareAndSet(current, 2, stampHolder[0], stampHolder[0] + 1);
Q13 Quelle est la différence entre ReentrantLock et synchronized ? Avancé ▼

ReentrantLock offre tout ce que fait synchronized, plus :

  • tryLock() : tentative non-bloquante
  • tryLock(timeout) : avec délai d'expiration
  • lockInterruptibly() : interruptible pendant l'attente
  • Fair mode : new ReentrantLock(true) → FIFO
  • Conditions multiples : lock.newCondition()
  • Monitoring : getQueueLength(), isLocked()

Inconvénient : il faut manuellement unlock() dans un bloc finally. synchronized se déverrouille automatiquement.

Q14 Quelle taille de thread pool choisir en production ? Avancé ▼

La formule de Brian Goetz :

Pour les tâches CPU-bound : N_threads = N_CPUs + 1

Pour les tâches I/O-bound : N_threads = N_CPUs × (1 + temps_attente / temps_CPU)

En pratique pour les services web, commencez avec N_CPUs × 2 à N_CPUs × 10 selon les mesures. Évitez newCachedThreadPool en production (peut créer des milliers de threads → OOM).

Q15 Expliquez le Java Memory Model (JMM) et la relation happens-before. Avancé ▼

Le JMM définit quand une écriture d'un thread est garantie d'être visible par un autre. Par défaut, rien n'est garanti (compilateurs et CPUs réordonnent). La relation happens-before garantit la visibilité :

  • unlock happens-before le prochain lock sur le même monitor
  • Écriture volatile happens-before sa lecture
  • Thread.start() happens-before toute action dans ce thread
  • Toute action d'un thread happens-before join() retourne
Q16 Comment implémenter un Singleton thread-safe ? Avancé ▼ 
// ── Approche 1 : Enum Singleton (RECOMMANDÉE) ─────────────────────────────────
// La JVM garantit qu'une enum n'est instanciée qu'une seule fois.
// Protection contre la sérialisation et la réflexion offerte gratuitement.
public enum MonSingleton {
    INSTANCE; // une seule instance garantie par la JVM
    public void doSomething() { }
}

// ── Approche 2 : Initialization-on-demand Holder (idiomatique) ────────────────
// La classe Holder n'est chargée que lors du premier appel à getInstance().
// Le classloader garantit l'initialisation thread-safe sans synchronized.
public class Singleton {
    private Singleton() {}
    private static class Holder {
        // initialisé au premier accès à Holder, thread-safe par spec JVM
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// ── Approche 3 : Double-checked Locking (Java 5+) ────────────────────────────
// volatile OBLIGATOIRE : sans lui, le compilateur peut réordonner les instructions
// de "new Singleton()" et publier une référence partiellement construite.
public class Singleton {
        private volatile static Singleton instance; // volatile indispensable !
    public static Singleton getInstance() {
        if (instance == null) {                  // 1er check SANS lock (performances)
            synchronized (Singleton.class) {
                if (instance == null)             // 2ème check AVEC lock (sûreté)
                    instance = new Singleton();
            }
        }
        return instance;
    }
}
Q17 Quelle est la différence entre thenApply et thenCompose ? Avancé ▼

thenApply(fn) applique T → U — équivalent de Stream.map. thenCompose(fn) attend T → CompletableFuture<U> et retourne CompletableFuture<U> (pas CF<CF<U>>) — équivalent de Stream.flatMap. Utilisez thenCompose quand votre transformation elle-même retourne un future asynchrone.

Q18 Qu'est-ce que ThreadLocal et quand l'utiliser ? Avancé ▼

ThreadLocal<T> fournit une variable dont chaque thread a sa propre copie indépendante. Idéal pour : connexion DB par thread, session utilisateur, SimpleDateFormat (non thread-safe).

// Chaque thread obtient sa propre instance de SimpleDateFormat via withInitial()
// → pas de synchronisation nécessaire sur le formateur
private static final ThreadLocal<SimpleDateFormat> formatter =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String date = formatter.get().format(new Date()); // propre à ce thread

// ┌─ PIÈGE : memory leak avec les thread pools ─────────────────────────────────
// │  Dans un pool, les threads sont réutilisés. La valeur ThreadLocal reste
// │  attachée au thread et sera lue par la prochaine requête si on ne la nettoie pas.
// └────────────────────────────────────────────────────────────────────────────
try {
    return formatter.get().format(new Date());
} finally {
        formatter.remove(); // ✅ nettoyage obligatoire dans les thread pools
}
