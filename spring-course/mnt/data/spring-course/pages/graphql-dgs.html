Chapitre

GraphQL avec Netflix DGS

Schéma, resolvers, mutations, DataLoaders et organisation projet.

1. Introduction

GraphQL est un langage de requête pour API. Le client demande exactement les champs voulus. Netflix DGS est un framework Java très pratique pour construire des API GraphQL sur Spring Boot.

ComparaisonRESTGraphQL
Forme des réponsesFixée par l’endpointChoisie par le client
Sur-récupérationFréquenteRéduite
EndpointsMultiplesSouvent un endpoint unique
ComplexitéSouvent plus simple au débutPlus puissante mais plus exigeante

2. Niveau débutant

Les bases :

  • Schema : contrat de l’API
  • type : structure d’un objet
  • Query : lecture
  • Mutation : écriture
  • Input : objet d’entrée
  • Resolver / Data fetcher : code Java qui fournit la donnée
# Fichier : src/main/resources/schema/schema.graphqls
type Query {
  productById(id: ID!): Product
}

type Product {
  id: ID!
  name: String!
  price: Float!
}
@DgsComponent
public class ProductDataFetcher {
    private final ProductService productService;

    public ProductDataFetcher(ProductService productService) {
        this.productService = productService;
    }

    @DgsQuery
    public Product productById(@InputArgument Long id) {
        return productService.findById(id);
    }
}

3. Niveau intermédiaire

Organisation de projet recommandée avec DGS :

src/main/java/com/example/catalog/
├── graphql/
│   ├── query/
│   ├── mutation/
│   └── dataloader/
├── service/
├── repository/
└── domain/

Exemple de mutation :

input CreateProductInput {
  name: String!
  price: Float!
}

type Mutation {
  createProduct(input: CreateProductInput!): Product!
}
@DgsComponent
public class ProductMutation {
    private final ProductService productService;

    @DgsMutation
    public Product createProduct(@InputArgument CreateProductInput input) {
        return productService.create(input.name(), input.price());
    }
}

Bonnes pratiques :

  • Valider les inputs côté service.
  • Ne pas laisser les data fetchers porter toute la logique métier.
  • Prévoir pagination et filtrage dès les listes volumineuses.

4. Niveau avancé

N+1 en GraphQL : comme en JPA, tu peux tomber sur une explosion de requêtes si chaque champ imbriqué déclenche une lecture supplémentaire. DGS permet d’utiliser des DataLoaders pour batcher les accès.

Cas réel : une requête demande 50 produits et pour chacun son fournisseur. Sans batching, tu peux faire 51 appels. Avec un DataLoader, tu regroupes ces lectures.

Erreurs : il faut distinguer erreurs techniques, erreurs de validation et absence de données. GraphQL renvoie souvent un tableau errors avec des détails contextualisés.

Pagination : pour une API durable, préfère un modèle explicite de pagination. Selon les cas, offset/limit suffit, sinon pense “cursor-based pagination”.

Recommandation senior : GraphQL est excellent quand le front a besoin de composer des vues riches et variables. Pour une API simple et stable, REST peut rester plus facile à opérer.

5. Exemples de code

// Fichier : SupplierDataLoader.java
@DgsDataLoader(name = "supplierLoader")
public class SupplierDataLoader implements BatchLoader<Long, Supplier> {
    private final SupplierService supplierService;

    @Override
    public CompletionStage<List<Supplier>> load(List<Long> supplierIds) {
        // On batch la lecture pour éviter le N+1.
        return CompletableFuture.supplyAsync(() -> supplierService.findAllByIds(supplierIds));
    }
}

6. À retenir

  • GraphQL permet au client de choisir ses champs.
  • DGS structure bien l’intégration GraphQL dans un projet Spring Boot.
  • Attention au N+1 et aux DataLoaders.
  • Les data fetchers doivent rester minces.
  • GraphQL n’est pas “meilleur partout” que REST ; il répond à certains besoins.
