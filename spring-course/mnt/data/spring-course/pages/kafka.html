Chapitre

Kafka

Streaming d’événements, topics, partitions, Spring Kafka et bonnes pratiques.

1. Introduction

Kafka est une plateforme de streaming d’événements distribuée, conçue pour gérer de gros volumes, conserver les messages et permettre plusieurs consommateurs indépendants.

Pourquoi Kafka existe : absorber des flux importants, rejouer l’historique, découpler des systèmes et construire des architectures événementielles robustes.

Analogie : Kafka ressemble à un journal d’événements persistant. On écrit dans un registre ordonné, puis plusieurs lecteurs viennent lire chacun à leur rythme.

2. Niveau débutant

Vocabulaire essentiel :

  • Broker : serveur Kafka.
  • Topic : canal logique.
  • Partition : subdivision d’un topic, base de parallélisme.
  • Offset : position d’un message dans une partition.
  • Producer : écrit des messages.
  • Consumer : lit des messages.
  • Consumer group : groupe partageant la consommation d’un topic.
// Fichier : OrderEventPublisher.java
@Service
@RequiredArgsConstructor
public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate;

    public void publish(OrderCreatedEvent event) {
        // La clé influence la partition et donc l’ordre local des messages liés.
        kafkaTemplate.send("order.created", event.orderId().toString(), event);
    }
}

Piège débutant : croire que l’ordre est global sur tout le topic. En pratique, l’ordre est garanti au niveau d’une partition, pas du topic complet.

3. Niveau intermédiaire

Concepts réalistes :

  • Rebalancing : répartition des partitions entre consommateurs d’un groupe.
  • Acks : niveau d’accusé de réception côté producteur.
  • Retries : tentatives de réémission.
  • DLQ : topic d’erreur pour les messages non traitables.
  • Retention : durée ou taille de conservation.
  • Compaction : conservation de la dernière valeur par clé.
@Configuration
public class KafkaProducerConfig {
    @Bean
    public ProducerFactory<String, OrderCreatedEvent> producerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        return new DefaultKafkaProducerFactory<>(props);
    }
}

Pourquoi acks=all et l’idempotence sont utiles : meilleure fiabilité, moins de doublons en cas de retry.

4. Niveau avancé

Exactly-once semantics : sujet subtil. Kafka peut offrir certaines garanties fortes, mais elles dépendent de la configuration du producteur, du consommateur et parfois des transactions Kafka.

Transactions Kafka : utiles lorsqu’on veut produire plusieurs messages de manière atomique, ou lire puis republier avec des garanties cohérentes.

Sérialisation : JSON est simple pour démarrer. Avro + Schema Registry devient intéressant quand les contrats évoluent et que plusieurs équipes consomment les événements.

Piège subtil : traiter Kafka comme une simple queue. Kafka est aussi un log persistant, conçu pour replay, analytics, intégration multi-consommateurs et haut débit.

Monitoring : surveiller lag consommateur, débit, erreurs de sérialisation, timeouts, rebalances, tailles de topics et saturation des brokers.

Comparaison Kafka vs RabbitMQ : Kafka est excellent pour l’event streaming, la rétention et la relecture. RabbitMQ est souvent plus direct pour la messagerie applicative et le routage fin.

5. Exemples de code

// Fichier : OrderEventConsumer.java
@Component
@Slf4j
public class OrderEventConsumer {

    @KafkaListener(topics = "order.created", groupId = "billing-service")
    public void onMessage(OrderCreatedEvent event) {
        // Le consumer doit idéalement être idempotent côté métier.
        // En cas de redelivery, il ne doit pas facturer deux fois.
        log.info("Received order event {}", event);
    }
}

6. À retenir

  • L’ordre est garanti par partition, pas globalement par topic.
  • Le design de la clé est un choix d’architecture important.
  • Idempotence, retries et DLQ sont des sujets de base en production.
  • Kafka n’est pas seulement une queue : c’est un log distribué persistant.
  • Il faut penser schémas d’événements, observabilité et reprise.
