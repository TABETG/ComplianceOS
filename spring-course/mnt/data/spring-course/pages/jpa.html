Chapitre

Spring Data JPA

Entités, relations, repositories, DTO, performance et N+1.

1. Introduction

JPA est une spécification Java pour mapper des objets vers une base relationnelle. Hibernate est une implémentation populaire de cette spécification.

ComparaisonJPAHibernate
NatureSpécificationImplémentation
RôleDéfinit des contratsExécute réellement le mapping et les requêtes
RecommandationCoder au plus près de JPAUtiliser Hibernate quand ses fonctionnalités avancées sont utiles

2. Niveau débutant

Les bases : @Entity, @Id, @GeneratedValue.

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String email;
}

Un repository Spring Data simplifie les opérations courantes :

public interface CustomerRepository extends JpaRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);
}

Piège débutant : retourner directement les entités JPA dans toutes les API externes sans DTO. Cela couple l’API HTTP au modèle de persistence.

3. Niveau intermédiaire

Relations principales :

  • @OneToOne : profil utilisateur, carte bancaire, etc.
  • @OneToMany / @ManyToOne : commande et lignes de commande.
  • @ManyToMany : à utiliser avec prudence.
@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();
}

@Entity
public class OrderLine {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;
}
ChoixAvantagesRisquesRecommandation
LAZYCharge à la demandeLazyInitializationException si mal utiliséPar défaut
EAGERSimple à court termeSurcharge, N+1, explosions de graphesÀ éviter sauf cas précis

CrudRepository vs JpaRepository : JpaRepository ajoute pagination, tri, flush et des outils très pratiques. C’est souvent le choix standard en projet Spring Data JPA.

4. Niveau avancé

N+1 : problème fréquent où une requête principale déclenche ensuite une requête supplémentaire par ligne chargée. Très courant avec des relations lazy mal exploitées.

Exemple : charger 100 commandes, puis accéder à leur client dans une boucle peut produire 101 requêtes.

Solutions classiques :

  • join fetch en JPQL
  • @EntityGraph
  • Projections ou DTO dédiés
  • Lecture optimisée selon le besoin écran / API
@Query("""
    select o from Order o
    join fetch o.customer
    where o.status = :status
""")
List<Order> findAllWithCustomerByStatus(@Param("status") OrderStatus status);

Audit : on utilise souvent @CreatedDate, @LastModifiedDate avec @EnableJpaAuditing.

Recommandation senior : penser les requêtes depuis le besoin métier et l’écran cible, pas depuis “l’entité complète”.

5. Exemples de code

// Fichier : CustomerSummary.java
public record CustomerSummary(Long id, String email, long orderCount) {}

// Fichier : CustomerRepository.java
@Query("""
    select new com.example.demo.customer.CustomerSummary(c.id, c.email, count(o.id))
    from Customer c
    left join c.orders o
    group by c.id, c.email
""")
Page<CustomerSummary> findCustomerSummaries(Pageable pageable);

Ici, on évite d’exposer toute l’entité et on répond exactement au besoin de lecture.

6. À retenir

  • JPA est une spécification, Hibernate une implémentation.
  • Préférer LAZY par défaut sur les relations.
  • Éviter les entités exposées directement aux API publiques.
  • Surveiller le N+1 dès les premiers écrans.
  • Les DTO et projections sont des outils d’architecture, pas juste de “l’enrobage”.
