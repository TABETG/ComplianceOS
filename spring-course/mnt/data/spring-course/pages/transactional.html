Chapitre

@Transactional

Transactions Spring, propagation, rollback, proxy et pièges de production.

1. Introduction

Une transaction est une unité de travail qui doit être exécutée de manière cohérente. Soit tout réussit, soit tout est annulé.

Analogie : un virement bancaire : débiter sans créditer serait incohérent. La transaction garantit l’intégrité.

@Transactional permet à Spring d’encadrer des opérations de persistence dans une transaction.

2. Niveau débutant

Exemple simple :

@Service
public class TransferService {
    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();

        from.debit(amount);
        to.credit(amount);
    }
}

Ici, si une exception survient après le débit et avant le crédit, la transaction évite un état incohérent.

Erreur fréquente : penser que @Transactional agit “dans la méthode”. En réalité, Spring passe généralement par un proxy autour du bean.

3. Niveau intermédiaire

Concepts indispensables :

  • Propagation : comment une transaction se comporte si une autre existe déjà.
  • Isolation : visibilité des données concurrentes.
  • Rollback : quand annuler les changements.
  • readOnly=true : optimisation potentielle pour lecture.
PropagationEffetUsage
REQUIREDRejoint la transaction existante ou en crée uneCas standard
REQUIRES_NEWSuspension de l’ancienne, création d’une nouvelleAudit séparé, journalisation indépendante
MANDATORYExige une transaction existanteAPI interne stricte

Checked vs unchecked exceptions : par défaut, Spring rollback sur les exceptions runtime, pas forcément sur les checked exceptions. On peut ajuster avec rollbackFor.

@Transactional(rollbackFor = IOException.class)
public void importFile() throws IOException { ... }

4. Niveau avancé

Piège majeur : les appels internes de méthode dans la même classe ne passent pas toujours par le proxy Spring. Donc un @Transactional sur une méthode appelée via this peut être ignoré.

Transaction et JPA : le contexte de persistence suit souvent le scope transactionnel. Le lazy loading a besoin d’une session active. Hors transaction, tu peux obtenir une LazyInitializationException.

Performance : garder une transaction ouverte trop longtemps augmente les verrous, la contention et le temps de rétention des connexions SQL.

Recommandation senior : la transaction vit en général au niveau service, là où le use case métier est complet. Le repository doit rester focalisé sur l’accès aux données.

ChoixAvantagesRisquesRecommandation
@Transactional sur serviceAligne transaction et use case métierPeut devenir trop large si service mal découpéPréféré
@Transactional sur repositorySimple pour une opération isoléeVision métier fragmentéeUsage ponctuel

5. Exemples de code

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentGateway paymentGateway;
    private final AuditService auditService;

    @Transactional
    public Order placeOrder(CreateOrderCommand command) {
        Order order = Order.create(command);
        orderRepository.save(order);

        paymentGateway.charge(order.totalAmount());

        // Attention : si auditService utilise REQUIRES_NEW,
        // l'audit peut être persisté même si la transaction principale échoue ensuite.
        auditService.recordOrderCreation(order.getId());
        return order;
    }
}

6. À retenir

  • @Transactional repose le plus souvent sur un proxy Spring.
  • Le rollback par défaut vise surtout les runtime exceptions.
  • Le lazy loading et la transaction sont étroitement liés.
  • La transaction doit vivre au niveau du use case métier.
  • Une transaction trop longue nuit aux performances.
