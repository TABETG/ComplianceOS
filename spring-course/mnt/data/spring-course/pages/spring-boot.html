Chapitre

Spring Boot

Fondations, auto-configuration, profils, structure et bonnes pratiques.

1. Introduction

Définition simple : Spring Boot est une surcouche du Spring Framework qui réduit la configuration nécessaire pour démarrer une application Java moderne. Il ne remplace pas Spring : il l’organise, le préconfigure et standardise la façon de construire une application.

À quoi ça sert : accélérer le démarrage d’un projet, réduire le boilerplate, homogénéiser la configuration et faciliter l’exécution locale comme le déploiement.

Analogie : Spring Framework, c’est une grande boîte à outils. Spring Boot, c’est un atelier déjà préparé avec les bons outils sur la table, l’électricité branchée et une organisation cohérente.
ComparaisonSpring FrameworkSpring BootRecommandation
PhilosophieFramework modulaire très flexibleConvention over configurationUtiliser Boot pour presque tous les projets métier modernes
ConfigurationSouvent plus expliciteBeaucoup d’auto-configurationBoot fait gagner du temps, mais il faut comprendre ce qu’il configure
DémarragePlus manuelTrès rapide avec startersIdéal en formation et en production
Erreur fréquente : croire que Spring Boot “fait de la magie”. En réalité, il applique des règles lisibles, basées sur le classpath, les propriétés et les beans déjà présents.

2. Niveau débutant

Les briques à connaître en premier :

  • Starter : dépendance groupée qui apporte un ensemble cohérent de librairies.
  • Auto-configuration : configuration automatique activée selon le contexte.
  • Component scan : détection automatique des classes annotées.
  • Bean : objet géré par le conteneur Spring.
  • Application context : le conteneur principal de Spring.
src/main/java/com/example/demo/
├── DemoApplication.java
├── controller/
│   └── HelloController.java
└── service/
    └── GreetingService.java
// Fichier : src/main/java/com/example/demo/DemoApplication.java
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        // Lance le conteneur Spring, crée les beans et démarre le serveur embarqué
        SpringApplication.run(DemoApplication.class, args);
    }
}

// Fichier : src/main/java/com/example/demo/service/GreetingService.java
@Service
public class GreetingService {
    public String sayHello() {
        return "Bonjour Spring Boot";
    }
}

// Fichier : src/main/java/com/example/demo/controller/HelloController.java
@RestController
@RequestMapping("/api")
public class HelloController {
    private final GreetingService greetingService;

    // Injection par constructeur : claire, testable, recommandée
    public HelloController(GreetingService greetingService) {
        this.greetingService = greetingService;
    }

    @GetMapping("/hello")
    public String hello() {
        return greetingService.sayHello();
    }
}
Piège débutant : placer la classe principale dans un package trop bas. La règle simple : mets la classe annotée @SpringBootApplication à la racine du package principal.

3. Niveau intermédiaire

Quand ton application grandit, tu dois comprendre ce que contient réellement @SpringBootApplication. Cette annotation combine :

  • @Configuration : la classe peut déclarer des beans.
  • @EnableAutoConfiguration : Spring Boot active ses configurations automatiques.
  • @ComponentScan : Spring cherche les composants dans le package courant et ses sous-packages.
Cas réel : en entreprise, on ajoute souvent plusieurs profils Spring comme dev, test, staging, prod pour changer l’URL de base de données, les niveaux de logs ou l’activation de certains beans.
# Fichier : src/main/resources/application.yml
spring:
  application:
    name: billing-service
  profiles:
    active: dev
server:
  port: 8081

---
spring:
  config:
    activate:
      on-profile: dev
  datasource:
    url: jdbc:postgresql://localhost:5432/billing_dev
    username: postgres
    password: postgres
logging:
  level:
    root: INFO
    com.example: DEBUG

---
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    url: jdbc:postgresql://prod-db:5432/billing
    username: billing_app
    password: ${DB_PASSWORD}

Bonnes pratiques :

  • Externaliser la configuration sensible avec des variables d’environnement.
  • Éviter de coder en dur les secrets.
  • Créer des classes de configuration dédiées via @ConfigurationProperties quand le nombre de propriétés grandit.

4. Niveau avancé

Auto-configuration : Spring Boot charge des classes d’auto-configuration conditionnelles. Elles s’activent selon des conditions comme “une classe est présente sur le classpath” ou “aucun bean équivalent n’a déjà été déclaré”.

Conséquence : si tu déclares ton propre bean ObjectMapper, DataSource ou TaskExecutor, tu peux remplacer ou compléter le comportement par défaut.

Piège subtil : “ça marche en local mais pas en production” est souvent un problème de profil, de variables d’environnement ou d’auto-configuration neutralisée par un bean custom.

Cycle de vie simplifié :

  1. Lecture des propriétés et préparation de l’environnement.
  2. Création de l’application context.
  3. Scan des composants.
  4. Application des auto-configurations.
  5. Création et injection des beans.
  6. Exécution des hooks de démarrage comme CommandLineRunner.
  7. Démarrage du serveur embarqué si application web.
@Configuration
public class HttpClientConfig {

    @Bean
    public RestClient restClient(RestClient.Builder builder) {
        // On personnalise le bean fourni par Spring Boot plutôt que de tout reconstruire à la main
        return builder
                .baseUrl("https://api.example.com")
                .build();
    }
}

Recommandation senior : comprendre ce que Boot t’offre par défaut, puis ne personnaliser que ce qui apporte une vraie valeur métier ou opérationnelle.

5. Exemples de code

// Fichier : src/main/java/com/example/demo/config/MailConfiguration.java
@Configuration
public class MailConfiguration {

    @Bean
    public MailClient mailClient(MailProperties properties) {
        // @Bean indique que l'objet retourné doit être géré par Spring.
        // Ici on construit un composant externe qu'on ne peut pas annoter avec @Component.
        return new MailClient(properties.host(), properties.port());
    }
}

// Fichier : src/main/java/com/example/demo/config/MailProperties.java
@ConfigurationProperties(prefix = "mail")
public record MailProperties(String host, int port) {}

// Fichier : src/main/resources/application.yml
mail:
  host: smtp.example.com
  port: 587

Pourquoi cette approche est bonne :

  • La configuration reste centralisée.
  • Le composant externe est bien intégré au conteneur.
  • Le code métier n’a pas besoin de connaître les détails techniques de création.

6. À retenir

  • Spring Boot accélère Spring, il ne le remplace pas.
  • Les starters simplifient les dépendances.
  • L’auto-configuration dépend du classpath, des propriétés et des beans déjà définis.
  • Les profils sont essentiels pour la gestion des environnements.
  • Une bonne structure de projet réduit énormément les bugs de configuration.

7. Exercices

Débutant

Explique la différence entre Spring Framework et Spring Boot. Puis crée un contrôleur REST avec un service injecté par constructeur.

Intermédiaire

Ajoute deux profils dev et prod avec deux configurations de datasource différentes. Justifie pourquoi les secrets ne doivent pas être commités.

Avancé

Un bean custom désactive involontairement une auto-configuration utile. Décris une méthode de diagnostic et propose une correction.
