Chapitre

RabbitMQ

Messaging, exchanges, queues, Spring AMQP et comparaison avec Kafka.

1. Introduction

RabbitMQ est un broker de messages orienté files, très utilisé pour la communication asynchrone entre services, le routage précis et les workflows de traitement.

Analogie : si Kafka ressemble à un journal d’événements persistant, RabbitMQ ressemble à un centre de tri postal très flexible, capable d’orienter chaque message selon des règles.

Cas d’usage : traitement asynchrone, file d’attente métier, notifications, jobs d’arrière-plan, intégration inter-applications.

2. Niveau débutant

Concepts essentiels :

  • Queue : file de messages.
  • Exchange : point d’entrée qui route vers une ou plusieurs queues.
  • Binding : règle de liaison entre exchange et queue.
  • Routing key : clé utilisée pour le routage.

@Configuration
public class RabbitConfig {
    public static final String EXCHANGE = "order.exchange";
    public static final String QUEUE = "billing.queue";
    public static final String ROUTING_KEY = "order.created";

    @Bean
    TopicExchange exchange() { return new TopicExchange(EXCHANGE); }

    @Bean
    Queue queue() { return new Queue(QUEUE, true); }

    @Bean
    Binding binding() {
        return BindingBuilder.bind(queue()).to(exchange()).with(ROUTING_KEY);
    }
}

3. Niveau intermédiaire

Points importants en projet :

  • ack / nack pour confirmer ou refuser le traitement
  • retry pour retenter
  • TTL pour expiration
  • DLQ pour messages non traitables
@Component
@Slf4j
public class BillingConsumer {

    @RabbitListener(queues = RabbitConfig.QUEUE)
    public void consume(OrderCreatedEvent event) {
        // Traitement métier asynchrone
        log.info("Billing event received {}", event);
    }
}

Piège fréquent : oublier la stratégie d’erreur. Sans retry / DLQ, les messages échoués deviennent vite ingérables.

4. Niveau avancé

Ordering : RabbitMQ peut préserver l’ordre dans certains scénarios, mais l’ordre global devient difficile dès qu’on introduit plusieurs consommateurs concurrents ou des retries.

Performance : penser taille des messages, prefetch, stratégie d’acknowledgement, concurrence des listeners et durabilité.

Patterns :

  • Work queue
  • Publish/subscribe
  • Request/reply
  • Delayed retry via TTL + DLQ
Kafka vs RabbitMQ : pour une chaîne de traitement métier avec routage fin et sémantique de file, RabbitMQ est souvent plus naturel. Pour un historique rejouable à grande échelle, Kafka est souvent meilleur.

Recommandation senior : choisis RabbitMQ quand tu penses “distribution ciblée de messages et traitement asynchrone”, pas quand ton vrai besoin est “historique rejouable de flux d’événements”.

5. Exemples de code

// Fichier : OrderPublisher.java
@Service
@RequiredArgsConstructor
public class OrderPublisher {
    private final RabbitTemplate rabbitTemplate;

    public void publish(OrderCreatedEvent event) {
        rabbitTemplate.convertAndSend(
            RabbitConfig.EXCHANGE,
            RabbitConfig.ROUTING_KEY,
            event
        );
    }
}

6. À retenir

  • RabbitMQ excelle dans le routage flexible et la messagerie applicative.
  • Les exchanges sont au cœur du design.
  • Il faut penser ack, retry, TTL et DLQ dès le départ.
  • L’ordre devient subtil dès qu’il y a concurrence et retries.
  • Le bon choix dépend du besoin métier, pas de la mode.
