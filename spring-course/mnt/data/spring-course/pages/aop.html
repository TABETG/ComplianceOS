Chapitre

AOP

Aspects, advices, pointcuts, limites et usages réalistes.

1. Introduction

L’AOP (Aspect-Oriented Programming) sert à traiter des préoccupations transverses sans polluer le code métier : logging, audit, métriques, sécurité, traçage.

Analogie : un contrôle qualité à l’entrée d’un atelier. Tu n’ajoutes pas le contrôle dans chaque machine ; tu mets un mécanisme transversal au bon endroit.

Pourquoi c’est utile : éviter de dupliquer le même code avant/après chaque méthode.

2. Niveau débutant

Vocabulaire clé :

  • Aspect : classe qui contient la logique transverse.
  • Advice : code exécuté avant, après ou autour d’une méthode.
  • Pointcut : expression qui sélectionne les méthodes ciblées.
  • Join point : point d’exécution interceptable.
  • Weaving : application de l’aspect.
@Aspect
@Component
@Slf4j
public class LoggingAspect {

    @Before("execution(* com.example.demo.service..*(..))")
    public void logBefore(JoinPoint joinPoint) {
        log.info("Appel de la méthode {}", joinPoint.getSignature().getName());
    }
}

Piège débutant : utiliser AOP pour la logique métier. L’AOP est utile pour le transversal, pas pour remplacer le design métier.

3. Niveau intermédiaire

Les advices principaux :

AdviceMomentUsage typique
@BeforeAvant l’exécutionValidation simple, log d’entrée
@AfterAprès, succès ou échecNettoyage
@AfterReturningAprès un succèsMétriques, audit
@AfterThrowingAprès une exceptionLogs d’erreur, alerting
@AroundAvant et après, contrôle completMesure de performance, wrappers
@Around("@annotation(TrackExecutionTime)")
public Object measure(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.nanoTime();
    try {
        return pjp.proceed();
    } finally {
        long duration = System.nanoTime() - start;
        log.info("{} took {} ms", pjp.getSignature(), duration / 1_000_000);
    }
}

En projet, on combine souvent AOP avec une annotation custom pour limiter l’impact et garder un ciblage clair.

4. Niveau avancé

En Spring, l’AOP standard repose surtout sur des proxies. Cela implique une limite importante : une méthode appelée en interne depuis la même classe peut ne pas passer par le proxy, donc l’aspect peut ne pas s’appliquer.

Piège subtil : le fameux “pourquoi mon aspect ne se déclenche pas ?”. Souvent, la méthode interceptée n’est pas appelée via le bean proxy Spring mais via this.

Limites :

  • Lisibilité si les pointcuts deviennent trop larges.
  • Complexité de debug.
  • Couplage implicite si trop d’aspects sont empilés.

Recommandation senior : AOP oui, mais ciblé, documenté et réservé aux besoins transverses. Pour un comportement métier explicite, mieux vaut souvent du code lisible dans un service.

5. Exemples de code

// Fichier : AuditAspect.java
@Aspect
@Component
@RequiredArgsConstructor
public class AuditAspect {
    private final AuditService auditService;

    @AfterReturning(
        pointcut = "execution(* com.example.demo.service.OrderService.placeOrder(..))",
        returning = "result"
    )
    public void auditOrderCreation(JoinPoint joinPoint, Object result) {
        // On journalise après succès pour éviter d’auditer une opération échouée.
        auditService.record("ORDER_CREATED", joinPoint.getArgs(), result);
    }
}

6. À retenir

  • AOP sert aux préoccupations transverses.
  • @Around est puissant mais doit être utilisé avec retenue.
  • Les proxies Spring imposent des limites, notamment sur les appels internes.
  • Évite les pointcuts trop généraux.
  • Documente les aspects, sinon le comportement devient opaque.

7. Exercices

Débutant

Crée un aspect qui loggue l’entrée dans toutes les méthodes d’un package service.

Intermédiaire

Mesure le temps d’exécution des méthodes annotées @TrackExecutionTime.

Avancé

Explique pourquoi un aspect @Transactional ou custom ne s’applique pas sur un appel interne dans la même classe.
