Corrigés

Corrigés détaillés, raisonnement et erreurs fréquentes.

1. Introduction

Les corrigés ci-dessous ne donnent pas seulement la réponse. Ils expliquent le raisonnement attendu, les choix techniques valables et les erreurs fréquentes à éviter.

2. Corrigés débutant

Correction — Différence Spring Framework / Spring Boot

Spring Framework est le socle. Spring Boot facilite son usage grâce aux starters, à l’auto-configuration et aux conventions. @SpringBootApplication regroupe configuration, scan et auto-configuration.

Erreur fréquente : dire que Spring Boot est “autre chose que Spring”.

Correction — Injection par constructeur

La classe ne doit pas faire new Repository(). Elle reçoit son repository dans le constructeur. Cela rend les dépendances explicites, facilite les tests unitaires et laisse le conteneur orchestrer les objets.

Correction — Entité JPA Book

Attendu : @Entity, un identifiant, des champs simples, puis un repository Spring Data. La méthode dérivée findByTitleContainingIgnoreCase montre la puissance de Spring Data sans écrire de requête manuelle.

3. Corrigés intermédiaires

Correction — Aspect de logging

Bonne réponse : utiliser @Aspect et un pointcut ciblé sur le package service. Il faut éviter un pointcut trop global sinon on loggue aussi du technique inutile et on dégrade la lisibilité.

Correction — Placement de @Transactional

Le bon niveau est généralement le service, car il porte le use case métier complet : création commande, mise à jour stock, audit. Si l’audit doit survivre à un échec principal, on peut envisager un service séparé en REQUIRES_NEW, avec prudence.

Correction — Schéma GraphQL

On attend un type, une query et une mutation. Le data fetcher ne doit pas contenir toute la logique métier : il délègue au service. C’est un point important de maintenabilité.

Correction — Clé Kafka

La clé doit refléter le besoin d’ordre. Si l’ordre importe par commande, la clé orderId est logique. Si l’ordre importe par client, la clé customerId peut être meilleure. La bonne réponse dépend donc du métier.

4. Corrigés avancés

Correction — N+1 sur commandes

Problème : une requête principale suivie d’une requête supplémentaire pour chaque relation. Solutions attendues : join fetch, @EntityGraph, projection DTO, ou redesign de la lecture. Il fallait aussi mentionner l’impact perf et la différence entre correction rapide et solution durable.

Correction — @Transactional ignoré

Bonne explication : Spring applique souvent @Transactional via un proxy. Un appel interne this.maMethode() ne passe pas par ce proxy. Solutions possibles : déplacer la méthode dans un autre bean, revoir le découpage, ou appeler via le bean proxy avec précaution.

Correction — Kafka vs RabbitMQ

a) Notifications asynchrones métiers ciblées : RabbitMQ est souvent plus naturel grâce à ses exchanges et son routage. b) Conservation rejouable d’un flux : Kafka est souvent meilleur grâce à la rétention et au replay.

Correction — Mini architecture e-commerce

Réponse attendue : le choix dépend du front et du métier. Exemple cohérent : REST si besoins simples et stables, GraphQL si front riche à composition variable ; JPA pour la persistence relationnelle ; Kafka pour les événements de domaine rejouables ; RabbitMQ pour des traitements asynchrones ciblés. Il fallait surtout justifier chaque décision par un besoin réel.

5. À retenir

  • Un bon corrigé explique autant le “pourquoi” que le “quoi”.
  • Les arbitrages d’architecture doivent toujours être justifiés par le contexte.
  • La réponse la plus “senior” n’est pas la plus compliquée, mais la plus adaptée.
