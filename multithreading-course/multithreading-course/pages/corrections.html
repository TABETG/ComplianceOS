Corrigés détaillés

Raisonnement, correction des bugs et justification des choix techniques.

Correction 1 — Processus vs thread

Un processus est une unité d’exécution isolée avec son propre espace mémoire. Un thread est un flux d’exécution léger dans un processus, partageant sa mémoire avec les autres threads du même processus.

Correction 2 — Concurrence vs parallélisme

La concurrence concerne la progression coordonnée de plusieurs tâches. Le parallélisme désigne leur exécution réelle simultanée sur plusieurs cœurs.

Correction 3 — start() vs run()

run() est un appel normal. start() demande à la JVM de démarrer un nouveau thread qui exécutera ensuite run().

Correction 4 — GIL

Le GIL signifie qu’en CPython, un seul thread exécute du bytecode Python à la fois. Cela limite les gains du threading sur du CPU-bound, mais reste très utile pour l’I/O.

Correction 5 — Lecture de code Java

Thread t = new Thread(() -> System.out.println("hello"));
t.run();
System.out.println("done");

Ici, le lambda s’exécute dans le thread courant, pas dans un nouveau thread. Le code utilise donc un seul thread d’exécution pour ce lambda.

Correction 6 — Compteur Python

Le bug est une race condition sur counter. La correction minimale consiste à protéger l’incrément avec un Lock. Une meilleure réponse peut aussi proposer une Queue ou une réduction locale par thread selon le besoin.

import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(10000):
        with lock:
            counter += 1

threads = [threading.Thread(target=increment) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)

Correction 7 — Producteur / consommateur

La bonne solution attendue est souvent une file bloquante avec une sentinelle d’arrêt ou un protocole explicite de fin. L’intérêt est d’éviter le partage direct d’une liste mutable et d’obtenir une coordination simple.

Correction 8 — Deadlock

La correction classique est d’imposer un ordre total sur les locks : toujours prendre A puis B, jamais l’inverse.

Correction 9 — Cas d’architecture

Pour 10 000 appels HTTP, la solution synchrone est simple mais peu réactive. Un thread pool peut convenir si le débit est contrôlé. Une approche asynchrone peut être plus efficace si l’écosystème s’y prête et si l’équipe sait la maintenir. La vraie bonne réponse dépend du niveau de complexité acceptable, du besoin de débit et de l’observabilité disponible.

Correction 10 — Sizing d’un pool

  • Mesurer la nature de la charge : CPU ou I/O.
  • Observer la taille de la file et les temps de traitement.
  • Vérifier si des dépendances externes ralentissent tout le pool.
  • Regarder s’il existe de la contention interne ou des locks trop gros.

Augmenter le pool sans diagnostic peut empirer la saturation.

Correction 11 — volatile et count++

volatile garantit la visibilité, mais count++ reste une suite lecture-calcul-écriture. Deux threads peuvent toujours se marcher dessus. Il faut une opération atomique, par exemple AtomicInteger.

Erreurs fréquentes à éviter
  • Donner une réponse purement syntaxique sans parler de shared state.
  • Proposer des locks partout sans discuter le design.
  • Confondre visibilité et atomicité.
  • Oublier la stratégie d’arrêt des workers.
