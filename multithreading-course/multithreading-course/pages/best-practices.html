Bonnes pratiques d’architecture

Immutabilité, réduction du shared state, choix des abstractions et recommandations de senior.

1. Introduction

Les bonnes pratiques d’architecture en concurrence cherchent d’abord la robustesse et la lisibilité, avant la sophistication.

2. Principes fondamentaux

  • Minimiser l’état mutable partagé.
  • Privilégier l’immutabilité.
  • Découpler les responsabilités.
  • Préférer les abstractions haut niveau.
  • Documenter les garanties thread-safe.

3. Recommandations de senior / tech lead

Choisir la bonne primitive

Ne prends pas un lock “par défaut”. Demande-toi si une queue, un message, une architecture sans partage ou une future suffirait mieux.

Éviter la sur-ingénierie

Un design concurrent élégant est souvent plus simple qu’on ne l’imagine : une file bornée, quelques workers, des timeouts, des retries mesurés, des métriques.

Tester intelligemment

  • Faire des tests répétés.
  • Injecter du délai artificiel pour exposer les interleavings.
  • Tester l’arrêt propre, les timeouts et la saturation.

Documenter

Une classe devrait préciser : est-elle thread-safe ? Quelles méthodes peuvent être appelées concurremment ? Quel état est protégé par quel lock ?

4. Cas d’usage réels

  • Backend Spring Boot : pool séparé pour tâches lentes.
  • Consommateur Kafka : ne pas bloquer le thread de consommation trop longtemps.
  • Pipeline Python : queue + workers pour l’I/O, multiprocessing pour le calcul lourd.
À retenir
  • Le meilleur design concurrent est souvent celui qui partage le moins possible.
  • Préférer les abstractions haut niveau réduit fortement les bugs.
  • Documenter la thread safety fait gagner énormément de temps en équipe.
