Executors, thread pools et exécution asynchrone

Pourquoi les pools existent, sizing, saturation, backpressure et futures.

1. Introduction

Créer un thread a un coût. Répéter ce coût à chaque tâche, sans borne, est une mauvaise idée en production. Les pools permettent de réutiliser des threads et de contrôler la charge.

2. Pourquoi les pools existent

  • Réutiliser les threads au lieu de les recréer sans cesse.
  • Limiter la concurrence maximale.
  • Appliquer une file d’attente.
  • Éviter la saturation incontrôlée.
// Java
ExecutorService pool = Executors.newFixedThreadPool(8);
pool.submit(() -> System.out.println("job"));
pool.shutdown();

# Python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=8) as pool:
    future = pool.submit(lambda: "job")
    print(future.result())

3. Niveau intermédiaire

File d’attente, saturation, backpressure

Si les tâches arrivent plus vite qu’elles ne sortent, la file grossit. À partir d’un certain point, la latence explose, la mémoire monte et le système se dégrade.

Taille du pool

Il n’existe pas de taille magique universelle. Pour du CPU-bound, on reste souvent proche du nombre de cœurs. Pour de l’IO-bound, on peut aller plus haut, mais il faut mesurer.

4. Niveau avancé

ThreadPoolExecutor en Java

Le vrai ThreadPoolExecutor permet de configurer finement le cœur du pool, le maximum, la file, le keep-alive et la politique de rejet.

import java.util.concurrent.*;

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4,                      // corePoolSize
    8,                      // maximumPoolSize
    60, TimeUnit.SECONDS,   // keepAliveTime
    new ArrayBlockingQueue<>(100), // file bornée
    new ThreadPoolExecutor.CallerRunsPolicy() // stratégie de rejet
);

CompletableFuture en Java

Très utile pour composer des traitements asynchrones. Attention toutefois au choix de l’executor utilisé.

concurrent.futures en Python

API simple et propre pour récupérer des résultats, gérer erreurs et soumettre des lots de tâches.

Erreurs fréquentes

  • Pool non borné.
  • Utiliser le même pool pour des tâches très hétérogènes.
  • Bloquer longtemps un pool destiné à la réactivité.
  • Oublier les politiques d’arrêt, de timeout et de rejet.
À retenir
  • Un pool contrôle la concurrence ; il n’est pas juste un confort de syntaxe.
  • Le sizing dépend du type de charge et doit être mesuré.
  • Une file infinie masque souvent un problème jusqu’au jour où elle explose.
