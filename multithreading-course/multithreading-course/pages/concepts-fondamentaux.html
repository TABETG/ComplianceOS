Concepts fondamentaux de concurrence

Shared state, thread safety, atomicité, visibilité mémoire, ordering, contention et coordination.

1. Introduction

Les concepts fondamentaux de concurrence expliquent pourquoi des bugs subtils apparaissent même quand le code semble correct “à l’œil nu”.

Vocabulaire essentiel

  • Shared state : état partagé entre plusieurs threads.
  • Mutable state : état qui peut changer.
  • Thread safety : capacité à rester correct même avec plusieurs threads.
  • Atomicité : opération indivisible.
  • Visibilité mémoire : quand un thread voit ou non les mises à jour d’un autre.
  • Ordering : ordre garanti ou non entre les opérations.

2. Niveau débutant

Section critique

Une section critique est une partie du code qui manipule une ressource partagée et qui doit être protégée.

Race condition

Une race condition survient quand le résultat dépend de l’ordre exact d’exécution des threads.

// Java - incrément non atomique
class Counter {
    int value = 0;

    void increment() {
        value++; // lecture + calcul + écriture = plusieurs étapes
    }
}

Le value++ n’est pas atomique. Deux threads peuvent lire la même valeur, puis écrire chacun leur résultat, ce qui perd une mise à jour.

Visibilité mémoire

Un thread peut continuer à voir une ancienne valeur s’il n’existe pas de garantie de visibilité. En Java, volatile, les locks et certaines primitives concurrentes jouent un rôle clé.

3. Niveau intermédiaire

Coordination entre threads

La synchronisation ne sert pas seulement à empêcher deux threads d’entrer en même temps dans une zone sensible. Elle sert aussi à coordonner : attendre un signal, publier un état, consommer une donnée disponible.

Starvation, livelock, deadlock

  • Starvation : un thread n’obtient jamais la ressource dont il a besoin.
  • Livelock : les threads bougent, mais n’avancent pas réellement.
  • Deadlock : chaque thread attend une ressource détenue par l’autre.

4. Niveau avancé

Immutabilité et confinement

La meilleure synchronisation est souvent d’éviter le partage. Un objet immuable n’a pas besoin de lock pour être lu en sécurité. Un état confiné à un thread n’est pas exposé aux interleavings concurrents.

Idempotence

En système distribué ou dans certains pipelines concurrents, rendre une opération idempotente permet de supporter des retries ou des exécutions répétées sans corrompre l’état.

Recommandation de senior

Commence toujours par la solution la plus simple qui respecte la sûreté. La sophistication concurrente doit être justifiée par un besoin réel.

À retenir
  • La plupart des bugs concurrents viennent du shared mutable state.
  • Un design sûr cherche d’abord à réduire le partage, puis à protéger ce qui reste.
  • Comprendre visibilité, atomicité et ordering est indispensable pour lire du code concurrent sérieusement.
