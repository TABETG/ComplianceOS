Race conditions, deadlocks et bugs classiques

Exemples concrets de bugs concurrents, explications et versions corrigées.

1. Introduction

Les bugs concurrents sont difficiles à reproduire parce qu’ils dépendent souvent du timing. Le même code peut “marcher” dix fois puis échouer une onzième fois.

2. Race condition

Définition simple : le résultat dépend de l’ordre d’exécution exact des threads.

// Bug Java : lost update
class Counter {
    int value = 0;

    void increment() {
        value++; // non atomique
    }
}
Pourquoi ça bug

L’incrément n’est pas une seule opération. Deux threads peuvent lire la même ancienne valeur, puis écraser mutuellement leur résultat.

// Version corrigée
import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    AtomicInteger value = new AtomicInteger();

    void increment() {
        value.incrementAndGet();
    }
}

3. Deadlock

Chaque thread attend une ressource détenue par un autre.

// Bug Java : deadlock
class DeadlockDemo {
    private final Object lockA = new Object();
    private final Object lockB = new Object();

    void method1() {
        synchronized (lockA) {
            synchronized (lockB) {
                System.out.println("method1");
            }
        }
    }

    void method2() {
        synchronized (lockB) {
            synchronized (lockA) {
                System.out.println("method2");
            }
        }
    }
}
Méthode pour l’éviter
  • Toujours acquérir les locks dans le même ordre global.
  • Réduire le nombre de locks.
  • Utiliser tryLock quand c’est pertinent.

4. Livelock, starvation, visibility bugs

Livelock

Les threads réagissent l’un à l’autre mais n’avancent jamais.

Starvation

Un thread reste continuellement défavorisé et n’obtient jamais de ressource utile.

Visibility bug

Un thread n’observe pas un changement d’état parce qu’aucune garantie de visibilité n’a été établie.

// Bug Java : flag non volatile
class BrokenStopFlag {
    private boolean running = true;

    void stop() { running = false; }

    void work() {
        while (running) {
            // pourrait ne jamais observer le false
        }
    }
}

// Correction
class SafeStopFlag {
    private volatile boolean running = true;

    void stop() { running = false; }

    void work() {
        while (running) {
            // la mise à jour devient visible
        }
    }
}

5. Double-checked locking

Le pattern a historiquement causé des bugs s’il n’est pas correctement combiné avec volatile.

6. Recommandation pratique

Quand un bug concurrent apparaît, commence par demander : “Quel état est partagé ? Quelle garantie protège sa lecture et son écriture ?”.

À retenir
  • Race condition, deadlock et visibilité mémoire sont les trois familles les plus classiques à connaître par cœur.
  • Un bug concurrent n’est pas “aléatoire” : il révèle une garantie absente ou mal pensée.
  • Prévenir est beaucoup moins coûteux que déboguer tard.
