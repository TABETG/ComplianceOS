Introduction au multithreading

Pourquoi le multithreading existe, à quoi il sert, quand l’utiliser et quand l’éviter.

1. Introduction

Le multithreading consiste à faire avancer plusieurs flux d’exécution dans un même processus. Dit simplement, au lieu qu’un programme fasse une seule chose à la fois, il peut gérer plusieurs tâches de manière coordonnée.

Analogie : imagine un restaurant. Un processus, c’est le restaurant entier. Les threads, ce sont les serveurs qui travaillent dans le même lieu et partagent la même cuisine.

À quoi ça sert

  • Améliorer la réactivité d’une application.
  • Gérer plusieurs clients ou plusieurs tâches en parallèle apparent.
  • Mieux exploiter les ressources de la machine quand c’est pertinent.
  • Découper un traitement en workers spécialisés.

Pourquoi c’est important

Beaucoup d’applications modernes sont naturellement concurrentes : API web, consommation de messages, batchs, interfaces graphiques, scraping, traitements réseau, ETL, pipelines de données. Comprendre la concurrence n’est pas “un bonus”, c’est une compétence de solidité technique.

Erreurs fréquentes

  • Penser que “plus de threads = plus rapide”.
  • Confondre concurrence et parallélisme.
  • Utiliser des threads pour des cas où une approche synchrone simple suffit.
  • Ignorer les coûts : contention, synchronisation, mémoire, debugging.

2. Niveau débutant

Processus vs thread

Un processus possède son propre espace mémoire. Un thread partage la mémoire de son processus avec les autres threads. Cela rend la communication plus facile, mais aussi plus risquée.

NotionProcessusThread
MémoireSéparéePartagée dans le processus
Coût de créationPlus élevéPlus léger qu’un processus
CommunicationPlus coûteusePlus simple mais plus dangereuse
IsolationForteFaible
Cas courantDeux applications distinctesTravaux concurrents d’une même application

Concurrence vs parallélisme

La concurrence, c’est gérer plusieurs tâches qui progressent ensemble. Le parallélisme, c’est exécuter réellement plusieurs tâches en même temps sur plusieurs cœurs.

Une application concurrente n’est pas toujours parallèle. Sur un seul cœur, l’ordonnanceur alterne rapidement l’exécution des threads.

Exemple minimal

// Java
public class HelloThread {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            System.out.println("Travail en arrière-plan");
        });

        worker.start(); // démarre réellement un nouveau thread
        worker.join();  // attend la fin du worker
        System.out.println("Fin du programme");
    }
}

# Python
import threading

def worker():
    print("Travail en arrière-plan")

t = threading.Thread(target=worker)
t.start()
t.join()
print("Fin du programme")

Pièges de débutant

  • Appeler run() au lieu de start() en Java.
  • Partager une variable globale sans synchronisation.
  • Oublier de join() quand on a besoin d’attendre un résultat.

3. Niveau intermédiaire

Dans une vraie application, on ne crée pas un thread “à la main” pour chaque demande. On utilise souvent des pools, des files, des primitives de coordination et des abstractions plus haut niveau.

Cas réalistes

  • Backend qui traite plusieurs requêtes HTTP.
  • Consommateur Kafka ou RabbitMQ qui exécute plusieurs traitements.
  • Batch qui lit, transforme et écrit en pipeline.
  • Scraping ou appels API multiples en parallèle côté Python.

Bonnes pratiques

  • Privilégier les abstractions haut niveau plutôt que le thread manuel.
  • Documenter qui possède l’état mutable.
  • Rendre explicite la stratégie d’arrêt et d’interruption.

4. Niveau avancé

Le vrai sujet n’est pas “comment lancer plusieurs threads”, mais “comment garantir la justesse, la performance et la capacité de debug quand plusieurs threads touchent aux mêmes ressources”.

Limites

  • Contention sur les verrous.
  • Coût des context switches.
  • Bugs non déterministes.
  • Complexité mentale forte.

Cas réels d’entreprise

  • Service Java Spring Boot qui consomme des messages et met à jour une base.
  • Service Python qui fait de nombreux appels réseau concurrents.
  • Pipeline où certaines étapes sont CPU-bound, d’autres IO-bound.
À retenir
  • Le multithreading résout des problèmes de réactivité et de concurrence, pas tous les problèmes de performance.
  • Partager de la mémoire rend le design plus délicat.
  • La première compétence à acquérir est la clarté conceptuelle : processus, thread, concurrence, parallélisme, shared state.
