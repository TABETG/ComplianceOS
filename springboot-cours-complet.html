Chapitre 01 / 05

IoC & Dependency Injection

L'Inversion of Control (IoC) est le cœur de Spring. Au lieu de créer vos objets avec new, vous déclarez vos dépendances et le container Spring les injecte. C'est ce qui rend le code testable, modulaire et maintenable.

@Component @Service @Repository @Configuration ApplicationContext
Junior
Les bases — Beans et injection constructeur

Spring gère un container (ApplicationContext) qui contient tous vos objets (beans). Pour déclarer qu'un objet est un bean Spring, on utilise des annotations stéréotypes.

@Component ──▶ Bean générique
@Service ──▶ Logique métier (alias sémantique)
@Repository ──▶ Accès données (+ exception translation)
@Controller ──▶ Couche HTTP REST/MVC
@Configuration ──▶ Classe de config + @Bean factory methods
🏗️
Injection par constructeur (recommandée)
La façon moderne et testable d'injecter des dépendances
L'injection par constructeur est la méthode recommandée depuis Spring 4.3. Elle rend les dépendances explicites, permet l'immutabilité (final) et facilite les tests unitaires sans Spring.
Java AuditService.java 
@Service
public class AuditService {

    // final = immutable = thread-safe
    private final AuditRepository auditRepository;
    private final RiskScoringService riskScoringService;
    private final NotificationService notificationService;

    // Spring 3.4 : @Autowired implicite si 1 seul constructeur
    public AuditService(
            AuditRepository auditRepository,
            RiskScoringService riskScoringService,
            NotificationService notificationService) {
        this.auditRepository = auditRepository;
        this.riskScoringService = riskScoringService;
        this.notificationService = notificationService;
    }

    public Audit createAudit(CreateAuditRequest request) {
        Audit audit = Audit.builder()
                .company(request.getCompany())
                .regulation(request.getRegulation())
                .status(AuditStatus.DRAFT)
                .build();
        return auditRepository.save(audit);
    }
}

Avec Lombok, vous pouvez remplacer ce constructeur par @RequiredArgsConstructor sur la classe. Spring Boot 3.4 + Lombok = 0 boilerplate.

    private final RiskScoringService riskScoringService;

⚠️ À éviter — Injection par champ (@Autowired sur field)

Ne faites PAS @Autowired private AuditRepository repo; sur un champ. C'est plus difficile à tester (pas de moyen de l'injecter sans Spring), crée des dépendances cachées, et ne permet pas l'immutabilité.

Quand plusieurs beans implémentent la même interface
Si Spring trouve plusieurs beans du même type, il lève une NoUniqueBeanDefinitionException. @Primary désigne le bean par défaut. @Qualifier spécifie lequel injecter.

🔬
BeanPostProcessor — Intercepter la création des beans
Hook sur le cycle de vie des beans avant/après initialisation
Un BeanPostProcessor s'exécute pour chaque bean après que Spring l'a instancié. C'est ainsi que Spring implémente @Autowired, AOP, @Transactional etc. en interne.
Java TenantValidationPostProcessor.java 
@Component
public class TenantValidationPostProcessor implements BeanPostProcessor {

    /**
     * Appelé AVANT l'initialisation (@PostConstruct, afterPropertiesSet)
     * Retourne le bean (modifié ou proxy) ou null = skip
     */
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if (bean instanceof TenantAware tenantAware) {
            tenantAware.validateTenantConfig();
        }
        return bean; // toujours retourner le bean !
    }

    /**
     * Appelé APRÈS l'initialisation — idéal pour créer des proxies
     */
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // Wrapper dans un proxy de monitoring
        if (bean.getClass().isAnnotationPresent(Monitored.class)) {
            return MonitoringProxy.wrap(bean);
        }
        return bean;
    }
}

Cycle de vie complet d'un Bean

1. Instanciation ──▶ Spring appelle le constructeur
2. Injection DI ──▶ Constructeur / Setter / Field injection
3. BeanPostProcessor ──▶ postProcessBeforeInitialization()
4. @PostConstruct ──▶ Méthode d'init (vérifications, warmup)
5. afterPropertiesSet() ──▶ InitializingBean (optionnel)
6. BeanPostProcessor ──▶ postProcessAfterInitialization()
7. Bean prêt ──▶ Utilisable dans l'application
8. @PreDestroy ──▶ Nettoyage à la fermeture
Java KafkaProducerService.java — @PostConstruct / @PreDestroy 
@Service
@RequiredArgsConstructor
@Slf4j
public class KafkaProducerService {

    private final KafkaTemplate<String, AuditEvent> kafkaTemplate;
    private final SchemaRegistryClient schemaRegistry;

    @PostConstruct
    public void init() {
        // Warmup : vérifier la connexion Kafka au démarrage
        log.info("KafkaProducerService initialized — verifying connectivity...");
        schemaRegistry.verifyConnection();
    }

    @PreDestroy
    public void cleanup() {
        // Flush les messages en attente avant shutdown
        kafkaTemplate.flush();
        log.info("KafkaProducerService : all messages flushed");
    }
}

Chapitre 02 / 05

AOP — Aspect-Oriented Programming

L'AOP permet de centraliser des comportements transverses (logging, sécurité, performance, audit) sans polluer votre logique métier. Spring AOP utilise des proxies dynamiques pour intercepter les appels.

@Aspect @Before / @After @Around Pointcut expressions Custom annotations
Junior
Concepts AOP — Aspect, Advice, Pointcut, JoinPoint
Aspect ──▶ La classe qui contient les comportements transverses
Advice ──▶ Le code qui s'exécute (@Before, @After, @Around...)
Pointcut ──▶ L'expression qui sélectionne où appliquer l'aspect
JoinPoint ──▶ Le point d'exécution (appel de méthode + args + target)
Weaving ──▶ Comment Spring applique l'aspect (proxy à l'exécution)
📝
Premier Aspect — Logging automatique
Loguer l'entrée et la sortie de toutes les méthodes de service
Java LoggingAspect.java 
@Aspect
@Component
@Slf4j
public class LoggingAspect {

    /**
     * Pointcut : toutes les méthodes publiques des classes @Service
     * execution([modificateur] [type-retour] [classe].[méthode]([args]))
     */
    @Pointcut("within(@org.springframework.stereotype.Service *)")
    public void serviceLayer() {}

    @Before("serviceLayer()")
    public void logBefore(JoinPoint joinPoint) {
        log.debug("→ {}.{}({})",
                joinPoint.getTarget().getClass().getSimpleName(),
                joinPoint.getSignature().getName(),
                Arrays.toString(joinPoint.getArgs()));
    }

    @AfterReturning(pointcut = "serviceLayer()", returning = "result")
    public void logAfter(JoinPoint joinPoint, Object result) {
        log.debug("← {}.{} returned: {}",
                joinPoint.getTarget().getClass().getSimpleName(),
                joinPoint.getSignature().getName(),
                result);
    }

    @AfterThrowing(pointcut = "serviceLayer()", throwing = "ex")
    public void logException(JoinPoint joinPoint, Exception ex) {
        log.error("✗ {}.{} threw: {}",
                joinPoint.getTarget().getClass().getSimpleName(),
                joinPoint.getSignature().getName(),
                ex.getMessage());
    }
}
Intermédiaire
@Around — Mesure de performance avec OpenTelemetry
⏱️
@Around — Contrôle total du flux d'exécution
L'advice le plus puissant : peut modifier les args, le résultat, ou bloquer l'appel
@Around enveloppe complètement la méthode. Vous devez appeler proceedingJoinPoint.proceed() pour exécuter la méthode originale. C'est la base de @Transactional et @Cacheable.
Java PerformanceAspect.java — ComplianceOS 
@Aspect
@Component
@RequiredArgsConstructor
public class PerformanceAspect {

    private final MeterRegistry meterRegistry; // Micrometer → Grafana Mimir

    @Around("@annotation(com.complianceos.annotation.Monitored)")
    public Object measurePerformance(ProceedingJoinPoint pjp) throws Throwable {
        String className  = pjp.getTarget().getClass().getSimpleName();
        String methodName = pjp.getSignature().getName();

        Timer.Sample sample = Timer.start(meterRegistry);

        try {
            Object result = pjp.proceed(); // ← appel de la vraie méthode

            sample.stop(Timer.builder("method.execution")
                    .tag("class", className)
                    .tag("method", methodName)
                    .tag("outcome", "success")
                    .register(meterRegistry));

            return result;

        } catch (Throwable ex) {
            sample.stop(Timer.builder("method.execution")
                    .tag("class", className)
                    .tag("method", methodName)
                    .tag("outcome", "error")
                    .register(meterRegistry));
            throw ex; // toujours re-lancer !
        }
    }
}

Annotations custom + Audit Trail automatique
🏷️
@AuditLog — Annotation custom pour l'audit trail DORA
Créer une annotation + aspect pour logger automatiquement dans TimescaleDB
DORA et NIS2 exigent un audit trail complet de toutes les actions. Plutôt que d'appeler manuellement auditTrailService.log(...) partout, on crée une annotation @AuditLog qui déclenche automatiquement l'enregistrement via AOP.
Java AuditLog.java — annotation custom 
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    AuditAction action();
    String resource();
    boolean logResult() default false;
}

public enum AuditAction {
    CREATE, READ, UPDATE, DELETE, EXPORT, SIGN, LOGIN
}

// Utilisation sur les méthodes de service
@Service
public class AuditService {

    @AuditLog(action = AuditAction.CREATE, resource = "AUDIT")
    public Audit createAudit(CreateAuditRequest request) { ... }

    @AuditLog(action = AuditAction.EXPORT, resource = "REPORT", logResult = true)
    public byte[] exportReport(UUID auditId) { ... }
}
Java AuditTrailAspect.java — TimescaleDB logging 
@Aspect
@Component
@RequiredArgsConstructor
@Slf4j
public class AuditTrailAspect {

    private final AuditTrailRepository trailRepository;
    private final TenantContext tenantContext;
    private final SecurityContextHolder securityContext;

    @Around("@annotation(auditLog)")
    public Object trailAction(ProceedingJoinPoint pjp, AuditLog auditLog)
            throws Throwable {

        UUID eventId = UUID.randomUUID();
        Instant start = Instant.now();

        try {
            Object result = pjp.proceed();

            // Enregistrement asynchrone dans TimescaleDB
            trailRepository.saveAsync(AuditTrailEntry.builder()
                    .eventId(eventId)
                    .tenantId(tenantContext.getTenantId())
                    .userId(getCurrentUserId())
                    .action(auditLog.action().name())
                    .resourceType(auditLog.resource())
                    .newValue(auditLog.logResult() ? toJson(result) : null)
                    .timestamp(start)
                    .ipAddress(getCurrentIp())
                    .build());

            return result;

        } catch (Throwable ex) {
            // Logger aussi les erreurs dans l'audit trail
            trailRepository.saveFailureAsync(eventId, ex.getMessage());
            throw ex;
        }
    }
}
⚠️
Limitation Spring AOP : Spring AOP ne fonctionne que sur des appels inter-beans (bean A appelle bean B). Si une méthode d'un bean s'appelle elle-même (this.autreMethode()), l'aspect ne s'applique pas. Solution : injecter le bean lui-même via @Lazy, ou utiliser AspectJ weaving (compile-time).

@Transactional

@Transactional est implémenté via AOP. Maîtriser ses pièges — self-invocation, propagation, isolation — est essentiel pour éviter les bugs de données en production.

Propagation Isolation rollbackFor Transactions imbriquées
Junior
Usage de base — ACID et rollback automatique
🔄
@Transactional — Comportement par défaut
Ce que Spring fait automatiquement pour vous
@Transactional sans paramètres utilise : propagation REQUIRED, isolation DEFAULT (celle de la BDD), rollback sur RuntimeException uniquement, timeout = -1 (infini), readOnly = false.
Java AuditService.java 
@Service
@RequiredArgsConstructor
@Transactional // Toutes les méthodes publiques sont transactionnelles par défaut
public class AuditService {

    private final AuditRepository auditRepo;
    private final EvidenceRepository evidenceRepo;
    private final KafkaProducerService kafkaProducer;

    /**
     * Si une exception survient n'importe où → tout est rollbacké.
     * Audit + Evidence = atomique.
     */
    public Audit submitAuditWithEvidence(SubmitAuditRequest req) {
        Audit audit = auditRepo.save(buildAudit(req)); // INSERT audit

        req.getEvidences().forEach(e ->
            evidenceRepo.save(buildEvidence(e, audit)) // INSERT evidence
        );

        // Si Kafka échoue → le save audit ET evidence sont rollbackés
        kafkaProducer.publishAuditStarted(audit);

        return audit;
    }

    // READ-ONLY → pas de dirty checking Hibernate → +30% perf
    @Transactional(readOnly = true)
    public List<Audit> findByTenant(UUID tenantId) {
        return auditRepo.findByTenantId(tenantId);
    }
}
💡
Mettez @Transactional(readOnly = true) sur toutes vos méthodes de lecture. Hibernate désactive le dirty checking (pas de tracking des modifications), ce qui améliore significativement les performances.

Propagation & Isolation — Les 7 niveaux expliqués

Niveaux de Propagation

Propagation Comportement si TX existante Comportement si aucune TX Usage
REQUIRED ★ Réutilise la TX existante Crée une nouvelle TX Par défaut — 95% des cas
REQUIRES_NEW Suspend la TX, crée une nouvelle Crée une nouvelle TX Audit trail (doit persister même si TX parent rollback)
NESTED Crée un savepoint dans la TX Comme REQUIRED Import batch : rollback partiel sans annuler tout
SUPPORTS Réutilise la TX S'exécute sans TX Méthodes qui marchent avec ou sans TX
NOT_SUPPORTED Suspend la TX S'exécute sans TX Opérations non-transactionnelles (appels HTTP externes)
MANDATORY Réutilise la TX Exception ! Méthodes qui DOIVENT être dans une TX
NEVER Exception ! S'exécute sans TX Méthodes qui ne doivent JAMAIS être dans une TX
💾
REQUIRES_NEW — Audit Trail dans ComplianceOS
L'audit trail doit être sauvegardé même si la transaction principale échoue
Java AuditTrailService.java 
@Service
@RequiredArgsConstructor
public class AuditTrailService {

    private final AuditTrailRepository trailRepo;

    /**
     * REQUIRES_NEW : S'exécute dans sa PROPRE transaction.
     * Même si AuditService.createAudit() fait un rollback,
     * cette entrée est TOUJOURS committée en base (DORA compliance).
     */
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAction(AuditTrailEntry entry) {
        trailRepo.save(entry);
    }
}

// Dans AuditService — le trail persiste même en cas d'erreur
@Service
public class AuditService {
    private final AuditTrailService trailService; // bean séparé !

    @Transactional
    public Audit processAudit(UUID auditId) {
        trailService.logAction(buildEntry()); // REQUIRES_NEW = TX séparée

        if (someCondition) {
            throw new BusinessException("..."); // TX principale rollback
            // Mais le trail est déjà committé dans TimescaleDB !
        }
        return audit;
    }
}

Isolation Problèmes évités Performance Usage
READ_UNCOMMITTED Aucun ⚡⚡⚡ Jamais en prod (dirty reads)

Pièges critiques & TransactionTemplate
🔴 Piège 1 — Self-invocation (le bug le plus courant)

Spring AOP crée un proxy autour de votre bean. Si une méthode du bean appelle une autre méthode du même bean via this, elle bypass le proxy → @Transactional est ignoré !

Java ❌ Self-invocation — Bug silencieux 
@Service
public class AuditService {

    public void processAll() {
        this.processOne(); // ← bypasse le proxy ! @Transactional ignoré !
    }

    @Transactional
    public void processOne() {
        // Cette TX ne démarre PAS si appelée via this
    }
}
Java ✅ Solution — Séparer en deux beans ou ApplicationContext 
// Solution 1 : Séparer en deux services
@Service
public class AuditBatchService {
    private final AuditService auditService; // bean séparé = proxy actif

    public void processAll() {
        auditService.processOne(); // ← passe par le proxy ✓
    }
}

// Solution 2 : @Lazy self-injection
@Service
public class AuditService {

    @Autowired @Lazy
    private AuditService self; // le proxy de soi-même

    public void processAll() {
        self.processOne(); // ← passe par le proxy ✓
    }

    @Transactional
    public void processOne() { ... }
}
🔴 Piège 2 — @Transactional sur méthodes private/protected

Spring AOP ne peut pas proxier les méthodes non-publiques. @Transactional sur une méthode private est silencieusement ignoré. Toujours mettre @Transactional sur des méthodes public.

🛠️
TransactionTemplate — Transactions programmatiques
Contrôle fin sur les limites de transaction dans du code complexe
Java ImportBatchService.java — Transactions imbriquées 
@Service
@RequiredArgsConstructor
public class ImportBatchService {

    private final TransactionTemplate txTemplate;
    private final ComplianceDataRepository dataRepo;

    /**
     * Import de 100 000 lignes CSV.
     * Chaque batch de 1000 lignes dans sa propre TX.
     * Si une TX échoue, les autres sont committées (NESTED behavior).
     */
    public ImportResult importComplianceData(List<ComplianceRow> rows) {
        var result = new ImportResult();

        Lists.partition(rows, 1000).forEach(batch -> {
            try {
                txTemplate.executeWithoutResult(status -> {
                    var valid = batch.stream()
                            .filter(this::isValid)
                            .toList();

                    dataRepo.saveAll(valid);
                    result.addProcessed(valid.size());

                    if (valid.size() < batch.size() * 0.5) {
                        // Rollback ce batch si plus de 50% invalide
                        status.setRollbackOnly();
                        result.addFailedBatch();
                    }
                });
            } catch (Exception e) {
                result.addError(e.getMessage());
                // continue les autres batches
            }
        });

        return result;
    }
}

Dans ComplianceOS, CO-09 (Pipeline ETL Polars) utilise ce pattern : chaque batch de 1000 lignes CSV est importé dans sa propre transaction, avec rapport d'erreurs détaillé sur les lignes invalides.

@Entity
@Table(name = "audits", indexes = {
    @Index(name = "idx_audit_tenant", columnList = "tenant_id"),
    @Index(name = "idx_audit_status", columnList = "status, tenant_id")
})
@Getter @Setter @Builder @NoArgsConstructor @AllArgsConstructor
@EntityListeners(AuditingEntityListener.class) // @CreatedDate, @LastModifiedDate
public class Audit {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Column(name = "tenant_id", nullable = false)
    private UUID tenantId;

    @Column(nullable = false)
    @Enumerated(EnumType.STRING)
    private AuditStatus status;

    @Column(nullable = false)
    @Enumerated(EnumType.STRING)
    private Regulation regulation; // NIS2, DORA, RGPD

    @Column(name = "risk_score")
    private BigDecimal riskScore;

    // Relations (voir section intermédiaire)
    @OneToMany(mappedBy = "audit", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Evidence> evidences = new ArrayList<>();

    @CreatedDate
    @Column(name = "created_at", updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    @Column(name = "updated_at")
    private Instant updatedAt;

    @Version // Optimistic locking
    private Long version;

    // Helper method pour les relations bidirectionnelles
    public void addEvidence(Evidence evidence) {
        evidences.add(evidence);
        evidence.setAudit(this);
    }
}

    Page<Audit> findByFilters(
            @Param("tenantId") UUID tenantId,

            @Param("from") Instant from,

Le problème N+1 — La bête noire des devs JPA
Comprendre et résoudre le problème de performance le plus courant avec Hibernate
Le problème N+1 : vous chargez N entités, et pour chacune Hibernate exécute 1 requête supplémentaire pour charger une relation. Résultat : 1 + N requêtes au lieu de 1 seule avec un JOIN.
Java ❌ N+1 Problem — 1 + N requêtes SQL 
// Audit.java — relation LAZY par défaut
@OneToMany(mappedBy = "audit", fetch = FetchType.LAZY)
private List<Evidence> evidences; // chargé à la demande

// Service — PROBLÈME !
public List<AuditDTO> getAuditsWithEvidences(UUID tenantId) {
    var audits = auditRepo.findByTenantId(tenantId); // Requête 1 : SELECT * FROM audits

    return audits.stream().map(audit -> {
        // Requête 2,3,4...N : SELECT * FROM evidences WHERE audit_id = ?
        // Exécutée pour CHAQUE audit !
        int count = audit.getEvidences().size();
        return new AuditDTO(audit, count);
    }).toList();
}
// Si 100 audits → 1 + 100 = 101 requêtes SQL !

@Transactional
public Audit approveAudit(UUID auditId) {
    try {
        Audit audit = auditRepo.findById(auditId).orElseThrow();
        audit.setStatus(AuditStatus.APPROVED);
        return auditRepo.save(audit);
        // Si un autre thread a modifié l'audit pendant ce temps →
        // OptimisticLockingFailureException lancée automatiquement
    } catch (OptimisticLockingFailureException e) {
        throw new ConcurrentModificationException(
            "Audit modifié par un autre utilisateur. Rafraîchissez et réessayez.");
    }
}

JPA Specifications — Filtres dynamiques

Java AuditSpecifications.java — Filtres GraphQL dynamiques 
public class AuditSpecifications {

    public static Specification<Audit> forTenant(UUID tenantId) {
        return (root, query, cb) ->
                cb.equal(root.get("tenantId"), tenantId);
    }

    public static Specification<Audit> hasStatus(AuditStatus status) {
        return (root, query, cb) ->
                status == null ? cb.conjunction() // no filter
                        : cb.equal(root.get("status"), status);
    }

    public static Specification<Audit> forRegulation(Regulation reg) {
        return (root, query, cb) ->
                reg == null ? cb.conjunction()
                        : cb.equal(root.get("regulation"), reg);
    }

    public static Specification<Audit> createdAfter(Instant date) {
        return (root, query, cb) ->
                date == null ? cb.conjunction()
                        : cb.greaterThanOrEqualTo(root.get("createdAt"), date);
    }
}

// Utilisation — composition dynamique avec JpaSpecificationExecutor
public Page<Audit> searchAudits(AuditFilter filter, Pageable pageable) {
    Specification<Audit> spec = Specification
            .where(forTenant(tenantContext.getTenantId()))
            .and(hasStatus(filter.getStatus()))
            .and(forRegulation(filter.getRegulation()))
            .and(createdAfter(filter.getFrom()));

    return auditRepo.findAll(spec, pageable);
}

DataLoader — Résoudre le N+1 GraphQL
🚀
DataLoader — Batching et caching automatiques
La solution GraphQL au problème N+1 : grouper les requêtes en un seul batch
Sans DataLoader : si on charge 10 audits, GraphQL appellera le resolver evidences 10 fois = 10 requêtes SQL. Avec DataLoader : les 10 appels sont batchés en 1 seule requête SQL WHERE audit_id IN (...).
Java EvidenceDataLoader.java 
@DgsDataLoader(name = "evidencesByAuditId", caching = true)
public class EvidenceDataLoader
        implements BatchLoader<UUID, List<Evidence>> {

    private final EvidenceRepository evidenceRepo;

    /**
     * DGS appelle cette méthode UNE FOIS avec TOUTES les clés.
     * Au lieu de N requêtes "WHERE audit_id = ?" →
     * 1 seule requête "WHERE audit_id IN (?, ?, ?, ...)"
     */
    @Override
    public CompletionStage<List<List<Evidence>>> load(List<UUID> auditIds) {
        return CompletableFuture.supplyAsync(() -> {
            // 1 requête pour TOUS les auditIds
            var allEvidences = evidenceRepo.findByAuditIdIn(auditIds);

            // Grouper par auditId pour renvoyer dans le bon ordre
            var byAuditId = allEvidences.stream()
                    .collect(Collectors.groupingBy(e -> e.getAudit().getId()));

            // Retourner dans le même ordre que auditIds (requis par DataLoader)
            return auditIds.stream()
                    .map(id -> byAuditId.getOrDefault(id, List.of()))
                    .toList();
        });
    }
}

// Dans AuditDataFetcher — utilisation du DataLoader
@DgsData(parentType = "Audit", field = "evidences")
public CompletableFuture<List<Evidence>> evidences(
        DgsDataFetchingEnvironment env) {

    Audit audit = env.getSource();
    DataLoader<UUID, List<Evidence>> loader =
            env.getDataLoader("evidencesByAuditId");

    return loader.load(audit.getId()); // batché automatiquement
}

@DgsComponent
@RequiredArgsConstructor
public class AuditSubscriptionFetcher {

    private final AuditEventPublisher eventPublisher;

    @DgsSubscription
    public Publisher<Audit> auditStatusChanged(@InputArgument UUID auditId) {
        return eventPublisher
                .getAuditStatusStream() // Flux<AuditStatusEvent>
                .filter(event -> event.getAuditId().equals(auditId))
                .map(AuditStatusEvent::getAudit);
    }
}

// Publisher alimenté depuis Kafka consumer
@Service
public class AuditEventPublisher {

    private final Sinks.Many<AuditStatusEvent> sink =
            Sinks.many().multicast().onBackpressureBuffer();

    // Appelé par le Kafka consumer
    public void publishStatusChange(AuditStatusEvent event) {
        sink.tryEmitNext(event);
    }

    public Flux<AuditStatusEvent> getAuditStatusStream() {
        return sink.asFlux();
    }
}

@Component
public class TracingInstrumentation extends SimpleInstrumentation {

    @Override
    public InstrumentationContext<ExecutionResult> beginExecution(
            InstrumentationExecutionParameters params,
            InstrumentationState state) {

        var operationName = params.getOperation();
        var span = Span.current();
        span.setAttribute("graphql.operation", operationName);

        return SimpleInstrumentationContext.whenCompleted((result, ex) -> {
            if (result.getErrors().isEmpty()) {
                span.setAttribute("graphql.status", "success");
            } else {
                span.setAttribute("graphql.errors", result.getErrors().size());
                span.setStatus(StatusCode.ERROR);
            }
        });
    }
}

Cheat Sheet — Spring Boot 3.4

🏗️ IoC / DI — Résumé
  • Toujours injection par constructeur (pas @Autowired sur field)
  • @RequiredArgsConstructor Lombok = 0 boilerplate
  • Utiliser @Primary + @Qualifier si plusieurs implémentations
  • @Profile pour beans env-spécifiques (dev/prod/test)
  • @ConditionalOnProperty pour feature flags
  • @PostConstruct pour warmup, @PreDestroy pour cleanup
🎯 AOP — Résumé
  • @Before = avant l'appel, @After = toujours après
  • @Around = contrôle total, doit appeler proceed()
  • @AfterReturning = succès, @AfterThrowing = exception
  • Spring AOP = proxies = méthodes publiques inter-beans seulement
  • Self-invocation bypass le proxy → séparer en 2 beans
  • Annotations custom + @Around("@annotation(ann)") = pattern puissant
🔄 @Transactional — Résumé
  • readOnly = true sur toutes les lectures
  • REQUIRES_NEW pour audit trail (indépendant du rollback)
  • Rollback automatique sur RuntimeException uniquement
  • Marquer rollbackFor = Exception.class si checked exceptions
  • Self-invocation = même piège qu'AOP
  • TransactionTemplate pour contrôle programmatique fin
📦 JPA — Résumé
  • @Version sur toutes les entités = optimistic locking
  • Relations LAZY par défaut = pas de chargement non voulu
  • N+1 → @EntityGraph ou JOIN FETCH explicite
  • DTO projections pour les vues en lecture (plus performant)
  • Specification<T> pour filtres dynamiques (GraphQL, REST)
  • @Modifying obligatoire pour UPDATE/DELETE en JPQL
📡 GraphQL DGS — Résumé
  • Schema-first : .graphqls dans resources/schema/
  • @DgsComponent + @DgsQuery/@DgsMutation
  • @DgsData(parentType, field) pour résoudre les relations
  • @DgsDataLoader obligatoire dès qu'on résout une relation
  • @PreAuthorize sur mutations sensibles
  • Introspection désactivée en production (sécurité)
