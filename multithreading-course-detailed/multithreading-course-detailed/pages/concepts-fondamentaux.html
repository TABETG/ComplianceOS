Concepts fondamentaux de concurrence

Atomicité, visibilité, ordering, état partagé et notions qui expliquent les vrais bugs concurrents.

1. Introduction

Les notions fondamentales de concurrence sont celles qui expliquent pourquoi du code “semble correct” mais casse en production. En multithreading, deux dangers reviennent sans cesse : l’état partagé mutable et l’absence de garanties d’ordre ou de visibilité.

Shared state et mutable state

Un état partagé est une donnée accessible par plusieurs threads. Si cet état peut changer, on parle d’état mutable partagé. C’est la source de la majorité des races, lost updates et corruptions.

2. Niveau débutant

Atomicité

Une opération atomique est indivisible : aucun autre thread ne peut observer un état intermédiaire. Un simple counter++ n’est pas atomique : lecture, calcul, écriture.

Visibilité mémoire

Quand un thread modifie une variable, un autre thread ne verra pas toujours immédiatement la nouvelle valeur sans mécanisme de synchronisation adapté.

Ordering

Le compilateur, le runtime et le CPU peuvent réordonner certaines instructions tant que le résultat reste correct pour un thread isolé. En concurrence, cela peut casser les hypothèses naïves.

class SharedFlag {
    boolean running = true;
}

class Worker implements Runnable {
    private final SharedFlag flag;

    Worker(SharedFlag flag) {
        this.flag = flag;
    }

    @Override
    public void run() {
        while (flag.running) {
            // boucle
        }
        System.out.println("Arrêt");
    }
}

Ce code paraît innocent. Pourtant, sans volatile ou synchronisation, le worker peut ne jamais voir le changement de running.

3. Niveau intermédiaire

Section critique

Une section critique est une zone où un accès concurrent non contrôlé est dangereux. On la protège avec un verrou ou on évite le partage.

Contention

La contention apparaît quand plusieurs threads se disputent la même ressource : verrou, CPU, connexion, file, disque. Une application peut être “thread-safe” mais lente à cause d’une contention excessive.

Starvation

Un thread est affamé quand il ne progresse presque jamais parce que d’autres accaparent CPU ou verrou.

Livelock

Deux threads ne sont pas bloqués, mais ils réagissent l’un à l’autre d’une façon qui empêche tout progrès utile. Ils “bougent” sans avancer.

4. Niveau avancé

Monitor, wait et notify

En Java, chaque objet peut servir de moniteur. Un thread peut entrer dans un bloc synchronized, attendre via wait(), puis être réveillé par notify() ou notifyAll(). C’est puissant mais bas niveau.

Immutabilité

L’immutabilité est souvent l’arme la plus simple : si un objet ne change jamais après construction, plusieurs threads peuvent le lire sans coordination particulière.

Confinement

Le confinement consiste à limiter une donnée à un seul thread ou à un seul contexte. Une donnée non partagée est naturellement plus sûre.

Idempotence

Dans les systèmes concurrents distribués, l’idempotence réduit le risque de double traitement. Si rejouer une opération produit le même effet, la robustesse augmente.

5. Exemples clairs

Bug de lost update

import threading

counter = 0

def increment():
    global counter
    for _ in range(100000):
        counter += 1  # lecture + calcul + écriture

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)

Le résultat peut être inférieur à 200000. C’est une race condition. Même si le GIL existe, les garanties ne remplacent pas une vraie conception thread-safe pour toutes les opérations partagées.

Pièges fréquents

  • Le GIL n’est pas un passe-droit pour ignorer la synchronisation logique.
  • Une variable partagée simple peut déjà suffire à introduire un bug.
  • Un bug concurrent peut ne se produire qu’une fois sur mille.
