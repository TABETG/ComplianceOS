Executors, thread pools et exécution asynchrone

Pertes de performance, dimensionnement, saturation, backpressure et usage propre des executors.

1. Pourquoi les thread pools existent

Créer un thread a un coût : allocation mémoire, enregistrement auprès de l’OS, context switching, supervision difficile. Les pools réutilisent des threads existants pour traiter plusieurs tâches sans recréer constamment des threads.

2. Java ExecutorService

ExecutorService pool = new ThreadPoolExecutor(
    8,                 // core threads
    16,                // max threads
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000)
);

Points clés

  • corePoolSize : taille de base.
  • maximumPoolSize : limite haute.
  • queue : file d’attente.
  • rejectedExecutionHandler : comportement en saturation.

Erreurs fréquentes

  • Queue infinie masquant la saturation.
  • Pool minuscule pour tâches bloquantes I/O.
  • Pool gigantesque causant contention et mémoire inutile.

3. Python ThreadPoolExecutor

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=16) as pool:
    futures = [pool.submit(fetch_url, url) for url in urls]
    for future in as_completed(futures):
        print(future.result())

Très utile pour des appels I/O parallélisés simplement.

4. Backpressure et saturation

Quand les producteurs créent plus vite que les consommateurs ne traitent, le système doit ralentir, rejeter ou bufferiser. Sans stratégie de backpressure, la mémoire explose ou la latence dérive.

ProblèmeSymptômeRemède
Pool saturéTemps de réponse qui monteLimiter la production, augmenter les consumers, gérer la file.
Queue trop grandeMémoire élevée, latence cachéeCapacité bornée, alerting, rejet contrôlé.
Tâches bloquantes dans petit poolBlocage globalPool dédié par type de charge.

5. Taille optimale d’un pool

Il n’existe pas de taille universelle. Le sizing dépend de la nature des tâches :

  • CPU-bound : proche du nombre de cœurs, avec ajustements selon contention.
  • I/O-bound : souvent plus grand, car beaucoup de temps est passé à attendre.

La vraie bonne réponse vient des métriques : temps d’exécution, attente, saturation, files, CPU, latence.

6. CompletableFuture et futur composable

En Java, CompletableFuture permet de chaîner des traitements asynchrones. En Python, concurrent.futures reste plus simple mais moins fluide pour les graphes complexes.

À retenir

  • Les pools servent à contrôler la concurrence, pas seulement à l’accélérer.
  • Un pool doit être pensé avec sa file d’attente et sa stratégie de saturation.
  • Le mauvais pool au mauvais endroit peut plomber toute l’application.
