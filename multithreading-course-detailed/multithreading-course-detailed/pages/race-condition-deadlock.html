Race conditions, deadlocks et bugs classiques

Comprendre les grands bugs concurrents, les reconnaître et savoir les éviter proprement.

1. Race condition

Une race condition survient quand le résultat dépend de l’ordre d’exécution entre plusieurs threads. Si cet ordre n’est pas maîtrisé, le résultat devient imprévisible.

class Counter {
    int value = 0;

    void increment() {
        value++; // non thread-safe
    }
}

Correction : synchroniser, utiliser une primitive atomique ou supprimer l’état partagé.

2. Deadlock

Un deadlock survient quand deux threads attendent chacun une ressource détenue par l’autre. Plus personne n’avance.

synchronized (lockA) {
    synchronized (lockB) {
        // ...
    }
}

// ailleurs
synchronized (lockB) {
    synchronized (lockA) {
        // ...
    }
}

Évitement : ordre global de prise des verrous, timeout, design sans double verrou si possible.

3. Livelock et starvation

Dans un livelock, les threads réagissent mais ne progressent pas. Dans la starvation, un thread progresse trop peu car d’autres monopolisent la ressource.

4. Visibility bug

class StopFlag {
    boolean stop = false;
}

Un thread écrit stop = true, un autre continue de lire false. Correction : volatile, lock ou autre relation happens-before.

5. Lost update

Deux threads lisent la même valeur, la modifient chacun de leur côté, puis écrivent successivement. L’une des mises à jour est perdue.

6. Double-checked locking

Ce pattern est historiquement piégeux quand il est mal implémenté. En Java moderne, il demande généralement un champ volatile si on l’utilise pour une initialisation paresseuse manuelle.

private static volatile ExpensiveService instance;

public static ExpensiveService getInstance() {
    if (instance == null) {
        synchronized (MyClass.class) {
            if (instance == null) {
                instance = new ExpensiveService();
            }
        }
    }
    return instance;
}

7. Interleavings et ordre d’exécution

Un même code peut produire différentes traces légales selon l’interleaving. C’est la raison pour laquelle un bug concurrent peut être rarissime et pourtant grave.

Pièges fréquents

  • Tester dix fois sans erreur ne prouve pas qu’un code concurrent est correct.
  • Un deadlock peut ne se produire que sous forte charge.
  • Les logs non horodatés et non corrélés rendent le diagnostic presque impossible.

À retenir

  • Un bug concurrent est souvent un bug de protocole entre threads.
  • Les solutions les plus fiables diminuent le partage mutable.
  • Les files, atomiques et structures concurrentes haut niveau évitent beaucoup de bugs.
