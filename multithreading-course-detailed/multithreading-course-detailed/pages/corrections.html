Corrigés détaillés

Corrigés expliqués, raisonnés et orientés bonnes pratiques de projet.

1. Correction — processus vs thread

Un processus est une instance d’application isolée avec son propre espace mémoire. Un thread est une unité d’exécution à l’intérieur d’un processus. Les threads partagent beaucoup de ressources, ce qui facilite la communication mais augmente le risque de bugs de concurrence.

2. Correction — start() vs run()

start() demande à la JVM de créer un nouveau thread d’exécution qui appellera ensuite run(). Appeler run() directement exécute simplement la méthode dans le thread courant, sans concurrence réelle.

3. Correction — GIL et threading Python

Le threading Python est particulièrement utile pour les tâches I/O-bound : appels HTTP, accès fichiers, attente réseau, scraping, sockets, appels à des services externes. Le GIL limite surtout le parallélisme CPU pur du bytecode Python.

4. Correction — Counter Java non thread-safe

Le code n’est pas thread-safe parce que value++ n’est pas atomique. Deux corrections classiques :

  • utiliser synchronized,
  • remplacer par AtomicInteger.
class SafeCounter {
    private final AtomicInteger value = new AtomicInteger(0);

    public void increment() {
        value.incrementAndGet();
    }

    public int getValue() {
        return value.get();
    }
}

Ici, le choix d’AtomicInteger est bon car le besoin est un compteur simple. Pour des invariants plus complexes, un lock peut devenir nécessaire.

5. Correction — diagnostic d’un blocage Java

  1. Récupérer métriques de saturation : latence, taille des queues, taux d’occupation des pools.
  2. Prendre un thread dump au moment du problème.
  3. Identifier threads BLOCKED / WAITING / TIMED_WAITING.
  4. Vérifier ordre de prise des verrous et ressources externes lentes.
  5. Corréler avec logs applicatifs et timeouts.

Erreur fréquente : regarder seulement le CPU alors que le vrai problème est un lock ou une file saturée.

6. Correction — deadlock

Problème : ordre incohérent d’acquisition des verrous. Correction simple : imposer un ordre global, par exemple toujours lockA puis lockB. Correction architecturale meilleure : éviter d’avoir besoin de deux verrous imbriqués ou passer par un acteur/queue centralisée.

7. Correction — producteur / consommateur

from queue import Queue
from threading import Thread

queue = Queue(maxsize=100)
SENTINEL = object()

def producer():
    for i in range(10):
        queue.put(i)
    queue.put(SENTINEL)

def consumer():
    while True:
        item = queue.get()
        try:
            if item is SENTINEL:
                queue.put(SENTINEL)
                break
            print("Processing", item)
        finally:
            queue.task_done()

Thread(target=producer).start()
Thread(target=consumer).start()
Thread(target=consumer).start()

Le point important ici est le protocole de fin. Sans sentinelle ou signal clair, les consumers peuvent attendre indéfiniment.

8. Correction — mini architecture

Dans le cas des fichiers envoyés à une API externe lente, le cœur du problème est I/O-bound. Une bonne solution serait :

  • pool de threads borné pour les appels externes,
  • queue interne bornée pour lisser la charge,
  • timeouts + retries contrôlés,
  • séparation du calcul léger et du stockage en base,
  • observabilité sur backlog, erreurs et saturation.

Je n’irais pas vers multiprocessing, car le calcul décrit est léger. L’async peut être pertinent si l’architecture entière est pensée pour cela, mais un pool I/O bien borné est souvent plus simple et plus maintenable.

À retenir

  • Une bonne correction concurrente traite le protocole, pas seulement la syntaxe.
  • Préférer les abstractions métier sûres comme les queues et pools bornés.
  • Le bon choix dépend toujours de la nature de la charge : CPU, I/O, latence, volumétrie.
