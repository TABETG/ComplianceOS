Python — Concurrency avancée

Locks, events, queues, pools, multiprocessing et choix de stratégie en Python.

1. Synchronisation avancée

Primitive PythonUsageRemarque

RLockVerrou réentrantLe même thread peut reprendre le lock.
SemaphoreLimiter le nombre d’accèsTrès utile pour limiter des appels externes.

QueueTransfert thread-safe de donnéesSouvent meilleur choix pour pipeline.
from queue import Queue
import threading

queue = Queue()

def producer():
    for i in range(5):
        queue.put(i)
    queue.put(None)  # sentinelle de fin

def consumer():
    while True:
        item = queue.get()
        if item is None:
            break
        print(f"Traitement {item}")
        queue.task_done()

Queue est souvent la primitive la plus propre pour producteur/consommateur.

2. ThreadPoolExecutor et concurrent.futures

from concurrent.futures import ThreadPoolExecutor

def fetch(url):
    # appel réseau simulé
    return f"fetched {url}"

urls = ["u1", "u2", "u3"]

with ThreadPoolExecutor(max_workers=8) as pool:
    results = list(pool.map(fetch, urls))

print(results)

C’est généralement la meilleure porte d’entrée haut niveau pour gérer plusieurs tâches I/O en Python.

ProcessPoolExecutor

Pour les tâches CPU-bound, ProcessPoolExecutor ou multiprocessing sont souvent plus adaptés que les threads.

3. Multiprocessing et alternatives

Le multiprocessing crée plusieurs processus. Chaque processus a son propre interpréteur et contourne donc la limitation du GIL pour le CPU. En contrepartie :

  • coût mémoire plus élevé,
  • coût de sérialisation entre processus,
  • communication plus lourde.
ApprocheBonne pourLimite principale
threadingI/O-bound légerPas de vrai parallélisme CPU pur sous CPython.

4. asyncio quand pertinent

asyncio n’est pas du multithreading. C’est de la concurrence coopérative basée sur une boucle événementielle. Très adapté quand tu as énormément d’I/O réseau et peu de calculs bloquants. Ce n’est pas un remplacement universel des threads.

5. Recommandations de senior

  • Choisis la primitive selon la nature de la charge : I/O, CPU, latence, volumétrie.
  • Préférer Queue et ThreadPoolExecutor aux bricolages manuels.
  • Évite de partager des objets mutables complexes sans protocole clair.
  • Documente qui produit, qui consomme, qui arrête, et comment on fait remonter les erreurs.

Pièges fréquents

  • Le GIL n’empêche pas toutes les races logiques.
  • Un trop grand nombre de threads peut dégrader les performances.
  • Les exceptions dans des workers oubliés sont une vraie source de bugs fantômes.
