Java — Concurrency avancée

Synchronisation, JMM, atomiques, locks, queues, pools et primitives avancées en Java.

1. Introduction

La vraie puissance de Java apparaît avec java.util.concurrent et le Java Memory Model. Ici, on quitte la simple création de threads pour entrer dans la coordination, la scalabilité et la sûreté mémoire.

2. Synchronisation classique

synchronized

synchronized protège une section critique via le moniteur d’un objet. Il apporte exclusion mutuelle et effets de visibilité mémoire.

public class Counter {
    private int value = 0;

    public synchronized void increment() {
        value++;
    }

    public synchronized int getValue() {
        return value;
    }
}

Verrou d’instance vs verrou de classe

  • Méthode d’instance synchronisée : verrou sur this.
  • Méthode statique synchronisée : verrou sur l’objet Class.

wait / notify / notifyAll

Ce trio permet d’attendre une condition sur un moniteur. Toujours utiliser une boucle while et non un simple if à cause des réveils intempestifs.

BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);

queue.put("message");   // bloque si la file est pleine
String value = queue.take(); // bloque si la file est vide

Pour un pipeline producteur/consommateur, BlockingQueue est souvent préférable à une coordination manuelle par wait/notify.

4. Modèle mémoire Java

volatile

volatile garantit principalement la visibilité et certaines contraintes d’ordre. Il ne rend pas atomique un counter++.

class StopSignal {
    volatile boolean running = true;
}

AtomicInteger

Quand tu as besoin d’une opération atomique simple comme un incrément sûr, préfère souvent AtomicInteger.

AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();

happens-before

Le JMM définit des règles garantissant qu’une écriture devient visible pour une lecture ultérieure dans un autre thread. Les locks, accès volatile, démarrage de thread, fin de thread et autres primitives créent ces relations.

5. Exécution asynchrone haut niveau

ExecutorService et ThreadPoolExecutor

ExecutorService pool = Executors.newFixedThreadPool(8);

pool.submit(() -> {
    // traitement I/O ou CPU selon le cas
});

pool.shutdown();

ScheduledExecutorService

Permet de planifier une tâche périodique ou différée.

CompletableFuture

CompletableFuture.supplyAsync(() -> fetchCustomer())
    .thenApply(customer -> enrich(customer))
    .thenAccept(System.out::println)
    .exceptionally(ex -> {
        ex.printStackTrace();
        return null;
    });

CompletableFuture est utile pour composer plusieurs traitements sans sombrer dans l’enfer des callbacks. Attention : il faut savoir sur quel executor tourne chaque étape.

6. Collections concurrentes et cas réels

ConcurrentHashMap

Appropriée quand plusieurs threads lisent et écrivent une map partagée sans verrou global externe.

Cas d’usage entreprise

  • Backend HTTP qui traite plusieurs requêtes en parallèle.
  • Workers qui consomment une queue interne puis appellent des APIs externes.
  • Consommateurs Kafka traitant des événements et enrichissant des données.
  • Batch de recalcul réparti via pool et barrière de synchronisation.

Pièges fréquents

  • Un pool mal dimensionné peut bloquer toute l’application.
  • CompletableFuture sans executor explicite peut utiliser le pool commun à ton insu.
  • volatile ne remplace pas un verrou pour les mises à jour composées.

À retenir

  • Utilise d’abord les primitives haut niveau de java.util.concurrent.
  • Comprendre le JMM évite les faux raisonnements sur la visibilité.
  • Choisis la primitive la plus simple qui garantit la sûreté nécessaire.
