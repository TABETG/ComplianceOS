Introduction au multithreading

Pourquoi les threads existent, ce qu’ils apportent, ce qu’ils coûtent et pourquoi ils sont difficiles à maîtriser.

1. Introduction

Un thread est une unité d’exécution à l’intérieur d’un processus. Plusieurs threads d’un même processus partagent la même mémoire, les mêmes objets, les mêmes fichiers ouverts, mais ils ont chacun leur pile d’exécution et leur compteur d’instruction. Dit autrement : un processus est une “boîte d’application”, un thread est un “ouvrier” qui travaille à l’intérieur.

Le multithreading sert à faire avancer plusieurs tâches en même temps ou, plus précisément, à laisser plusieurs unités de travail progresser de manière concurrente. Cela peut améliorer la réactivité, le débit, l’utilisation CPU, ou simplement éviter de bloquer le thread principal pendant une attente réseau, disque ou I/O.

À retenir

  • Multithreading ne veut pas automatiquement dire 'plus rapide'.
  • Le vrai enjeu n’est pas seulement la création de threads mais la coordination entre eux.
  • Plusieurs threads partagent souvent le même état, donc les bugs peuvent être subtils.

2. Définition simple, utilité, importance

Définition simple

Un thread exécute du code. Si tu n’as qu’un seul thread, ton application fait une chose à la fois. Si tu en as plusieurs, plusieurs tâches peuvent avancer en parallèle réel ou apparent selon le nombre de cœurs CPU et l’ordonnancement de l’OS.

À quoi ça sert

  • Garder une application fluide pendant des opérations lentes.
  • Traiter plusieurs requêtes utilisateur ou messages simultanément.
  • Construire des workers, pipelines, batchs ou consommateurs de messages.
  • Exploiter plusieurs cœurs CPU pour certains calculs.

Quand on l’utilise

  • Backend web qui reçoit plusieurs requêtes.
  • Consommation Kafka ou RabbitMQ.
  • Téléchargements, appels HTTP, accès base de données, scraping, fichiers.
  • Traitements batch parallélisés.

Pièges fréquents

  • Confondre concurrence et parallélisme.
  • Croire que plus de threads = forcément meilleures performances.
  • Oublier le coût de synchronisation et de contention.

Exemple mental

Imagine une cuisine de restaurant. Le processus est le restaurant entier. Chaque thread est un cuisinier. Tous les cuisiniers partagent le même frigo et les mêmes ustensiles. Si deux cuisiniers prennent la même casserole au même moment sans coordination, le chaos commence.

Exemple minimal

public class Main {
    public static void main(String[] args) {
        Thread worker = new Thread(() -> {
            System.out.println("Travail en arrière-plan");
        });

        worker.start(); // démarre un vrai nouveau thread
        System.out.println("Thread principal");
    }
}

Ici, l’ordre d’affichage n’est pas garanti. Le thread principal et le thread worker peuvent s’exécuter dans un ordre différent selon l’ordonnancement.

4. Niveau intermédiaire

En vrai projet, le problème n’est presque jamais “comment créer un thread ?” mais plutôt :

  • combien de threads créer,
  • comment leur donner du travail,
  • comment partager ou éviter de partager l’état,
  • comment arrêter proprement un traitement,
  • comment éviter saturation, blocage ou corruption de données.

Dans un backend Spring Boot, on préfère généralement un pool de threads, des queues, des executors ou des frameworks plus haut niveau plutôt que des `new Thread(...)` partout.

import threading
import time

def fetch_data():
    print("Début appel I/O")
    time.sleep(2)
    print("Fin appel I/O")

worker = threading.Thread(target=fetch_data)
worker.start()

print("Le thread principal continue...")
worker.join()
print("Travail terminé")

Ce code n’accélère pas forcément le CPU, mais il montre bien qu’on peut laisser un travail attendre pendant qu’un autre thread continue.

5. Niveau avancé

Coûts réels du multithreading

  • Coût mémoire de chaque thread.
  • Context switching : le CPU change de thread courant.
  • Contention sur les verrous.
  • Complexité mentale et bugs non déterministes.
  • Difficulté de test et de reproduction.

Quand il ne faut pas l’utiliser

  • Quand un traitement simple synchrone suffit.
  • Quand l’état partagé serait trop risqué.
  • Quand la vraie attente vient d’un service externe lent qui impose déjà ses propres limites.
  • Quand l’asynchrone ou la file de messages serait plus adaptée.

Recommandations de senior

  • Réduis au minimum l’état mutable partagé.
  • Fais circuler des messages ou tâches plutôt que des objets mutables partagés.
  • Documente les garanties thread-safe d’une classe.
  • Prévois toujours une stratégie d’arrêt, de timeout et d’observabilité.

6. Comparaison simple : synchrone, concurrence, parallélisme

ConceptDéfinitionExemple
SynchroneUne action attend la fin de la précédenteLire 10 fichiers un à un.
ConcurrencePlusieurs tâches progressent sans forcément s’exécuter physiquement en même tempsServeur qui gère plusieurs clients.
ParallélismePlusieurs tâches s’exécutent réellement sur plusieurs cœursCalcul matriciel réparti sur 8 cœurs.

À retenir

  • Concurrence = organisation de plusieurs tâches.
  • Parallélisme = exécution physique simultanée.
  • Une application concurrente n’est pas forcément parallèle.
