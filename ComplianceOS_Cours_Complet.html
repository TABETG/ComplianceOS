Une plateforme SaaS d'intelligence réglementaire qui aide les entreprises à se conformer à NIS2, DORA, RGPD et ISO 27001 grâce à l'IA, la signature électronique qualifiée et une architecture cloud-native moderne.

⬡ Méthodologie

Comment aborder ce projet

Principes fondamentaux à garder en tête tout au long des 12 mois.

📐 DDD — Domain-Driven Design

Le code est organisé autour du domaine métier, pas des frameworks. Tes entités principales : Company (l'entreprise cliente), Audit (un audit de conformité), Policy (une politique interne), RiskItem (un écart identifié), Evidence (une preuve). Tout le reste gravite autour de ces entités.

🔑 Multi-tenancy — Isolation par tenant

Chaque client (entreprise) est un tenant isolé. En pratique : Row-Level Security PostgreSQL pour que les données d'un tenant ne soient jamais visibles par un autre. C'est la base du SaaS B2B. Chaque requête SQL filtre automatiquement par tenant_id.

📡 API-First

Le contrat API (Protobuf pour gRPC, GraphQL schema, OpenAPI 3.1 pour REST) est défini avant le code. Cela permet aux services de se développer en parallèle. Les tests de contrat Pact valident que l'API respecte sa promesse.

🔄 GitOps — Infrastructure comme code

Tout est versionné : le code, la configuration Kubernetes, l'infrastructure AWS. ArgoCD surveille le repo Git et déploie automatiquement ce qui y est décrit. La production = le contenu du repo Git. Pas de surprises, pas de config manuelle.

Phase 1 · Core Platform & Auth · Mois 1–2

Java 24 — Le langage du backend

Java 24 introduit des fonctionnalités majeures qui changent la façon d'écrire du code concurrentiel et expressif. Voici ce que tu vas utiliser concrètement.

Virtual Threads
Project Loom
CONCURRENCE
Les virtual threads permettent d'écrire du code concurrent comme du code séquentiel, mais avec des performances asynchrones. Finis les callbacks et CompletableFuture complexes.
Dans ComplianceOS : chaque requête HTTP est traitée dans un virtual thread. Avec 10 000 requêtes simultanées, Java 24 utilise quelques threads OS seulement au lieu de 10 000.
Structured Concurrency
JEP 462
CONCURRENCE
Gère des tâches parallèles comme une unité : si une tâche échoue, les autres sont annulées automatiquement. Plus de fuite de threads.
Utilisation : appel parallèle vers le service ML Python ET le service RAG, avec timeout global sur les deux.
Records + Sealed Classes
Java 17+, stabilisé
EXPRESSIVITÉ
Records = classes immuables en une ligne. Sealed classes = hiérarchies fermées pour les types algébriques. Idéal pour les événements Kafka.
Exemple : record AuditCreatedEvent(UUID auditId, String tenantId, Instant timestamp){}
Java 24 AuditService.java — Virtual Threads + Structured Concurrency
@Service public class AuditService { // Virtual Thread ExecutorService — c'est tout ce qu'il faut configurer private final ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor(); @Transactional public AuditResult processAudit(UUID auditId) { // Structured Concurrency : les 2 tâches tournent en parallèle try (var scope = new StructuredTaskScope.ShutdownOnFailure()) { var mlScore = scope.fork(() -> mlService.scoreRisk(auditId)); var ragResult = scope.fork(() -> ragService.analyze(auditId)); scope.join().throwIfFailed(); // attend les 2, fail-fast si l'une échoue return new AuditResult(mlScore.get(), ragResult.get()); } } } // Record immuable pour l'event Kafka public record AuditCreatedEvent( UUID auditId, String tenantId, String companyName, Instant createdAt ) {} // Sealed class pour les statuts d'audit (type algébrique) public sealed interface AuditStatus permits Draft, InProgress, Completed, Archived {}
💡 Concepts clés à retenir
  • Thread OS : thread natif du système, coûteux (1–2 Mo de mémoire). Limité à quelques milliers.
  • Virtual Thread : thread géré par la JVM, ultra-léger (quelques Ko). Peut en créer des millions.
  • Blocking = OK avec virtual threads : si le virtual thread attend une I/O, la JVM le "démonte" du thread OS et réutilise ce thread OS pour autre chose.
  • Record : génère automatiquement constructeur, equals, hashCode, toString. Immuable par design.
  • Sealed interface : le compilateur sait tous les types possibles → pattern matching exhaustif avec switch.

🔑 Concepts Spring essentiels
  • IoC (Inversion of Control) : tu ne crées pas les objets, Spring les crée et les injecte où tu en as besoin via @Autowired ou constructeur.
  • Bean : un objet géré par Spring. Annoté @Service, @Repository, @Component, etc.
  • @Transactional : toute la méthode s'exécute dans une transaction DB. Si une exception survient → rollback automatique.
  • @Valid : valide automatiquement le body de la requête selon les annotations Bean Validation (@NotNull, @Size, etc.).

PostgreSQL 17 — La base de données principale

PostgreSQL 17 est la base de données relationnelle la plus avancée du monde open source. Dans ComplianceOS, elle fait tout : données métier, isolation multi-tenant, vecteurs pour l'IA.

Row-Level Security (RLS)
Politique de sécurité au niveau de chaque ligne. PostgreSQL filtre automatiquement les données par tenant_id, côté base de données. Même si le code oublie le filtre, la DB refuse de montrer les données d'un autre tenant.
C'est le verrou ultime de la multi-tenancy. Même un bug dans le code Java ne peut pas exposer les données d'un autre client.
pgvector
Extension PostgreSQL qui ajoute un type de données VECTOR et des index pour la recherche par similarité cosine. Permet le RAG directement dans PostgreSQL.
Les embeddings des articles NIS2/DORA sont stockés ici. La recherche sémantique "trouve les articles similaires à ma question" tourne dans la DB.
Flyway
Versionning des migrations SQL. Chaque changement de schéma est un fichier SQL numéroté. Flyway les applique dans l'ordre au démarrage.
Le schéma en production est identique au schéma de développement. Jamais de "ça marche chez moi mais pas en prod".
SQL — PostgreSQL 17 V1__init_schema.sql — Multi-tenancy + RLS + pgvector
-- Table principale des audits (toutes les données filtrées par tenant_id) CREATE TABLE audit ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), tenant_id TEXT NOT NULL, -- clé de partition tenant company_id UUID NOT NULL, status TEXT NOT NULL DEFAULT 'DRAFT', regulation TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW() ); -- Row-Level Security : la DB elle-même filtre par tenant ALTER TABLE audit ENABLE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation ON audit USING (tenant_id = current_setting('app.tenant_id')); -- Extension pgvector pour les embeddings IA CREATE EXTENSION IF NOT EXISTS vector; -- Table des chunks réglementaires vectorisés (pour le RAG) CREATE TABLE regulatory_chunk ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), article_id TEXT NOT NULL, -- ex: "NIS2-Art-21" regulation TEXT NOT NULL, content TEXT NOT NULL, embedding vector(1536) NOT NULL -- 1536 dims pour Titan v2 ); -- Index HNSW pour la recherche cosine rapide CREATE INDEX ON regulatory_chunk USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- Recherche : les 5 chunks les plus proches d'un embedding de question SELECT article_id, content, 1 - (embedding <<=> '[0.1, 0.3, ...]'::vector) AS similarity FROM regulatory_chunk ORDER BY embedding <<=> '[0.1, 0.3, ...]'::vector LIMIT 5;

Keycloak est le serveur d'identité open source de référence. Il gère SSO, RBAC, tokens JWT et les méthodes d'auth modernes (Passkeys, MFA). Tu ne codes plus d'authentification from scratch.

Le JWT contient : user_id, tenant_id, rôles. Chaque microservice valide le JWT localement (sans appeler Keycloak). C'est du stateless auth.

Passkeys FIDO2
Authentification sans mot de passe. La clé privée ne quitte jamais l'appareil de l'utilisateur. Résistant au phishing, conforme NIS2 (MFA fort).
NIS2 exige l'authentification multi-facteurs pour les systèmes critiques. Passkeys = solution la plus robuste et la meilleure UX.
RBAC / ABAC
4 rôles : ADMIN (tout), AUDITOR (audits R/W), VIEWER (lecture seule), EXTERNAL_AUDITOR (audits partagés uniquement). Les permissions sont dans le JWT.
Quand un admin change le rôle d'un utilisateur, le token est invalidé dans Redis et un nouveau token avec les bons rôles est émis. Instantané.

GraphQL Netflix DGS — API externe flexible

GraphQL est l'API publique de ComplianceOS. Contrairement à REST, le client demande exactement les champs dont il a besoin. Pas de sur-fetch, pas de sous-fetch.

GraphQL vs REST
Avec REST, tu as 5 endpoints pour obtenir les infos d'un audit. Avec GraphQL, une seule requête demande exactement les champs voulus, depuis n'importe quelle profondeur du graphe de données.
Idéal pour les clients SaaS qui ont des besoins variés. Le frontend Next.js peut optimiser ses queries sans changer le backend.
Netflix DGS
Framework GraphQL pour Spring Boot, développé par Netflix. Annotations simples, intégration Spring native, DataLoaders pour éviter le N+1 problem.
Le N+1 problem : charger 100 audits puis 100 queries pour charger leurs entreprises. DataLoader batch tout en 1 query.

FastAPI 0.115 — L'API Python haute performance

FastAPI est le framework Python préféré pour les APIs de ML. Async natif, validation automatique des données avec Pydantic, génération OpenAPI automatique.

Async natif
FastAPI est basé sur ASGI (comme WSGI mais async). Chaque endpoint peut être async def. Idéal pour appels parallèles vers des LLMs ou bases de données.
L'analyse d'un document fait 3 appels : extraction texte, embedding, appel LLM. Avec async, les appels indépendants tournent en parallèle.
Pydantic v2
Validation automatique des données d'entrée et de sortie. Si le body JSON ne correspond pas au schéma → HTTP 422 automatique avec le détail de l'erreur.
Les réponses JSON du service ML sont toujours conformes au schéma. Plus de "KeyError" en prod parce qu'un champ était absent.

LangChain 0.3 (Python) — Agents et RAG

LangChain est le framework Python pour construire des applications basées sur des LLMs. Tu y définis des chaînes de traitement, des agents avec des outils, et des pipelines RAG.

🤖 Qu'est-ce qu'un Agent LangChain ?

Un agent est un LLM qui peut décider d'utiliser des outils pour répondre à une question. Il raisonne en boucle : "j'ai besoin d'info X → j'utilise l'outil search → j'ai le résultat → je peux maintenant répondre". C'est fondamentalement différent d'un simple prompt.

Python — LangChain 0.3 document_analyzer_agent.py
from langchain.agents import AgentExecutor, create_tool_calling_agent from langchain_community.tools import tool from langchain_aws import ChatBedrock # LLM : Claude 3.5 Sonnet via AWS Bedrock (données privées dans le VPC) llm = ChatBedrock( model_id="anthropic.claude-3-5-sonnet-20241022-v2:0", region_name="eu-west-1" ) # Outil 1 : recherche dans le corpus réglementaire @tool def search_regulation_corpus(query: str) -> str: """Recherche dans les articles NIS2, DORA, RGPD et ISO 27001.""" results = vector_store.similarity_search(query, k=5) return "\n\n".join([r.page_content for r in results]) # Outil 2 : classification d'un écart (gap) @tool def classify_gap(gap_description: str) -> str: """Classifie un gap de conformité : LOW / MEDIUM / HIGH / CRITICAL.""" # Logique de classification basée sur le contexte réglementaire return gap_classifier.predict(gap_description) # Agent avec ses outils tools = [search_regulation_corpus, classify_gap] agent = create_tool_calling_agent(llm, tools, prompt) runner = AgentExecutor(agent=agent, tools=tools, verbose=True) # L'agent raisonne autonomement et utilise les outils selon ses besoins result = runner.invoke({ "input": "Analysez cette politique de sécurité et identifiez les gaps NIS2", "document_text": extracted_text })

XGBoost + SHAP — Scoring de risque ML

XGBoost est l'algorithme de gradient boosting le plus utilisé dans l'industrie. Rapide, précis, interprétable avec SHAP. Tu l'utilises pour calculer le score de risque réglementaire de chaque entreprise.

🌳 Comment fonctionne XGBoost (simplifié)

XGBoost construit une forêt d'arbres de décision en séquence. Chaque arbre corrige les erreurs du précédent. Au final : 100 arbres légers qui votent ensemble = prédiction robuste. Bien meilleur qu'un seul gros arbre.

SHAP (SHapley Additive exPlanations) : explique pourquoi le modèle a donné ce score. "Le secteur Santé contribue +15 points au risque car c'est un secteur critique NIS2." Indispensable pour la conformité réglementaire.

Temporal.io — Orchestration durable de workflows

Temporal est la plateforme d'orchestration de workflows la plus robuste. Un workflow Temporal survit aux pannes, aux redémarrages, aux timeouts. C'est la colonne vertébrale du cycle de vie d'un audit.

⚡ Pourquoi Temporal est révolutionnaire

Sans Temporal : un audit qui prend 3 jours (analyse IA + validation humaine + signature) peut planter à n'importe quelle étape. Tout recommence depuis zéro.

Avec Temporal : chaque étape est enregistrée en durée indéfinie. Si le service IA plante après l'étape 2, Temporal reprend à l'étape 3 automatiquement. La validation humaine peut attendre 30 jours sans perte d'état.

Java — Temporal.io AuditWorkflow.java — Cycle de vie complet
// Le workflow orchestre les étapes — chaque étape est durable @WorkflowInterface public interface AuditWorkflow { @WorkflowMethod AuditResult runAudit(UUID auditId); // Signal : l'auditeur valide depuis l'interface Next.js @SignalMethod void humanValidate(ValidationDecision decision); } public class AuditWorkflowImpl implements AuditWorkflow { private ValidationDecision validationDecision; // persisté par Temporal @Override public AuditResult runAudit(UUID auditId) { // Étape 1 : Ingestion des documents activities.ingestDocuments(auditId); // Étape 2 : Analyse IA — retry 3x avec backoff si panne AnalysisResult analysis = Workflow.newActivityStub( AIAnalysisActivity.class, ActivityOptions.newBuilder() .setStartToCloseTimeout(Duration.ofMinutes(10)) .setRetryOptions(RetryOptions.newBuilder().setMaximumAttempts(3).build()) .build() ).analyze(auditId); // Étape 3 : Scoring ML activities.scoreML(auditId, analysis); // Étape 4 : Attente validation humaine (jusqu'à 30 jours!) Workflow.await( Duration.ofDays(30), () -> validationDecision != null ); // Étape 5 : Signature électronique activities.signDocument(auditId); // Étape 6 : Archivage return activities.archive(auditId); } @Override public void humanValidate(ValidationDecision decision) { this.validationDecision = decision; // Temporal persiste ce signal } }

AWS Bedrock + RAG — LLM privé et recherche sémantique

AWS Bedrock donne accès à des LLMs (dont Claude 3.5) dans ton VPC AWS. Les données ne quittent jamais ton infrastructure. Le RAG (Retrieval-Augmented Generation) ancre les réponses du LLM dans des faits réels.

🧠 Qu'est-ce que le RAG ?

Sans RAG : tu demandes au LLM "Que dit NIS2 Article 21 ?" → il hallucine ou donne une réponse générique non sourcée.

Avec RAG : 1) ta question est transformée en vecteur (embedding), 2) on cherche les passages les plus similaires dans le corpus réglementaire, 3) ces passages sont injectés dans le contexte du LLM, 4) le LLM répond avec des sources exactes.

Qdrant + pgvector — Base de données vectorielle

Les vecteurs (embeddings) sont des représentations numériques de texte qui capturent le sens. Qdrant et pgvector permettent de chercher par similarité sémantique, pas par mots-clés.

🔢 Comment fonctionne la recherche vectorielle

"Mesures de sécurité réseau" et "protection des infrastructures informatiques" : même sens, mots différents. La recherche par mots-clés rate. La recherche vectorielle trouve les deux car leurs vecteurs sont proches dans l'espace mathématique.

ComplianceOS utilise la recherche hybride : dense (similarité cosine via pgvector) + sparse (BM25 via Qdrant) + reranking. Les 3 méthodes combinées donnent les meilleurs résultats.

Phase 4 · Signature & Cryptographie · Mois 7–8

eIDAS 2.0 — Signature électronique qualifiée (QES)

eIDAS 2.0 est le règlement européen sur l'identité numérique. Une signature QES (Qualified Electronic Signature) a la même valeur légale qu'une signature manuscrite dans toute l'Union Européenne.

Types de signatures
SES (Simple) : email avec nom. Pas de valeur légale.
AES (Avancée) : identité vérifiée, clé liée à la personne.
QES (Qualifiée) : clé stockée en HSM certifié QSCD. Valeur légale maximale.
ComplianceOS génère des QES (PAdES-LTA). Les rapports d'audit signés sont valables devant un tribunal EU.
PAdES-LTA
PDF Advanced Electronic Signature - Long Term Availability. La signature inclut un horodatage RFC 3161 et toutes les informations nécessaires pour la vérifier dans 50 ans, sans dépendre de services externes.
Les rapports d'audit doivent être conservés 7 ans (DORA/NIS2). La signature doit rester valide pendant tout ce temps.
🔐 Chaîne de confiance PKI — Comment ça marche
1
CA Racine (Root CA) : autorité de certification de confiance. Certifie l'autorité intermédiaire.
2
CA Intermédiaire : émet les certificats utilisateurs. Si compromise, seule l'intermédiaire est révoquée.
3
Certificat utilisateur : lié à l'identité de l'auditeur. Sa clé privée est dans le HSM.
4
HSM (Hardware Security Module) : boîtier physique certifié FIPS 140-2 où la clé privée est générée et ne quitte jamais le matériel.
5
TSA (Time Stamp Authority) : horodatage qualifié signé par une autorité reconnue. Prouve que le document existait à ce moment précis.

HashiCorp Vault 1.17 — PKI dynamique et secrets

Vault est le gestionnaire de secrets de référence. Il génère des certificats TLS à courte durée de vie, tourne les credentials de base de données, et injecte les secrets dans Kubernetes automatiquement.

🔑 Pourquoi "pas de secrets dans le code"

Le pattern classique dangereux : mot de passe PostgreSQL dans application.yml → committé dans Git → exposé à toute l'équipe et potentiellement en ligne.

Avec Vault : les services démarrent sans secrets. Vault injecte les credentials au runtime, via le sidecar Vault Agent dans Kubernetes. Les credentials expirent après 24h et sont renouvelés automatiquement.

Istio — Service Mesh et Zero-Trust

Istio est un service mesh qui s'intercale entre chaque pod Kubernetes. Il chiffre automatiquement tout le trafic réseau entre services (mTLS) sans modifier le code applicatif.

🛡️ Zero-Trust Network — le principe

"Ne fais confiance à personne, vérifie tout." Dans un cluster Kubernetes sans Istio, si un attaquant prend le contrôle d'un pod, il peut contacter tous les autres pods librement. Avec Istio en mode strict mTLS : chaque service doit présenter un certificat valide pour pouvoir communiquer. Un pod compromis est isolé.

Kafka 3.8 KRaft — Event Streaming

Kafka est la plateforme de streaming de messages la plus utilisée en production. Dans ComplianceOS, chaque changement d'état d'un audit publie un événement Kafka que tous les services intéressés consomment.

📡 Event-Driven Architecture — Le pattern de fond

Sans Kafka : le service Audit appelle directement le service Notification, le service ML, le service Archivage. Couplage fort. Si la Notification est down, l'Audit échoue aussi.

Avec Kafka : le service Audit publie audit.completed et oublie. La Notification, le ML, l'Archivage sont abonnés et réagissent indépendamment. Si la Notification est down, elle lit les messages manquants quand elle redémarre. Couplage zéro.

Quarkus 3.15 + GraalVM — Native Image

Quarkus compile Java en binaire natif via GraalVM. Résultat : démarrage en 50ms au lieu de 5s, consommation mémoire de 30Mo au lieu de 300Mo. Idéal pour le service de notification à fort volume.

Spring Boot vs Quarkus
Spring Boot : JVM classique, démarrage ~3-5s, ~300Mo RAM. Parfait pour la logique métier complexe. Quarkus Native : démarrage <50ms, ~30Mo RAM. Parfait pour les microservices stateless à haute fréquence.
Le service de notification reçoit des milliers d'events Kafka/minute. Son cold start (KEDA scale-up) doit être imperceptible. → Quarkus native.
GraalVM Native Image
GraalVM analyse le bytecode Java à la compilation et génère un binaire natif pour la plateforme cible (Linux AMD64). Tout ce qui n'est pas utilisé est éliminé (dead code elimination).
Le binaire natif inclut tout ce dont l'application a besoin. Pas de JVM à démarrer. Exécution directe comme un programme C.

Chaos Engineering — Tester la résilience

Le Chaos Engineering consiste à provoquer délibérément des pannes en production (ou staging) pour valider que le système s'en remet correctement. "Test before prod tests you."

💥 Les 4 expériences Chaos Mesh dans ComplianceOS
1
PodChaos : tue un pod aléatoire du service Notification → Kubernetes doit le redémarrer et SSE doit se rétablir en <2 min (cache Redis).
2
NetworkChaos : ajoute 200ms de latence réseau → le circuit breaker Resilience4j s'ouvre et le service répond avec un fallback en <100ms.
3
IOChaos : simule un disque lent → les services avec retry exponentiels doivent absorber le problème.
4

@RestController @RequestMapping("/webhooks/stripe") public class StripeWebhookController { @PostMapping public ResponseEntity<Void> handleWebhook( @RequestBody String payload, @RequestHeader("Stripe-Signature") String sig ) throws Exception { // Valider que le webhook vient bien de Stripe (HMAC SHA-256) Event event = Webhook.constructEvent(payload, sig, stripeSecret); switch (event.getType()) { case "checkout.session.completed": // Paiement réussi → activer l'abonnement immédiatement var session = (Session) event.getDataObjectDeserializer().getObject().get(); subscriptionService.activate(session.getCustomerEmail(), session.getMetadata()); break; case "invoice.payment_failed": // Paiement échoué → notifier + retry dans 3 jours billingService.handlePaymentFailure(event); break; case "customer.subscription.deleted": // Résiliation → passer en lecture seule 30 jours subscriptionService.downgrade(event); break; } return ResponseEntity.ok().build(); } }
